## M002 · 助手

先别从 Bronze / Silver / Gold 开始。先把 **Hermes 到底是什么角色、一次工作循环是什么** 定死。

我建议从这 4 层往下设计。

### 1. 先定 Hermes 的身份

Hermes 不是“自动建湖脚本”，而是一个 **长期存在的 Data Steward Agent**：

> 围绕一个业务目标，持续发现数据、人和业务知识；在授权范围内推进数据治理；关键节点找人确认；把确认后的知识沉淀下来。

所以它的北极星不是：

`把 Bronze → Silver → Gold 跑完`

而应该类似：

`持续把某个业务域的数据变成可信、可理解、可复用的数据资产。`

Bronze / Silver / Gold 只是它执行任务的几个阶段。

---

### 2. 再定义最核心的 Loop

我认为你的 Hermes 主循环应该是：

```text
恢复长期状态
↓
现在的 North Star 是什么？
↓
现在有哪些未完成事项？
↓
能自己推进吗？
├─ 能 → 执行
└─ 不能 → 找对应的人
↓
过程中发现：
人 / 表 / JOIN / 业务定义 / 新问题
↓
立即沉淀
↓
达到 checkpoint？
├─ 否 → 继续推进其他事项
└─ 是 → 汇报 + 等人决策
↓
本轮结束
↓
等待新消息 / 审批 / cron 唤醒
```

这个才是你应该先实现清楚的东西。

不是：

```text
找表 → bronze → silver → gold → 完
```

因为真实组织里的工作会不断分叉、等待人、补信息、回来修改。

---

### 3. 然后定义 Hermes 永远要记住的 5 类 State

这是你下一步最值得先设计的数据结构。

**Mission**
```text
North Star
当前 scope
Sponsor
成功标准
```

**World Model**
```text
认识哪些人
谁负责什么
有哪些数据源
有哪些表
表之间可能是什么关系
```

**Knowledge**
```text
字段是什么意思
指标定义
JOIN 关系
哪些是 hearsay
哪些 confirmed
谁确认的
```

**Work State**
```text
当前有哪些 task
状态是什么
blocked_by 谁
next_action 是什么
```

**Data Lifecycle**
```text
source
→ discovered
→ approved
→ bronze
→ silver candidate
→ silver verified
→ gold candidate
→ published
```

这样新会话启动时，Hermes 不需要“回忆聊天记录”。

而是：

```text
load mission
load assets
load people
load confirmed knowledge
load open tasks
```

这才是真正的长期 Agent。

---

### 4. 最后才设计 checkpoint

Checkpoint 不应该按“每知道一张表”触发。

应该按 **决策风险** 触发。

例如：

```text
发现一张表
→ Hermes 自己登记
→ 不需要打扰人

准备复制生产数据
→ 权限 checkpoint

准备定义清洗规则
→ 业务 owner checkpoint

准备确认 JOIN
→ domain expert checkpoint

Silver 首次产出
→ sample review checkpoint

Gold 发布
→ owner / sponsor checkpoint
```

这就很符合“人之常情”。

Hermes 平时自己干活，**只有需要人承担决策责任时才找人**。

---

所以你现在第一件事，我建议不是继续改工具，而是先画这个东西：

```text
Hermes State Machine

IDLE
↓
DISCOVERING
↓
WAITING_FOR_ACCESS
↓
BRONZE_READY
↓
WAITING_FOR_STAGE_APPROVAL
↓
SILVER_BUILDING
↓
WAITING_FOR_DOMAIN_REVIEW
↓
SILVER_VERIFIED
↓
GOLD_BUILDING
↓
WAITING_FOR_PUBLISH_APPROVAL
↓
PUBLISHED
↓
MONITORING
```

注意它旁边永远还有一个：

```text
BLOCKED / WAITING_FOR_HUMAN
```

但这个状态 **不会阻塞整个 Hermes**。A 表等财务确认时，它可以继续处理 B 表。

你现在真正要搞清楚的第一个问题其实是：

> **Hermes 的“工作单元”到底是什么？一张表、一个业务目标，还是一个 data product？**

我建议答案是 **一个 Business Mission / Data Product**。表只是 Mission 下面的资产。这样你后面的 Bronze、联系人、JOIN、审批、Gold 才不会越做越乱。

## M004 · 助手

### 1. North Star 不要放 Identity

**Identity 放稳定不变的东西：**

```text
You are Hermes, a persistent Data Steward Agent.

Your job:
- understand business data needs
- discover relevant people and data
- build trustworthy governed data assets
- never invent business semantics
- ask humans when authority or business judgment is required
- preserve provenance and confirmed knowledge
```

North Star 会换，所以不适合写死在 Identity。

建议三层：

```text
Identity            长期不变
└─ Hermes 是谁、原则是什么

Mission             一个项目周期
├─ North Star
├─ Sponsor
├─ Scope
├─ Success Criteria
└─ Target Data Product

Current Objective   中短期变化
├─ 当前阶段目标
├─ 当前缺口
└─ Next Actions
```

比如：

```text
North Star:
让管理层能够可信地分析客户利润。

Current Objective:
先确认收入、成本、退款三类数据来源。

Next Action:
找 Alice 确认退款表 owner。
```

所以你说的 **scope 也别只放普通 memory**。

它应该是结构化、持久化的 `Mission State`。Memory 可以给 Hermes 检索，但 Mission 是事实源。

---

### 2. “刚开始一张表都没有”时，不能规定一张表 = Silver

这里最好不要让 Bronze/Silver 驱动 Agent。

应该是 **Gap 驱动**。

刚启动：

```text
North Star
↓
需要回答什么业务问题？
↓
这些问题需要什么信息？
↓
当前知道哪些数据？
↓
缺什么？
↓
找人 / 找表
```

例如刚开始只知道：

```text
orders
```

Hermes 不应该想：

> 有一张表了，做 Silver。

而应该想：

```text
目标 = 客户利润

orders 能提供：
✓ 销售收入
✓ 客户
✓ 商品

仍缺：
? 成本
? 退款
? 折扣
? 汇率
```

于是自然多问几句：

> 成本在哪里？
> 退款是不是另一套系统？
> 最终财务认可哪个利润口径？

然后可能发现：

```text
orders
product_cost
refunds
customer
exchange_rate
```

这时候才逐渐形成一个完整 Data Product。

---

后期已经有很多表也一样。

不要：

```text
发现更多表 → 全部接入
```

而是：

```text
Mission requirement
↓
已有资产能不能满足？
├─ 能 → 不再扩张
└─ 不能
    ↓
    缺什么证据 / 字段 / 业务含义？
    ↓
    针对性找数据
```

这样 Hermes 不会变成“看到表就收藏”的 Data Hoarder。

可以给 discovery 一个简单原则：

> **Only discover outward when an unresolved requirement, quality issue, lineage dependency, or business question justifies it.**

---

### 3. 原表整改建议：建议纳入，但只做到“发现 + 建议 + 跟踪”

我会这样划权限边界：

```text
Hermes 可以：
✓ 发现源表问题
✓ 证明问题
✓ 判断影响
✓ 找 Owner 确认
✓ 提整改建议
✓ 建 issue / remediation task
✓ 跟踪有没有解决
```

例如：

```text
orders.status:
发现 7 个非标准状态值

影响：
Silver 需要额外 mapping

建议：
source system 将状态限制为枚举
```

但默认：

```text
Hermes 不直接：
✗ 改生产源表
✗ 改上游业务系统
✗ 强制修改业务流程
```

除非 Mission 明确授权。

所以它不是 out of scope。

更准确地说是：

> **Source remediation recommendation 属于 Data Steward scope；upstream modification 默认不属于 execution scope。**

这个设计也很漂亮，因为 Silver 不应该永远替源系统擦屁股。

Hermes 可以暂时：

```text
Bronze 原样保存
↓
Silver 修正
↓
同时创建 upstream remediation
```

以后上游改好了，再简化 Silver。

---

### 4. Data Product 要定义成“一个可以验收的东西”

别把 Data Product 定义成“一堆 Gold 表”。

建议：

> **Data Product = 为一个明确消费者/业务用途提供的、可持续维护、具有明确语义和质量承诺的数据输出。**

一个 Data Product 最少包含：

```text
Name
Purpose
Consumers
Business Questions
Owner

Inputs
Transformations
Confirmed Semantics
Output Schema / Metrics

Quality Rules
Freshness
Access Policy
Lineage

Acceptance Criteria
```

比如：

```text
Data Product:
Customer Profitability

Purpose:
分析客户级真实利润

Consumers:
Finance + Sales Management

Outputs:
customer_id
revenue
refund
cost
gross_profit
gross_margin

Required sources:
orders
refunds
product_cost

Acceptance:
- Finance 确认利润公式
- 99% order 可关联成本
- refund coverage >= 99.5%
- daily freshness
- lineage complete
- Owner approves release
```

这样就能明确 **什么时候停**。

---

Hermes 的 Mission 可以真正结束：

```text
Acceptance Criteria 全满足
+
无 critical unresolved gap
+
Owner 接受
↓
Mission = COMPLETED
```

然后不是继续无休止 BUILD，而是进入：

```text
MONITORING
```

只有出现：

```text
schema change
quality degradation
new business requirement
owner asks expansion
source changes
```

才重新开启工作。

所以完整生命周期我更建议：

```text
MISSION CREATED
↓
UNDERSTAND
↓
DISCOVER
↓
INGEST
↓
MODEL
↓
VALIDATE
↓
PUBLISH
↓
ACCEPTED
↓
MONITOR
```

**Bronze / Silver / Gold 是数据资产状态；不是 Hermes 自己的状态机。**

这个区分很关键。

Hermes 的状态是“我现在在做什么”。

表的状态才是：

```text
discovered → approved → bronze → silver → gold
```

Data Product 的状态则是：

```text
defined → building → validating → accepted → monitoring
```

这三套状态分开，你后面的设计会清楚很多。

## M006 · 助手

对。那 **Data Product 不适合作为 Hermes 的执行单元**，太大。

更合适的是三层：

```text
Mission       长期，几周到几个月
↓
Work Cycle    5–7 天
↓
Task          几小时到 1–2 天
```

### 你真正需要的是 `Work Cycle`

每次 Cycle 只推进一个有限范围：

```text
Cycle Goal:
把“客户收入”这部分数据搞清楚

本轮 Scope:
- 找到订单相关表
- 确认 owner
- 接入 bronze
- 理清关键字段
- 验证主要 JOIN
- 识别还缺什么

Out of scope:
- 成本
- 退款
- 上游源表整改
```

5–7 天后 **强制停一次**，不要求已经到 Silver/Gold。

Hermes 输出：

```text
Cycle Review

完成：
✓ 发现 4 张相关表
✓ 3 张已进入 bronze
✓ order/customer JOIN 已确认
✓ revenue 字段定义已确认

未完成：
- discount 含义等待 Alice
- 1 张表尚未获批

新发现：
- 退款可能来自另一系统
- customer_id 存在历史映射问题

建议下一 Cycle：
1. 补退款数据
2. 完成 revenue silver
3. 验证 customer mapping
```

然后 Sponsor 选择：

```text
[继续建议方案]
[调整优先级]
[缩小范围]
[扩大范围]
[本 Mission 暂停]
```

这样非常符合你说的“人之常情汇报”。

---

### Bronze / Silver 也不要绑定 Cycle

可能出现：

**Cycle 1**
```text
发现 6 张表
→ 3 张 Bronze
→ 还没有 Silver
```

完全正常。

**Cycle 2**
```text
补 2 张 Bronze
→ 做出 revenue Silver v1
```

**Cycle 3**
```text
补 refunds
→ revenue Silver 修订
→ 做第一个 Gold
```

所以 Hermes 判断的是：

> **这 5–7 天最值得降低哪个 uncertainty / gap？**

而不是：

> 这周必须从 Bronze 升到 Silver。

---

### 这样 North Star 体系也更清楚

### 目标

解决一个问题：

> Agent 可以持续自主推进，但不能无限跑。运行到一定阶段后必须停下来汇报，让人判断方向是否继续。

### Cycle 流程

```text
项目启动
↓
设定当前 Trust Level
↓
得到本轮 Cycle Budget
时间 / token / 工作量
↓
Agent 正常工作
↓
持续记录本轮变化
↓
是否触发 Cycle Stop？
├─ 否 → 继续
└─ 是
    ↓
    停止主动扩展
    ↓
    生成 Cycle Report
    ↓
    给 Sponsor / 项目负责人
    ↓
    人做决策
    ↓
    更新下一轮目标 + Trust Level
    ↓
    开启下一 Cycle
```

```text
Cycle Budget
最多多久 / 多少 token

Trust Level
当前自主程度

Previous Review
上一轮人给了什么意见
```

```text

可以找人、看表、做 profile、接 Bronze

Level 0
```

```text
Token Budget reached
```

### 4. Stop 后不是立刻停止所有东西

准确说是：

> **停止主动扩展新工作。**

```text

→ 又发现一个新系统
→ 再跑三小时
```

所以 Cycle Stop 相当于：


### 5. Cycle Report 应该固定格式

建议非常短。

| 项目 | 内容 |
|---|---|
| 本轮目标 | 原计划做什么 |
| 已完成 | 实际做完什么 |
| 新发现 | 新表、新人、新关系 |
| 未解决 | 当前还缺什么 |
| Blocked | 卡在哪、等谁 |
| 风险 | 有什么不确定性 |
| 建议下一步 | Agent 推荐怎么继续 |


主要决定：

```text

B. 自主周期要不要拉长/缩短
C. Scope 是否变化
```

```text

```

Trust 本质上控制：

> **多久需要整体接受一次人工校准。**

例如：

```text

Level 1 → 1天
Level 2 → 3天
Level 3 → 5–7天
```

升级依据先简单处理：

```text

方向正确
报告准确
没有大量返工
没有明显遗漏
```

就可以升级。

如果人发现 Agent 方向跑偏：

```text
Trust downgrade
Cycle 重新缩短
```

### 1. Role：长期基本不变

Role 是 Agent 的稳定身份。

例如：

```text
Role:
Data Steward Agent
```

它回答：

```text
我负责什么
我不负责什么
什么原则不能违反
遇到不确定性应该怎么处理
什么时候找人
```

比如：

```text
Hermes Data Steward

职责：
- 理解业务数据需求
- 主动发现相关人和数据
- 建立可信的数据资产
- 保留来源和确认记录
- 不猜测业务定义
- 不越权执行
```

Role 不应该频繁改。

---

### 2. Mission：每个项目一份

Mission 是当前项目上下文。

它回答：

```text
为什么做
谁发起
最终想解决什么
当前允许做到哪里
目前最重要的问题是什么
```

结构可以先固定成：

```text
North Star
Sponsor
Scope
Success Direction
Current Objective
Known Constraints
Current Status
```

---

### 3. North Star

North Star 是长期方向。

例如：

```text
让 Finance 和 Sales 能可信地分析客户利润。
```

它不是：

```text
这周接入 orders 表。
```

后者只是 Objective。

North Star 主要用来做一个判断：

> 新发现的事情值得继续追吗？

例如发现一张 `employee_attendance`：

```text
与客户利润无关
→ 不扩展
```

发现 `refunds`：

```text
直接影响利润
→ 应继续探索
```

---

### 4. Scope

Scope 是非常重要的边界。

例如：

```text
Current Scope:
- revenue
- customer
- refund

Out of Scope:
- HR
- marketing attribution
- source-system redesign
```

这样 Agent 即使发现很多东西，也不能无限扩张。

注意 Scope 可以变化，但应该由：

```text
Cycle review
Sponsor 指示
明确的新任务
```

来改变。

不能 Agent 自己不断扩大 Mission。

---

### 5. Current Objective

这个是 Mission 里面变化最快的部分。

例如：

```text
North Star:
客户利润分析

Current Objective:
先把 revenue 部分搞清楚
```

进一步可能变成：

```text
当前重点：
1. 确认 orders authoritative source
2. 确认 discount 是否包含在 order_total
3. 找 refund owner
```

所以层级是：

```text
Role
↓
Mission
↓
North Star
↓
Current Objective
↓
具体 Task
```

---

### 6. 工作过程中如何使用 Mission

Agent 每准备开启一个新分支，都问：

```text
这个动作是否：
1. 服务当前 Objective？
2. 或解决当前 Mission 的明确 gap？
3. 或解除当前 blocker？
```

如果都不是：

```text
记录
但不主动扩展
```

这样就防止 Agent 越做越散。

---

### 7. Mission 会在什么时候更新

不是每次聊天都改。

主要在这些情况下：

```text
Sponsor 改目标
↓
Scope 改变

Cycle Review
↓
Current Objective 更新

发现原目标不可行
↓
提出 Mission adjustment

一个阶段完成
↓
切换下一个 Objective
```

例如：

```text
Cycle 1
Objective:
找到 revenue 数据

Cycle 2
Objective:
确认 revenue 口径和 JOIN

Cycle 3
Objective:
形成 revenue silver
```

North Star 可能一直不变。

---

### 8. 新会话启动时

这是 Module 2 很重要的一点。

不能重新问：

> 我们现在要做什么？

应该：

```text
加载 Role
↓
加载 Mission
↓
加载 Current Objective
↓
加载最近一次 Cycle Review
↓
继续
```

所以新会话里 Agent 应该知道：

```text
我是谁
项目目标是什么
现在做到哪
这一阶段要推进什么
```

至于：

```text
认识谁
有哪些表
有哪些 JOIN
```

那是 Module 5 Memory。

---

### Module 2 最终只负责

```text
Who am I?
↓
Why am I working?
↓
What is the current mission?
↓
What is in / out of scope?
↓
What should I focus on now?
```

它不负责：

- 怎么找到表 → Module 3
- Bronze/Silver 怎么推进 → Module 4
- 人和表怎么长期记住 → Module 5
- 等人后怎么恢复 → Module 6
- 能不能执行某动作 → Module 7
- 多久必须停下来汇报 → Module 1

你刚才补的也可以正式记成 Module 1 的关系：

> **Cycle 控制多久需要整体校准；中间具体关键动作仍由 Hook + Approval 保证安全。**

不要固定死 North Star。**Role 固定，North Star 用一个 Mission Setup Skill 和发起人一步步设定。**

建议这样：

```text
首次启动 Mission
↓
Mission Setup Skill
↓

↓
Agent 提炼 North Star
↓
发起人确认
↓
写入 Mission State
↓
```

问题不用很多，核心就这些：

```text
1. 你最终想解决什么业务问题？
2. 谁会使用结果？
3. 什么结果算“有用/成功”？
4. 当前最想先解决哪一块？
5. 明确有哪些东西暂时不要碰？
```

例如用户说：

> 我想把销售数据整理好，最后管理层能看客户利润。

Agent 不直接照抄，而是提炼：

```text
North Star:
建立一套可信、可持续维护的客户利润数据基础，
让 Finance 和 Sales 能统一分析客户级收入、成本和利润。
```

然后确认一次。

### 后续修改规则

North Star 应该是**低频修改**的：

```text
Current Objective
可以每个 Cycle 改

Scope
可以阶段性改

North Star
只有业务目标明显变化时才改
```

所以 Module 2 里面最好有一个独立能力：

**Mission Setup / Mission Refinement Skill**

它负责：

```text
创建 Mission
→ 澄清目标
→ 提炼 North Star
→ 定义 Scope
→ 定义初始 Objective
→ 请求确认
```

这样比你手工预先写死一个 North Star 更通用，也更像真正的长期 Agent。

## Module 3. Discovery

这个模块解决：

> **当 Hermes 不知道下一步该找哪张表、找谁、缺什么信息时，怎么主动探索，而不是等用户喂答案。**

它是自驱力真正落地的地方。

### 总体流程

```text
Current Objective
↓
识别当前 Gap
↓
判断 Gap 类型
├─ 缺表
├─ 缺联系人
├─ 缺字段含义
├─ 缺 JOIN 关系
└─ 缺业务流程信息
↓
从已知世界开始探索
↓
找到候选 人 / 表 / 系统 / 关系
↓
验证相关性
↓
登记到 Memory
↓
Gap 是否解决？
├─ 是 → 返回 Data Steward Loop
└─ 否 → 继续下一跳探索
```

---

### 1. Discovery 从 Gap 开始，不是随便扫

不能设计成：

```text
看到数据库
→ 扫全部表
→ 全接入
```

应该是：

```text
North Star:
客户利润

Current Objective:
搞清 revenue

Known:
orders

Gap:
不知道 discount 在哪里
```

所以 Hermes 才开始探索：

```text
orders.discount?
↓
字段没有
↓
问 orders owner
↓
得知 promotion_service
↓
发现 discount_events
```

每次探索都要能回答：

> 我为什么在找这个？

---

### 2. 最开始什么都不知道时

这是 Discovery Skill 最关键的特殊情况。

```text
Mission 已建立
但：
Known People = sponsor
Known Assets = 0
```

这时候不要让 Hermes 自己乱搜。

第一跳应该找 Sponsor：

```text
“为了开始这个目标，
哪套系统/哪张表最接近这个业务问题？
谁最了解它？”
```

最好一次问两个方向：

```text
Seed Person
+
Seed Asset/System
```

有其中一个就能开始扩展。

例如：

```text
Sponsor
↓
Bob 负责销售系统
↓
Bob
↓
sales.orders
↓
orders 关联 customer
↓
CRM owner = Alice
```

Discovery 本质上是在建立一张：

```text
People ↔ Systems ↔ Tables ↔ Business Concepts
```

网络。

---

### 3. Discovery 有几种固定模式

V1 可以只做 5 类：

**A. Person Discovery**

```text
这个问题谁最懂？
谁是 owner？
谁有确认权？
```

**B. Asset Discovery**

```text
这个业务信息存在哪？
哪张表是 authoritative source？
有没有其他相关表？
```

**C. Semantic Discovery**

```text
这个字段是什么意思？
这个指标怎么算？
这个状态值代表什么？
```

**D. Relationship Discovery**

```text
这两张表怎么 JOIN？
哪个 key 才可靠？
有没有历史映射？
```

**E. Process Discovery**

```text
这个数据是怎么产生的？
退款什么时候进入系统？
哪个系统先写、哪个系统后同步？
```

这五类基本覆盖企业数据探索。

---

### 4. 探索不能无限向外长

需要一个 stopping rule。

每发现新东西，都判断：

```text
Does this directly help:
- current Objective
- unresolved Gap
- required lineage
- validation of an important assumption
```

如果都不是：

```text
记录为 related lead
但不继续追
```

比如发现：

```text
orders
↓
employee_id
↓
HR employee table
```

当前目标是客户利润。

那就：

```text
记录可能存在 employee_id 关系
STOP
```

不要开始研究 HR。

---

### 5. 每次探索结果都要分可信度

不能“别人随口说一句”就成为事实。

至少区分：

```text
Lead
听说可能存在

Candidate
已经找到具体对象

Verified
技术上验证存在

Confirmed
业务负责人确认含义
```

例如：

```text
Bob:
“退款应该在 finance_refund 里。”

→ Lead

数据库确实找到 finance.refunds
→ Verified Asset

Finance Owner:
“这是正式退款事实表。”
→ Confirmed
```

这个状态后面会进入 Module 5。

---

### 6. Discovery 什么时候结束并返回主 Loop

不是“把整个公司搞懂”。

而是：

```text
当前 Gap 已有足够信息，可以继续执行
↓
停止探索
↓
回 Module 4
```

例如：

```text
Gap:
不知道退款数据在哪

Discovery:
找到 finance.refunds
确认 owner
确认主键
确认基本含义

Enough
↓
回 Data Steward Loop
↓
准备接入 Bronze
```

---

### 7. Discovery 遇到人没回复怎么办

它只负责：

```text
发现需要找 Alice
↓
发出问题
↓
登记 pending
```

之后等待、切换其他任务、恢复，由：

**Module 6 Resume / Coordination**

负责。

Discovery 不自己管理长期等待。

---

### Module 3 最核心的 Skill

可以概括成一个：

> **Gap-Driven Discovery Skill**

逻辑就是：

```text
What am I trying to achieve?
↓
What do I not know?
↓
Who or what could resolve it?
↓
What is the cheapest credible next step?
↓
Explore one hop
↓
Evaluate again
```

重点是 **one hop at a time**。

不要一次规划：

> 我要把整个数据架构全部探索完成。

而是：

```text
缺 discount
→ 先找 orders owner
→ 得到新线索
→ 再决定下一步
```

这样更像真实 Data Steward，也更安全。

### Module 3 边界

它负责：

- 主动发现人
- 主动发现表/系统
- 主动问业务语义
- 找 JOIN/流程线索
- 判断是否值得继续探索

它不负责：

- 真正接入、清洗、做 Silver → Module 4
- 长期记忆 → Module 5
- 等人和任务恢复 → Module 6
- 权限/审批 → Module 7

一句话：

> **Module 2 给目标，Module 3 把未知变成可行动的信息。**

<a id="m028"></a>

## M028 · 助手

不是它“自己知道”，你要给它一个**明确的触发规则**。

最合适的是两层。

### 1. 在主循环里定义什么时候进入 Discovery

比如写进 Data Steward 的核心指令：

```text
When the current objective cannot be advanced because required
people, datasets, semantics, relationships, or business process
information are unknown, invoke the Discovery skill.
```

也就是 Agent 每一步先判断：

```text
Current Objective
↓
能直接继续执行吗？
├─ 能 → 正常执行
└─ 不能
    ↓
    缺什么？
    ├─ 人
    ├─ 表
    ├─ 语义
    ├─ JOIN
    └─ 业务流程
        ↓
        invoke Discovery
```

### 2. Discovery Skill 自己的描述要写得足够明确

例如 `SKILL.md`：

```text
# Discovery Skill

Use this skill when progress is blocked by missing knowledge about:
- which dataset or system contains required information
- who owns or understands a dataset
- field or metric semantics
- relationships between datasets
- how a business process generates data

Do not use this skill merely to explore unrelated datasets.
Discovery must start from a concrete unresolved gap.
```

Hermes 在选 skill 时看到这个描述，就会匹配。

---

但我建议再加一个更硬的状态判断。

比如维护：

```text
current_gap:
  type: asset_unknown
  question: "Where is refund data stored?"
  blocks_objective: true
```

只要：

```text
blocks_objective = true
AND gap.type ∈ {
  person_unknown,
  asset_unknown,
  semantic_unknown,
  relationship_unknown,
  process_unknown
}
```

就进入 Discovery。

这样就不是完全依赖 LLM 临场发挥。

---

所以最终是：

```text
Mission / Objective
↓
Agent 尝试推进
↓
Gap Detector
↓
有 Discovery-type Gap？
├─ No → 正常工作
└─ Yes → Discovery Skill
```

我建议 **V1 用“LLM 判断 + 明确规则”**，不用一开始写成完全硬编码 router。

因为很多情况不是简单字段能判断，比如：

> “这个 revenue 看起来不对，我是不是还缺退款？”

这种就是模型先识别出一个 `possible data gap`，然后调用 Discovery。

所以 Module 3 前面其实应该多一个很轻的东西：

**Gap Detection → Discovery Routing**

它不是独立一级模块，而是 Discovery 的入口。

```text
- scope
- sponsor

current
- objective
- phase
- active_task
- next_action

gaps

- unknown person
- unknown semantic
- unknown relationship
- unknown process

known
- relevant assets
- relevant people

waiting
- pending approval
- pending reply

cycle
- current_cycle
- remaining budget
- last review
```

Agent 每次开始行动前不是直接思考，而是：

```text
↓

↓
有没有 blocker / gap？
├─ 没有 → 继续当前工作
└─ 有
    ↓

    ↓
    如果是未知人/表/语义/JOIN/流程

```

例如：

```text

客户利润可信分析

完成 revenue 数据理解

Active Task:
确认 orders 的收入字段

Gap:
discount 是否已经包含在 order_total
type = semantic_unknown
blocks_objective = true
```

Hermes 一启动就知道：

> 我不是随便探索。我正在搞 revenue，现在被 discount 定义卡住了。

于是调用 Discovery Skill，去找合适的人确认。

Discovery 完以后也要写回 State：

```text
Gap:
semantic_unknown
→ resolved

Finding:
order_total includes discount

Confirmed by:
Sales Owner Bob

Next Action:
profile order_total and prepare silver rule
```

然后 Module 4 接着干。

所以你现在可以把核心运行逻辑理解成：

```text
Role + Mission
        ↓
   Project State
        ↓
   “我现在在哪？”
        ↓
   “下一步能不能做？”
   ↓              ↓
能做            有未知
↓                ↓
Module 4      Module 3
```

这其实非常关键。

**North Star 给 Agent 驱动力，State 给 Agent 方向感，Discovery 给 Agent 在不知道时继续前进的能力。**

## Module 4. Data Steward Loop

这个模块解决：

> **已经知道要处理哪张表、找谁、业务目标是什么之后，Hermes 怎么把数据真正往可用状态推进。**

它是你的 Agent 最核心的专业工作流。

### 总体流程

```text
读取当前 State
↓
确定 Active Asset / Active Task
↓
判断当前资产处于什么阶段
↓
执行这一阶段该做的动作
↓
遇到未知信息
→ Module 3 Discovery

遇到高风险动作
→ Module 7 Approval / Guardrail

遇到等待
→ Module 6 Resume / Coordination

完成阶段动作
↓
更新 State
↓
继续下一阶段
```

---

### 1. 不要让 Hermes 默认“发现表就做 Silver”

一张表先进入资产生命周期：

```text
Discovered
↓
Relevant
↓
Approved for access
↓
Bronze
↓
Profiled / Understood
↓
Silver Candidate
↓
Silver Verified
↓
Gold Candidate
↓
Published
```

不是每张表都必须走到 Gold。

有的可能：

```text
Discovered
→ 判断没用
→ Archived / Ignore
```

有的可能：

```text
Bronze
→ 只作为原始证据保留
```

---

### 2. Discovered → Relevant

Hermes先判断：

> 这张表为什么和当前 Objective 有关？

例如：

```text
Objective:
搞清收入

发现：
sales.orders

Reason:
包含订单金额、客户、日期
```

如果相关，就进入下一步。

如果只是边缘信息：

```text
记录
但不继续投入
```

---

### 3. Relevant → Bronze

这里主要完成：

```text
确认 source
确认 owner
确认访问权限
确认基础 schema
获得接入批准
原样复制 / snapshot 到 Bronze
```

核心原则：

> Bronze 尽量保持原始状态，不在这里做复杂业务解释。

这一步涉及权限或生产访问时，由 Module 7 管。

---

### 4. Bronze → Understanding

这是你 Agent 很关键的一层。

不是 Bronze 后直接 transform，而是先理解：

```text
profile
↓
看字段
↓
看 null / unique / distribution
↓
识别 key
↓
识别时间字段
↓
识别异常值
↓
结合业务目标提出问题
```

然后形成：

```text
Known
Unknown
Suspected
Confirmed
```

例如：

```text
Known:
order_total 存在且非空

Unknown:
是否已扣除 discount

Suspected:
customer_id 可 JOIN crm.customers

Confirmed:
尚无
```

未知就交给 Module 3。

---

### 5. Understanding → Silver Candidate

只有“理解已经足够”才开始提出 Silver 规则。

例如：

```text
过滤测试订单
统一 currency
标准化 status
确认 revenue 字段
JOIN customer
处理退款
```

Hermes要明确：

```text
Input
Transformation
Reason
Evidence
Expected Output
```

而不是直接改数据。

---

### 6. Silver Candidate → Silver Verified

执行 transformation 后要验证：

```text
行数变化是否合理
金额是否守恒
JOIN 是否大量丢失
null 是否异常
重复是否增加
业务规则是否满足
```

然后根据风险决定是否找人复核。

例如：

```text
原始 revenue = 10.2m
Silver revenue = 9.7m

差异原因：
测试订单 -0.3m
取消订单 -0.2m
```

这就可以给业务负责人看。

这里的“首次规则确认、重要 JOIN、重大差异”仍然可能触发 Module 7。

---

### 7. Silver 不一定马上 Gold

Gold 应该由业务消费需求驱动。

例如：

```text
Silver:
clean_orders
clean_refunds
clean_customer

如果当前只是把底层整理清楚
→ 可以停在这里

如果 Mission 需要：
客户利润看板
→ 再做 Gold
```

所以：

> Bronze / Silver / Gold 是资产成熟度，不是任务完成度。

---

### 8. 原表整改建议放低优先级

你前面已经定了。

在 Module 4 里只作为 side finding：

```text
发现 source 问题
↓
记录 remediation suggestion
↓
如果不阻塞当前目标
→ 不展开
```

例如：

```text
orders.status 存在 7 个非标准值

当前处理：
Silver 做 mapping

附带建议：
上游未来改成 enum

Priority:
low
```

只有严重影响正确性时才升级。

---

### 9. 什么时候返回 Discovery

Module 4 自己不负责“猜”。

只要遇到：

```text
不知道 owner
不知道字段含义
不知道 authoritative source
不知道 JOIN
不知道业务规则
不知道数据生成流程
```

就：

```text
产生 Gap
↓
写 State
↓
调用 Module 3
```

Discovery 解决后回来继续。

---

### 10. 什么时候算当前 Task 完成

不是必须到 Gold。

例如一个 Task 可以定义：

```text
Task:
验证 orders 是否足以支撑 revenue

Done Criteria:
- orders 已接入 Bronze
- revenue 字段已确认
- discount 口径已确认
- customer join 已验证
- 主要质量问题已记录
```

满足就结束这个 Task。

然后 State 决定下一步。

---

### Module 4 的核心循环

可以压缩成：

```text
Locate current asset/task
↓
Understand current stage
↓
Do the next valid stewardship action
↓
Validate result
↓
Record evidence/state
↓
Advance maturity if justified
```

它的核心原则不是：

> 尽快把数据做成 Gold。

而是：

> **在证据和确认足够的情况下，让数据一步一步变得更可信。**

边界也很清楚：

- 不知道去哪找 → Module 3
- 等人/等审批 → Module 6
- 高风险动作 → Module 7
- 长期记忆 → Module 5
- 到 Cycle 时间必须停 → Module 1

## Module 5. Organizational Memory

这个模块解决：

> **Hermes 怎么长期记住“这个组织是怎么运作的、数据在哪、谁负责什么、哪些结论已经确认”，而不是每次新会话重新问。**

你已经有对应 state/tool，所以这里重点不是“怎么存”，而是**存什么、什么时候写、什么时候读、什么不能直接当事实**。

### 总体流程

```text
工作开始 / 恢复
↓
读取相关 Memory
↓
结合 Project State + Asset State
↓
执行任务
↓
产生新事实 / 新线索 / 新确认
↓
按可信度写回
↓
后续任务复用
```

### 1. Memory 建议分 5 类

```text
People
Assets
Semantics
Relationships
Decisions
```

**People**
```text
Alice
- role: Finance Manager
- knows: refund policy
- authority: can confirm refund definition
```

**Assets**
```text
sales.orders
- owner: Bob
- source_system: ERP
- purpose: order facts
```

**Semantics**
```text
order_total
- meaning: amount after discount
- status: confirmed
- confirmed_by: Bob
```

**Relationships**
```text
sales.orders.customer_id
→ crm.customers.customer_id
status: confirmed
```

**Decisions**
```text
2026-09-14:
Revenue Silver excludes test orders.
Approved by Alice.
```

---

### 2. Memory 和 State 要严格区分

你现在已经有：

```text
Project State
Asset State
```

这两个回答：

> **现在做到哪了？**

Memory 回答：

> **我们已经知道什么？**

例如：

```text
Asset State:
orders 当前 = profiled
next_action = build silver candidate
```

而 Memory：

```text
orders.order_total = discount 后金额
confirmed_by = Bob
```

任务做完以后 Asset State 可能变化甚至关闭，但这个业务知识仍然应该保留。

---

### 3. 什么时候写 Memory

不要等 Cycle 结束才统一写。

应该事件发生时就沉淀。

```text
认识新联系人
→ 写 People

验证新表存在
→ 写 Assets

人确认字段定义
→ 写 Semantics

JOIN 被验证
→ 写 Relationships

审批形成正式决定
→ 写 Decisions
```

Cycle Report 主要是汇报，不是主要记忆机制。

---

### 4. 一定要区分“线索”和“事实”

这个很关键。

不能：

```text
Bob: “我记得退款可能在 finance 表。”
↓
Memory:
refund table = finance.refunds
```

应该：

```text
claim:
refund data may be in finance
source: Bob
confidence: lead
```

后来：

```text
实际发现 finance.refunds
→ verified

Finance Owner 确认它是正式退款表
→ confirmed
```

建议至少有：

```text
lead
candidate
verified
confirmed
deprecated
```

否则长期 Agent 跑久以后会把历史猜测当真。

---

### 5. Memory 还要处理冲突

比如：

```text
Bob:
order_total 含税

Alice:
order_total 不含税
```

不能覆盖旧记录。

应该：

```text
Semantic Conflict:
order_total tax treatment

Claim A: includes tax
source = Bob

Claim B: excludes tax
source = Alice

status = unresolved
```

然后生成 Gap：

```text
semantic_conflict
```

再触发 Module 3 去找真正有确认权的人。

---

### 6. 新会话怎么用 Memory

启动时不要把全部 Memory 塞给 Hermes。

应该按当前任务检索：

```text
Current Objective:
refund 数据

↓ retrieve

相关人
相关表
相关业务定义
相关 JOIN
历史决定
```

这样不会因为组织知识越来越多，把上下文撑爆。

所以是：

```text
Persistent Memory
↓
contextual retrieval
↓
Working Context
```

不是全量加载。

---

### 7. Memory 需要“过期”概念

企业知识会变。

例如：

```text
Bob was owner of sales.orders
```

半年后可能不是了。

所以最好有：

```text
valid_from
last_verified
source
status
```

对于容易变化的信息：

```text
owner
schema
权限
业务流程
```

需要允许重新验证。

而像：

```text
历史审批决定
某次 Cycle 结论
```

则保留历史，不覆盖。

---

### 8. 和 Module 3 / 4 的关系

Discovery 先查 Memory：

```text
Gap:
谁负责 refund？

↓
Memory 已知 Alice 是 refund owner
→ 不需要重新问 Sponsor
```

Module 4 也一样：

```text
准备理解 order_total
↓
Memory 已经有 confirmed semantic
→ 直接复用
```

所以 Memory 会让 Agent 越工作越“懂公司”。

---

### Module 5 的核心边界

它负责：

- 组织知识长期沉淀
- 可信度/来源
- 冲突记录
- 历史决定
- 按当前任务取回相关知识

它不负责：

- 当前任务做到哪 → State
- 怎么继续探索 → Module 3
- 怎么处理表 → Module 4
- 等人后怎么恢复 → Module 6

一句话：

> **State 让 Hermes 知道“我现在在哪”，Memory 让 Hermes 知道“这个组织我已经学会了什么”。**

- **Role Knowledge**：比如 Finance Manager、Data Engineer、Sales Ops 这类岗位通常负责什么、通常能确认哪些问题。

例如：

```text
- sales.discount_rules

- discount business rules

usually_knows:
- sales workflow
- CRM / ERP handoff
```

```text

- sales process
- order operations
- discount rules
- CRM usage

likely_authority:
- sales process semantics
- sales operational definitions
```

这样 Hermes 遇到未知问题时可以推理：

```text

↓
没有
↓
查组织角色知识
↓
Sales Ops 很可能知道
↓
找到具体 Sales Ops 人员
↓
询问
```

但要注意：**“岗位通常负责什么”只能是探索线索，不能当成确认权。**

所以建议 SQL 里至少区分：

```text
people
roles
person_roles
role_responsibilities
asset_ownership
semantic_authority
person_expertise
```

其中：

- `role_responsibilities` = 一般规律
- `person_expertise` = 对这个人的实际观察
- `semantic_authority / asset_ownership` = 已确认事实

这会直接增强 Module 3 Discovery，因为 Agent 不只是“认识谁”，而是逐渐形成一张 **组织能力地图**。

## Module 6. Resume / Coordination

这个模块解决：

> **Hermes 同时推进多个事项时，某个任务被人、审批或外部条件卡住，怎么不阻塞整个 Agent；条件满足后又怎么准确恢复。**

### 总体流程

```text
当前 Task
↓
能继续？
├─ 能 → 继续执行
└─ 不能
    ↓
    标记 waiting / blocked
    ↓
    记录：
    - 等什么
    - 等谁
    - 为什么
    - 恢复条件
    - 恢复后 next_action
    ↓
    切换到其他可执行 Task
```

外部事件到来：

```text
收到回复 / 审批通过 / 条件满足
↓
找到对应 Task
↓
重新读取最新 State
↓
检查原假设是否仍成立
↓
恢复 next_action
```

---

### 1. Task 需要明确状态

最少：

```text
ready
running
waiting_human
waiting_approval
waiting_external
blocked
completed
cancelled
```

例如：

```text
Task:
确认 refund_status 业务含义

status:
waiting_human

waiting_for:
Alice

resume_condition:
Alice confirms the meaning

next_action:
update semantic knowledge and continue profiling refunds
```

这样不是“记得以后回来”，而是有明确恢复点。

---

### 2. 等待时不能冻结整个 Hermes

例如同时有：

```text
Task A
确认 refunds 定义
→ 等 Alice

Task B
profile orders
→ 可执行

Task C
验证 customer JOIN
→ 可执行
```

应该：

```text
A → waiting
↓
Scheduler / Agent 选 B
↓
B 做完再选 C
```

这也是你长期 Agent 和普通单会话 Agent 很大的区别。

---

### 3. Resume 不能直接接着旧上下文跑

这是重点。

两天后 Alice 回复了，不能：

```text
恢复旧 conversation
→ 从旧 reasoning 继续
```

而应该：

```text
收到 Alice 回复
↓
定位 Task A
↓
读取最新 Project State
↓
读取最新 Asset State
↓
读取相关 Knowledge
↓
应用 Alice 的新信息
↓
重新判断 next_action
```

因为等待期间可能已经发生：

- 表结构变了
- 另一个人已经解决了
- Objective 改了
- 这个 Task 已经不重要了

所以 Resume 是 **state-based resume**，不是 conversation-based resume。

---

### 4. 如何知道该恢复哪个 Task

每个等待动作都要有 correlation。

例如：

```text
task_id = T-103
question_id = Q-27
person = Alice
asset = refunds
```

发邮件/消息时带上内部关联。

回复回来后：

```text
reply
↓
match question_id / task_id
↓
恢复 T-103
```

避免 Agent 收到一句：

> “Yes, that includes cancellations.”

却不知道是在回答哪个问题。

---

### 5. 长时间没人回复怎么办

Module 6 负责催办策略：

```text
waiting
↓
超过 reminder threshold
↓
提醒一次
↓
仍未回复
↓
找 alternate contact / escalate / defer
```

例如：

```text
Day 1:
问 Bob

Day 2:
提醒 Bob

Day 4:
仍无回复
→ 查是否有 backup owner

Day 5:
报告给 Sponsor：
此项仍 blocked
```

但不要无限催。

---

### 6. Coordination 不只是等待，还包括任务排序

Hermes 同时有很多 Task 时，要知道先做哪个。

V1 可以简单按：

```text
1. 当前 Objective 直接相关
2. 不依赖人的可执行任务
3. 能解除其他 blocker 的任务
4. 高价值 / 低成本任务
5. 低优先级改进
```

所以它不是纯 scheduler，而是：

> **维护一组可推进、等待、阻塞的工作，并持续选择最合理的下一项。**

---

### 7. 和 Cycle 的关系

Module 6 可以让 Agent连续工作，但 Module 1 仍然能强制停：

```text
还有 8 个 ready tasks
但 Cycle 到期
↓
停止开新 Task
↓
生成报告
```

报告里自然包含：

```text
Running
Waiting
Blocked
Completed
Recommended next
```

---

### Module 6 的核心边界

它负责：

- Task 状态
- waiting / blocked
- 多任务切换
- 回复关联
- resume
- reminder / escalation
- 下一任务选择

它不负责：

- 为什么做这个项目 → Module 2
- 不知道找谁/找什么 → Module 3
- 数据具体怎么处理 → Module 4
- 知识怎么沉淀 → Module 5
- 哪些动作能不能做 → Module 7

一句话：

> **Module 6 让 Hermes 从“单线程聊天 Agent”变成“可以长期推进多个真实工作事项的执行者”。**

```text
Project
└─ Task
   └─ Communication Thread
```

```text
Task T-103
确认 refund_status 口径

当前 Session
↓
发现需要找 Alice
↓
发邮件给 Alice
↓
邮件 thread 绑定 T-103
```

```text
↓
邮件回复到达
↓
通过 thread_id / task_id 找到 T-103
↓
启动新的 working session
↓
重新加载最新 State + Knowledge
↓
继续 T-103
```

所以原则是：

> **能保持同 Session 就保持，保证自然连续；但任务连续性必须靠 Task/State，而不能靠 Session。**

另外“拉了个人进来”也不意味着把所有人混成一个大对话。比如 Bob 和 Alice 分别回答不同问题，最好各自有 communication thread：

```text
T-103
├─ Thread A → Alice：退款口径
└─ Thread B → Bob：订单字段历史
```

Hermes 自己的 working session 可以同时协调这两个 thread。这样以后恢复不会乱。

不能假设“一封回复只对应一个 Task”。应该做成 **message → answer units → task routing**。

流程：

```text
收到 Bob 的回复
↓
先找候选范围
- 这个 communication thread 绑定哪些 open questions
- Bob 当前有哪些 pending questions
- 哪些 asset / topic 相关
↓
LLM 把回复拆成多个 answer units
↓
每个 answer unit 分别匹配 question_id
↓
question_id → task_id
↓
分别更新对应 Task
```

例如 Bob 回复：

> order_total 是折后金额。  
> customer_id 可以直接连 CRM。  
> refunds 不归我，应该找 Alice。

系统拆成：

```text
Answer 1
"order_total 是折后金额"
→ Q-21
→ Task T-101 semantic clarification

Answer 2
"customer_id 可以直接连 CRM"
→ Q-35
→ Task T-108 join validation

Answer 3
"refunds 应该找 Alice"
→ Q-42
→ Task T-115 refund discovery
```

然后分别更新：

```text
T-101 → resolved / next_action

T-108 → candidate evidence
可能还需要技术验证

T-115 → Bob 不负责
新增 Alice discovery lead
```

关键是 **Task 上面最好还有一层 Question / Request**：

```text
Task
└─ Question
   - question_id
   - asked_to
   - exact_question
   - topic
   - asset
   - status
```

因为真正适合和邮件回答对应的，通常不是整个 Task，而是一个具体问题。

Routing 可以用这些信号：

1. `thread_id`：最强候选范围
2. `question_id`：如果发信时能携带，最可靠
3. `person_id`
4. `asset / field / topic`
5. 原始 question 与 reply 的语义匹配
6. 当前哪些 question 仍是 open

再加置信度：

```text
high confidence
→ 自动 route

medium
→ route，但标记 needs_review

low / 一个回答可能对应多个问题
→ 不自动关闭 Task
→ 放入 unresolved inbox
```

而且 **一个 answer 可以更新多个 Task，一个 Task 也可以等多个人的 answer**。不要建成 1:1。

我会把 Module 6 的核心关系设计成：

```text
Task
↓
Question / Request
↓
Communication Thread
↓
Incoming Message
↓
Answer Unit
↓
Question
↓
Task update
```

这样以后邮件、Slack、Teams 都能用同一套 routing。

## Module 7. Governance / Guardrails

这个模块解决：

> **Hermes 可以做什么、做到什么程度、什么时候必须停下来找人。**

它不是“工作流程”，而是给前 6 个模块套安全边界。

### 总体流程

```text
Hermes 准备执行动作
↓
识别 action type / risk
↓
检查权限 + policy + scope
↓
是否允许直接执行？
├─ Yes → 执行
├─ Need approval → 暂停该 Task，发审批
└─ Forbidden → 拒绝执行并记录
↓
执行后记录 evidence / audit log
```

### 1. 先把动作分级

V1 可以简单分 4 档：

```text
L0 只读低风险
L1 可逆写操作
L2 高影响操作
L3 禁止/特殊授权
```

例如：

**L0**
- 看 schema
- 查 metadata
- 小范围 profile
- 查已有 knowledge
- 读 Bronze

默认可执行。

**L1**
- 创建 Bronze
- 更新内部 metadata
- 写 knowledge SQL
- 创建 task / issue

通常可执行，但仍受 scope 和权限限制。

**L2**
- 访问敏感生产数据
- 大范围 SQL
- 发布 Silver/Gold
- 改重要业务口径
- 修改权限
- 发代表组织立场的通知

需要审批或明确授权。

**L3**
- 修改生产源表
- 删除生产数据
- 绕过权限
- 未授权对外发送敏感数据

默认禁止。

---

### 2. SQL Guardrail

你已经有这块，继续作为核心。

流程：

```text
Hermes 生成 SQL
↓
AST / policy 检查
↓
检查：
- read/write
- table scope
- row limit
- timeout
- forbidden statement
- sensitive columns
- estimated impact
↓
allow / approval / deny
```

尤其 Module 4 Safe Profiling 会大量依赖这个。

比如：

```text
SELECT *
FROM orders;
```

Guardrail 应该拦住或改成安全版本。

---

### 3. Approval 和 Cycle 必须分开

你前面已经定得很对。

```text
Cycle checkpoint
= 整体方向要不要重新校准

Approval
= 这个具体动作现在能不能做
```

比如 Cycle 还有 2 天：

```text
Hermes 想发布 Gold
↓
仍然必须审批
```

不能因为 Trust Level 高就绕过关键审批。

---

### 4. Trust 可以影响“自动执行范围”，不能取消硬边界

例如：

```text
低 Trust
L1 也可能审批

高 Trust
L1 自动执行
```

但：

```text
生产 DELETE
敏感权限修改
Gold 正式发布
```

这种硬规则不应该因为 Trust Level 高就自动放开。

所以：

```text
Trust = soft autonomy
Guardrail = hard boundary
```

---

### 5. Human Authority 也要检查

不是“找个人确认”就算批准。

比如：

```text
Bob 说：
“你直接改这个利润口径吧。”
```

系统要查：

```text
Bob 是否有 semantic authority？
```

如果没有：

```text
可以作为 evidence
不能作为正式 approval
```

这正好用到 Module 5 的：

```text
asset ownership
semantic authority
role
person capability
```

---

### 6. Data Access Guardrail

至少考虑：

```text
谁允许 Hermes 看什么
哪些列敏感
是否能看原始值
是否只能 aggregate
是否能跨域 JOIN
```

例如：

```text
customer_email
personal_id
salary
```

可能允许：

```text
COUNT / aggregate
```

但不允许直接拉全量原始值。

---

### 7. Communication Guardrail

Hermes 会主动联系很多人，所以邮件本身也要管。

至少：

```text
允许联系谁
每人同时 pending 问题上限
哪些信息不能发给这个人
是否允许跨部门披露
是否代表 Sponsor 做承诺
```

例如发现：

```text
Bob 不应该看到 Finance 的成本明细
```

即使 Hermes 自己有权限，也不能把这部分直接带进邮件。

---

### 8. Knowledge Write Guardrail

写 SQL Knowledge Base 也不能完全自由。

比如：

```text
Bob 说：
“我觉得 order_total 应该是折后金额。”
```

不能直接：

```text
status = confirmed
```

而应该根据 authority：

```text
lead / candidate / verified / confirmed
```

Module 7 可以约束：

> 只有满足特定 evidence + authority 条件，才能升级到 confirmed。

这样长期知识库不会越来越脏。

---

### 9. Audit

所有重要动作都应该留下：

```text
who/what initiated
action
target
reason
policy decision
approval
execution result
timestamp
```

尤其：

```text
为什么读这张表
为什么联系这个人
谁批准了这个 transformation
为什么这个 semantic 被标记 confirmed
```

以后出问题可以回溯。

---

## Module 7 和其他模块的关系

```text
Module 2
想做什么

Module 3
想找什么

Module 4
想执行什么数据动作

Module 5
想写入什么组织知识

Module 6
想联系谁 / 恢复什么任务

```

所以它相当于整个 Agent 的横切层。

> **前 6 个模块负责让 Hermes 越来越能干，Module 7 负责保证它越能干以后也不会越权。**

# Hermes Data Steward Agent：7 个核心模块逻辑

## 总体定位

Hermes 不是数据分析 Agent，而是一个长期运行的 **Data Steward Agent**。

它负责围绕业务目标持续推进：

**人 → 数据源 → 表 → 语义 → JOIN → 数据质量 → Bronze / Silver / Gold → 审批 → 组织知识沉淀。**

它不回答诸如“为什么销售下降”“哪个客户值得营销”这类分析问题。即使只是回答“有哪些数据可以支持这个问题”，也必须先判断请求者是否有权限知道相关数据资产存在。

整体关系：

```text
Role / Mission
      ↓
Project State
      ↓
当前 Objective / Gap
      ↓
Discovery ←→ Data Steward Loop
      ↓
Organizational Knowledge
      ↓
Resume / Coordination

整个过程外围：
Cycle / Trust
Governance / Guardrails
```

---

# Module 1 — Cycle / Trust

## 解决的问题

Hermes 可以持续自主工作，但不能无限运行。

关键动作已有 Hook + Approval 保证执行安全；Cycle 解决的是另一个问题：

> Agent 整体方向运行多久以后，必须停下来向人汇报和重新校准？

因此：

```text
Approval
= 某个具体动作现在能不能做

Cycle
= 整体工作方向是不是仍然正确
```

## 基本流程

```text
项目启动
↓
设置当前 Trust Level
↓
得到 Cycle Budget
- 时间
- token
↓
Hermes 正常推进
↓
中间关键动作继续经过 Hook / Approval
↓
时间或 token 达到阈值
↓
停止开启新的工作分支
↓
完成当前原子操作
↓
生成 Cycle Report
↓
Sponsor / 发起人 review
↓
调整：
- 下一阶段目标
- Scope
- Trust Level
↓
开始下一 Cycle
```

## Trust 是逐步建立的

初始频繁汇报：

```text
0.5 天
→ 1 天
→ 2–3 天
→ 5–7 天
```

不是单纯按时间升级，而是看：

```text
方向是否稳定
报告是否准确
是否频繁返工
是否出现重大遗漏
```

如果跑偏，可以重新缩短 Cycle。

## Cycle Report

固定短报告即可：

| 内容 | 说明 |
|---|---|
| Goal | 本轮原目标 |
| Completed | 已完成 |
| New Findings | 新发现的人、表、关系 |
| Pending | 尚未解决 |
| Blocked | 卡在哪里、等谁 |
| Risks | 风险和不确定性 |
| Recommended Next | Agent 建议下一步 |

人主要决定三件事：

```text
下一轮重点是什么
Scope 要不要变
自主周期拉长还是缩短
```

---

# Module 2 — Role / Mission

## 解决的问题

让 Hermes 知道：

```text
我是谁？
为什么工作？
当前项目最终要解决什么？
现在最应该推进什么？
```

## Role

Role 长期稳定，写在类似 `IDENTITY.md` 中。

定义：

```text
Hermes 是 Data Steward Agent

负责：
- 理解业务数据需求
- 主动发现数据和负责人
- 推进数据治理
- 不猜业务语义
- 维护 provenance
- 在授权范围内自主工作
```

Role 不包含具体业务 North Star。

## Mission

每个项目独立存在。

包含：

```text
North Star
Sponsor
Scope
Current Objective
Known Constraints
Current Status
```

例如：

```text
North Star:
建立可信的客户利润数据基础。

Current Objective:
先把 Revenue 数据源和口径搞清楚。
```

## North Star 不预先写死

通过 **Mission Setup / Refinement Skill** 和发起人一起建立：

```text
首次启动
↓
询问发起人：
- 最终解决什么业务问题？
- 谁使用结果？
- 什么算成功？
- 当前先做哪一部分？
- 哪些内容暂时不要碰？
↓
Hermes 提炼 North Star
↓
发起人确认
↓
写入 Mission
```

North Star 低频修改。

Current Objective 可以每个 Cycle 更新。

## Mission 提供自驱力

每次开启新分支前判断：

```text
这个动作是否：
- 服务 Current Objective？
- 解决 Mission Gap？
- 解除 Blocker？
```

都不是：

```text
可以记录
但不主动扩展
```

# Module 3 — Discovery

## 解决的问题

当 Hermes 不知道下一步找哪张表、找谁、字段是什么意思、JOIN 怎么做时，能够主动继续，而不是停下来等待用户喂答案。

## 入口：Gap Detection

Hermes 先读取 State，知道自己当前在哪。

```text
Current Objective
↓
Active Task
↓
当前能继续吗？
├─ Yes → 正常执行
└─ No
    ↓
    缺什么？
```

Discovery 类型 Gap：

```text
person_unknown
asset_unknown
semantic_unknown
relationship_unknown
process_unknown
```

出现这些 Gap，就调用 Discovery Skill。

## 最开始什么都不知道

如果：

```text
Known People = Sponsor
Known Assets = 0
```

第一跳找发起人：

```text
这个目标最相关的数据在哪？
谁最了解这部分？
```

目标是得到至少一个：

```text
Seed Person
或者
Seed Asset / System
```

然后逐步扩展：

```text
Sponsor
↓
Bob
↓
sales.orders
↓
customer_id
↓
CRM
↓
Alice
```

## 五类探索

```text
Person Discovery
Asset Discovery
Semantic Discovery
Relationship Discovery
Process Discovery
```

## Gap-driven，不允许随便扫

不是：

```text
看到新表 → 全部探索
```

而是：

```text
当前 Gap
↓
哪个最便宜、最可信的下一步能解决它？
↓
探索一跳
↓
重新判断
```

典型 one-hop：

```text
不知道 discount
↓
先问 orders owner
↓
得到新线索
↓
再决定下一步
```

## 停止条件

Discovery 不是“搞懂整个公司”。

当当前 Gap 已经足够解决：

```text
停止探索
↓
回到 Data Steward Loop
```

# Module 4 — Data Steward Loop

## 解决的问题

当 Hermes 已经知道当前要处理什么资产以后，如何真正把数据从未知状态逐步变成可信资产。

## 每个表都有 Asset State

除了 Project State，每个资产还维护自己的状态：

```text
source / owner
current_stage
known semantics
unknowns
quality issues
candidate joins
confirmed joins
blockers
next_action
```

## 生命周期

```text
Discovered
↓
Relevant
↓
Approved
↓
Bronze
↓
Safe Profiling
↓
Structural Understanding
↓
Business Understanding
↓
Silver Candidate
↓
Silver Verified
↓
Gold / Published（如需要）
```

不是每个表都必须走到 Gold。

## Bronze 后不是直接 Transform

最重要的一步是：

### Safe Profiling

先理解数据。

包括：

```text
Schema
- column
- type
- nullable

Volume
- row count

Distribution
- null rate
- distinct
- min / max
- median
- quantiles
- top values

Quality
- duplicates
- type anomaly
- range anomaly
- impossible values
- category anomaly
- timestamp gap

Keys
- candidate PK
- uniqueness
- candidate FK
```

例如：

```text
order_amount
type = decimal
median = 268
p95 = 4820
min = -82000

发现负数
↓
退款？冲销？错误？
↓
semantic_unknown
↓
Module 3 Discovery
```

## Profiling 本身也要安全

Module 4 决定安全策略：

```text
metadata 优先
↓
轻量 aggregate
↓
sampling
↓
确实需要才全表扫描
```

避免：

```text
SELECT * FROM huge_table
```

真正执行限制由 Module 7 Harness 强制。

## Silver

理解充分后才能提出 transformation：

```text
Input
Transformation
Reason
Evidence
Expected Output
```

例如：

```text
过滤测试订单
统一 currency
标准化 status
确认 revenue
JOIN customer
```

然后验证：

```text
行数变化
金额守恒
JOIN loss
null
duplicates
business rules
```

## Source remediation

源表整改建议保留，但默认低优先级：

```text
发现源系统问题
↓
记录建议
↓
不阻塞当前 Mission → 不展开
```

除非直接影响结果正确性。

# Module 5 — Organizational Knowledge

## 解决的问题

Hermes 越工作，应该越了解这个组织。

不是单纯依赖聊天 Memory，而是形成可查询、可审计的组织知识。

## 四层信息体系

### 1. SQL / Knowledge Store

正式事实和可结构化经验的 Source of Truth。

存：

```text
People
Roles
Assets
Ownership
Semantic Authority
Field Semantics
JOIN Relationships
Role Responsibilities
Person Capabilities
Historical Decisions
Evidence / Provenance
```

例如：

```text
Bob = Sales Ops
Bob owns sales.orders
order_total = 折后金额
orders.customer_id → customers.id
Bob 擅长处理销售库历史问题
```

其中“Bob 熟悉销售库历史问题”也适合结构化成：

```text
person_capabilities
- person_id
- capability
- confidence
- evidence_count
- last_verified
```

这样 Discovery 可以直接利用。

### 2. Person Memory

只存难结构化、但影响沟通方式的经验：

```text
Bob 喜欢简短问题
Bob 更适合给具体表例子
Alice 更喜欢一次看到完整背景
```

只有准备和这个人沟通时才加载。

### 3. Project Summary Memory

用来快速恢复整体上下文：

```text
当前已接入 5 张核心表，
正在处理 orders / refunds，
customer JOIN 已确认，
cost 仍等待 Finance。
```

它不是 Source of Truth，只是摘要缓存。

### 4. Session Context

当前一次会话里的临时内容。

Session 结束可以丢弃或压缩。

## State 与 Knowledge 区分

```text
State
= 我现在做到哪

SQL Knowledge
= 这个组织我已经确认了什么

Memory
= 快速恢复和沟通辅助

Session
= 当前临时上下文
```

## 更新机制

不是定时全量刷新，而是：

```text
事件驱动 + Session 收尾 + Cycle reconcile
```

结构化事实发生变化：

```text
立即写 SQL / State Tool
```

Session 结束或 Cycle checkpoint：

```text
重写 Project Summary Memory
```

周期性：

```text
Memory Summary
vs
SQL + State
↓
不一致
→ SQL / State 为准
→ 重写 Memory
```

# Module 6 — Resume / Coordination

## 解决的问题

Hermes 在真实组织里同时会推进很多事情。

某个问题等人回复时，不能整个 Agent 卡住。

## Task 状态

至少：

```text
ready
running
waiting_human
waiting_approval
waiting_external
blocked
completed
cancelled
```

等待时必须记录：

```text
等谁
等什么
为什么
恢复条件
恢复后的 next_action
```

然后继续其他 ready task。

## Resume 必须基于 State

不是：

```text
两天后恢复旧 conversation
```

而是：

```text
收到回复
↓
找到对应 Task
↓
加载最新 Project State
↓
加载 Asset State
↓
加载相关 Knowledge
↓
检查旧假设是否仍成立
↓
继续 next_action
```

所以 Task continuity 不能依赖 Session。

## Session 从“人级”降为“Task Session”

以前：

```text
Bob
↓
一个 Session
```

现在：

```text
Bob
↓
Router
├─ Task Session A
├─ Task Session B
└─ Task Session C
```

用户前台仍然感觉是在和同一个 Hermes 沟通，但后台已经拆成多个 Task Session。

## Email Routing

优先使用邮件原生关系：

```text
Hermes 发邮件
↓
绑定 question_id / task_id / thread_id
↓
提醒对方直接 Re: 回复
↓
通过 In-Reply-To / References / thread_id
直接 route 回原 Task
```

Routing 优先级：

```text
1. Email thread / In-Reply-To
2. question_id / task_id
3. person + open questions
4. LLM semantic router
5. 无法确认 → unresolved inbox
```

LLM Router 本身无长期记忆，只负责分流。

## 一封邮件回答多个问题

不能假设 Message = Task。

应该：

```text
Incoming Message
↓
拆成 Answer Units
↓
分别匹配 Question
↓
Question → Task
↓
分别更新 Task
```

关系：

```text
Task
↓
Question / Request
↓
Communication Thread
↓
Incoming Message
↓
Answer Unit
↓
Question
↓
Task update
```

## Human Attention Management

与之前“限制每个人的问题数量”直接对应：

```text
person_open_questions(Bob) <= N
```

Bob 已经有 3 个 pending 问题，就不要继续无限发送第 4、5、6 个。

新问题进入 queue，等前面的 resolved 再发。

# Module 7 — Governance / Guardrails

## 解决的问题

前 6 个模块让 Hermes 越来越能干。

Module 7 保证：

> 它越能干，也不会越权。

整个模块由 Harness 强制，而不是依赖 LLM 自律。

## 三个最关键的判断

### 1. Subject Visibility

请求这个信息的人有没有权知道？

不仅是 raw data。

连以下信息都可能有权限：

```text
某张表是否存在
表名
Schema
Quality Summary
Sample
Aggregate
Raw Data
```

例如没有 HR 权限的人：

```text
甚至可能无权知道 payroll 表的位置和结构
```

所以 Hermes 回答：

> 哪些数据可以支持这个问题

之前，也必须先检查 Visibility。

### 2. Authority Resolution

当需要确认某件事时，不是“找个人问”。

而是：

> 谁真正有资格确认这个问题？

根据 confirmation type 查：

```text
Asset Access
Semantic Definition
JOIN / Lineage
Business Rule
Publication
```

例如：

```text
revenue 定义
→ Semantic Authority

能不能读 payroll
→ Data Access Authority

能不能发布 Gold
→ Publication Authority
```

Hermes负责找到正确的人并推动审批，不代表 Hermes 自己是审批人。

### 3. Responder Authority

有人回邮件说“可以”，不代表这个回答有效。

```text
收到 Bob 回复
↓
他说了什么？
↓
这个 statement 属于哪种 authority？
↓
Bob 是否具有该 authority？
```

例如：

```text
Bob 是 Sales Ops

他说 order_status 的业务含义
→ 可能有效

他说“你可以读 payroll”
→ 无对应 authority
→ 只能作为建议，不能授权
```

## Visibility 同样适用于回邮件的人

Hermes 回复 Bob 时也要检查：

```text
Bob 有权看到哪些字段？
Bob 能知道哪些表存在？
能否给他 Finance 数据？
```

Hermes 自己有权限，不代表能把信息转发给任何人。

## Harness 的多个控制层

```text
Agent reasoning
↓
Task Router
↓
Tool Permission
↓
Data Scope
↓
SQL Guardrail
↓
Approval Hook
↓
Authority Check
↓
Communication Policy
↓
Cycle Checkpoint
↓
Audit
```

## SQL / Tool Guardrail

包括：

```text
read/write
table scope
row limit
timeout
sensitive columns
forbidden statement
estimated impact
```

## Trust 不覆盖硬规则

```text
Trust
= 多久需要整体人工校准

Guardrail
= 无论 Trust 多高都不能越过的边界
```

例如高 Trust 也不能自动获得：

```text
生产 DELETE
敏感权限修改
未经授权的数据访问
```

## Organization Directory / OA

真实企业最终可以接：

```text
OA
HRIS
Microsoft Entra
Google Workspace
IAM / RBAC
ServiceNow
飞书 / 钉钉 / 企业微信
```

Hermes通过统一抽象调用：

```text
find_person
find_role_owner
check_authority
check_visibility
find_approver
start_approval
```

Demo 不需要真实 OA。

直接做一个假的 `org_directory` / SQL Tool 即可，重点展示：

> Hermes 不会因为某个人说“可以”就执行，而是先检查这个人有没有对应权限。

# 七个模块最终关系

```text
1 Cycle / Trust
控制：多久必须整体停下来向人汇报

2 Role / Mission
控制：我是谁、为什么做、当前方向是什么

3 Discovery
控制：不知道下一步时，怎么主动找到人、表和知识

4 Data Steward Loop
控制：具体怎样把数据逐步变成可信资产

5 Organizational Knowledge
控制：如何把组织知识长期沉淀并复用

6 Resume / Coordination
控制：多个任务、多人沟通、等待和恢复

7 Governance / Guardrails
控制：什么能看、什么能做、谁能确认、谁能审批
```

最核心的一条运行链：

```text
North Star
↓
Current Objective
↓
读取 State
↓
能推进？
├─ 能
│   ↓
│ Data Steward Loop
│
└─ 不能
    ↓
    Gap
    ↓
    Discovery
    ↓
    找人 / 找表 / 找定义
    ↓
    更新 Knowledge + State
    ↓
    回 Data Steward Loop

过程中：
- 等人 → Resume / Coordination
- 高风险动作 → Governance / Approval
- 时间/token 到 → Cycle Review
```

最终定位：

> **Hermes Runtime 提供通用 Agent 能力；你的系统在 Hermes 之上增加了一套长期、自驱、可审计、受权限约束的 Data Steward Operating System。**
:::

   邮件 `Re:` / thread-id 优先确定性 routing，LLM router 兜底。

7. **Cycle Hook**  
   在现有 Harness 上加：
   - elapsed time
   - token budget
   - stop-new-branch
   - generate review
   - 等 Sponsor 重新放行  
   
   不替代你已有关键动作审批。

8. **Authority / Visibility Tool**  
   这是现有审批之外还缺的一层：
   ```text
   这个人有权知道吗？
   这个人有权确认吗？
   这个回复能不能作为正式 approval？
   应该找谁确认？
   ```
   Demo 可以直接用假的 org-directory SQL。

9. **Session Lifecycle 改造**  
   每次 session：
   ```text
   start
   → load summary + state + relevant SQL knowledge

   working
   → event-driven update SQL / state

   end
   → refresh project summary memory
   ```
   这样 session 不再承担长期事实。

10. **Eval 补对应测试项**  
   你已有评估框架，不是重做，只补这些新行为：
   - 会不会在未知时调用 Discovery
   - 会不会越 Scope
   - 会不会把未确认事实写成 confirmed
   - Router 是否路由正确
   - authority 判断是否正确
   - Cycle 到点是否真的停止扩展
   - 新 session 是否能准确恢复

所以可以概括成 **六类代码改动**：

```text
Prompt
Skills
State
SQL Knowledge Tools
Router / Session
Harness Hooks
```

再加现有 Eval 的测试覆盖。

```text
数据基础已具备：
- Revenue：ready
- Cost：ready
- Refund：ready
- Customer mapping：confirmed

当前质量：
- 2020+ coverage 99.6%
- historical mapping仍有0.4% unresolved

因此：
可以支持2020+客户利润分析。
```

如果用户无权知道 Finance 表：

```text
不能暴露 finance.cost_detail 表名
```

只能说：

> Relevant governed data exists, but part of the underlying finance data is outside your current visibility.

真正“哪个客户利润最高”应该交给另一个 Analytics Agent / BI 系统。

这个场景测试的是：**Hermes 不因为数据已经在 Lake 里，就退化成万能 SQL 分析机器人。**

第八个场景：**Memory 摘要和真实 State / SQL 不一致。**

背景：

Project Memory 还写着：

```text
当前已接入 5 张表，
Finance mapping 仍未确认。
```

但实际上后台已经变成：

```text
Project State:
已接入 7 张表

Knowledge SQL:
Finance mapping 已 confirmed

Asset State:
crm.customer_profile 已完成 profiling
```

新 Session 启动时，Hermes 不能直接相信 Memory。

正确流程：

```text
Session start
↓
读取 Project Summary Memory
↓
读取当前 Project State / Asset State / SQL Knowledge
↓
发现不一致
↓
以 State + SQL 为准
↓
刷新 Working Context
↓
重写 Project Summary Memory
```

比如更新成：

```text
当前已接入 7 张相关表。
Sales / Finance customer mapping 已确认。
CRM 已完成 profiling。
当前主要未解决项是 historical mapping exceptions。
```

然后才继续工作。

这个场景测试的是：

> **Memory 只是快速恢复摘要，不能成为事实源；State / SQL 永远优先。**

<a id="m167"></a>

## M167 · 用户

那么什么时候看memory 什么时候session就够了呢

<a id="m168"></a>

## M168 · 助手

可以按一个很简单的原则：

> **当前 Task 连续进行，用 Session；跨 Session、跨 Task、需要项目整体背景时，再看 Memory。**

### Session 就够的情况

同一个 Task Session 里连续推进：

```text
问 A 一个字段含义
↓
A 回复
↓
继续确认
↓
做 profiling
↓
再问一个相关问题
```

这些上下文已经在当前 Session，不需要每一步重新读 Memory。

多人 Resolution Thread 也是一样：

```text
A/B/C 正在讨论同一个 JOIN
```

只要 Task Session 没断，直接用当前 Task Session。

### 需要读 Memory 的情况

主要四种：

**1. 新 Session 启动**

```text
Hermes 新启动
→ 看 Project Summary Memory
→ 快速知道项目整体做到哪
```

**2. Task 恢复跨度比较久**

例如 3 天后有人回复：

```text
先读 Task State
+ 相关 Knowledge
必要时再读 Project Memory
```

Memory 用来补“最近项目整体发生了什么”。

**3. 从一个 Task 切到另一个 Task**

例如 Sales Task 做完，切 Finance：

```text
当前 Session 不一定知道项目最近整体变化
→ 读取 Project Summary Memory
```

**4. 要和某个具体人沟通**

这时读：

```text
Person Memory
```

比如：

```text
Bob prefers concise questions
```

只在准备联系 Bob 时加载。

---

所以优先级可以定成：

```text
当前 Task Session
↓
够用？
├─ Yes → 不读 Memory
└─ No
    ↓
    需要项目整体背景 → Project Memory
    需要个人沟通背景 → Person Memory
```

但真正执行前依旧是：

```text
Session / Memory = 给模型理解上下文
State / SQL Tool = 确认真实现状
```

也就是说 **Memory 不应该每次调用**。否则既费 token，又容易把旧摘要反复塞进上下文。

最理想的是：

> **Session 优先，Memory 按需，State/SQL 执行前为准。**

## M170 · 助手

第九个场景：**同一个人一封邮件回答多个 Task，Router 需要拆分。**

背景：

Bob 当前有 3 个 open questions：

```text id="m1p8cj"
Q1 → orders.discount 定义
Q2 → customer_id 历史映射
Q3 → refund owner 是谁
```

Bob 直接 Re: 回复：

> `order_total` 已经扣过 discount。  
> 老 customer_id 我不太确定，可能要问 MDM。  
> refunds 现在归 Alice 管。

系统不能把整封邮件塞进一个 Task。

正确流程：

```text id="6de3ly"
Incoming Email
↓
先通过 Re:/thread 找到候选范围
↓
拆成 3 个 Answer Units
↓
分别 route
```

结果：

```text id="v7w6ah"
Answer 1
→ Q1
→ semantic confirmed/candidate
→ 更新对应 Task

Answer 2
→ Q2
→ Bob 无法确认
→ 新增 MDM discovery lead
→ Task 保持 unresolved

Answer 3
→ Q3
→ Alice = candidate owner
→ 再查 org directory / authority
→ 然后联系 Alice
```

Bob 的这封邮件本身只需要回一封简短确认，甚至可以不回。

后台关键是：

> **Message 只是 transport，真正的执行单位是 Answer Unit → Question → Task。**

这个场景主要测试 Router 是否会把一个自然语言回复正确拆到多个 Task，而不是让 session 越积越乱。
