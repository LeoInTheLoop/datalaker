## 二、现有实现更细、应保留的部分

### 1. Hermes 负责循环，插件提供工具与约束

当前已经采用 Hermes 的工具注册、前后 hook、用量 hook 和 cron。恢复作业先运行 monitor，输出未变化时不唤醒模型；巡检和催办也区分确定性脚本与需要模型的工作。蓝图可以直接延续这一结构，不需要再写一套 Runtime、scheduler 或评估框架。

依据：[插件入口](../.hermes/plugins/data-steward/__init__.py) `register()`；[cron](../.hermes/plugins/data-steward/cron.py) `JOBS`、`ensure_jobs()`；[恢复 monitor](../ops/resumable.py)。

### 2. 正式审批比“有权的人回信说可以”更具体

现有门禁检查工具等级、有效票据和动作身份；对已声明归一或身份规则的工具，恢复时由 `_replay_approved_args()` 回填人批准的参数，避免模型换一种表达就改掉实际规则。callback 校验签名、有效期、链接意图并防重复决定。模型不能把普通邮件正文直接变成执行许可。

这些机制应保留。待补的是“这个人此刻是否有权确认这个对象”，而不是把正式审批改回模型读一句“同意”就执行。

依据：[门禁](../plugins/datasteward_gate/__init__.py) `_gate()`、`_replay_approved_args()`；[审批 callback](../services/approval_callback.py) 第 102、143 行；[策略表](../plugins/datasteward_gate/policy.py)。

### 3. 资产知识已经超出普通 Memory 摘要

`asset_catalog` 分开记录 observed / inferred / confirmed / refuted，带来源、证据和历史；读档默认不重复访问源，并显示观测时间。新观测为空时不直接覆盖旧结构。`metadata_watch` 比对结构变化后另建复核记录，不擅自改写历史确认。

这正是蓝图应复用的资产知识基础。缺失的组织能力、业务 authority 和项目摘要应扩展进去；不必把已知资产重新搬到一套新 Memory 存储。

依据：[catalog](../services/catalog.py) `record_observed()`、`snapshot()`、`record_inference()`、`confirm()`、`refute()`；[metadata_watch](../services/metadata_watch.py) `sweep()`、`_mark_for_review()`。

### 4. 清洗已有可复核基础，已有 Gold 保护可供下游复用

清洗保留 `_raw` 原值，已有前后样例查询函数。发布要求资产先分类，显式拒绝把 `_raw` 列发布到 Gold，保存上游血缘；数据访问还有分类和策略同步机制。这些是可复用的具体实现；按最终 R02/R16，Gold 已移出 Hermes 核心职责，现有发布代码应作为兼容/下游能力看待，不能作为核心完成条件。

但“有样例查询函数”和“首次 transformation/重大变化已由对应 Authority 复核”是两件事；最终 R03 要求后者落实到核心 Silver 工作链。

依据：[clean](../services/clean.py) `apply()`、`before_after()`；[publish](../services/publish.py) `publish_gold()`；[policy_sync](../services/policy_sync.py)。

### 5. 现有 Eval 结构应继续用

正负对照、证据不足判 `INCONCLUSIVE`、去掉护栏检查判据是否能发现错误、保留原始结果供离线重判，均已有设计与实现入口。蓝图要求的是把新行为放进这个框架。

依据：[行为 Eval 说明](../evals/behavior/README.md)、[行为驱动](../tests/run_behavior_case.py)、[测评术语](../docs/eval-model.md)。本次未重跑这些检查，不沿用旧通过数字作为当前成绩。

## 三、确实没有做到位的关键连接

### A. 有 runs，但缺少项目目标与工作任务的整体状态

`runs` 已支持 `running / waiting_human / done / abandoned / failed`，保存参数、checkpoint、等哪张审批、恢复次数等。门禁在具体工具受阻时登记任务线，cron 在批准后恢复。不能说当前没有 State 或没有跨会话恢复。

蓝图的 Task 范围更大：例如“弄清客户历史 ID 映射”可能依赖两个联系人、三个问题、若干技术验证，最后得出“不应关联”也可完成任务。它不是一条工具审批线。

还需要在现有存储上表达 Mission/Objective/Scope、任务依赖、Question、当前 Cycle 和下一步，并提供模型可查询的统一视图；不必逐字照搬蓝图表名或把所有状态塞进一个大枚举。

依据：[runs](../services/runs.py) `STATUSES`、`create()`、`suspend()`、`resumable()`；[治理库 schema](../plugins/datasteward_gate/approvals.py) `runs`；[门禁](../plugins/datasteward_gate/__init__.py) `_track_suspend()`。

对应 I01、I03、I05、I06。

### B. 有邮件归属组件，但当前入口仍按人建会话

本机 Hermes 邮件 adapter 使用 `chat_id=sender_addr`、`user_id=sender_addr`，回复上下文也以发件人邮箱为键。它保留 `In-Reply-To` 对应字段，但没有据此建立蓝图要求的 Task Session。

项目的 `mail_threads.resolve_run()` 已能根据回信头、主题 token 等找回 run；本次在当前插件、业务服务、ops 与 Docker 入口中未找到该函数接入正式邮件入口的调用。现有单元测试直接调用它，证明组件有逻辑，不能证明正式入站已完成任务分流。

普通联系人邮件的 `send_contact_email()` 还没有传入 `run_id`，按“收件人 + 相同主题”查重也不足以表达不同任务、同线程追问和消息级幂等。

需接通：出站 Task/Question/Message-ID 绑定 → 入站精确归属 → 必要时模型拆 Answer Units → 更新各问题与依赖 → 恢复相关 Task。多人讨论、静默策略和 debounce 建在这条线上。

依据：[mail_threads](../services/mail_threads.py) `record()`、`resolve_run()`；[组件测试](../tests/test_mail_threads.py)；[联系人发信工具](../.hermes/plugins/data-steward/tools.py) 第 1346—1381 行；本机 [Hermes email adapter](../../hermes-agent/plugins/platforms/email/adapter.py) 第 1179—1203 行。本机源码检查不等于已确认运行容器使用相同版本。

对应 I03、I06。

### C. WIP 已有，但不是完整的“每人最多几个问题”

`_wip_exceeded()` 已限制全局及每个 approver role 的待办；环境变量名虽含 `PER_PERSON`，实际按角色统计审批记录。一个人兼多个角色时，与按真人汇总不同；普通探索提问也没有全部进入这条队列。

因此应复用现有在办机制，扩展实际收件人、开放问题、排队与释放语义。最终 R10 新增每批处理窗口、配额不自动补满、仅严重阻塞/明确催办提前追加；每人 3、2–3 工作日及静默窗数值保留为配置，不因默认值不同判代码错误。

依据：[门禁](../plugins/datasteward_gate/__init__.py) `_wip_exceeded()` 第 1065 行；[联系人发信工具](../.hermes/plugins/data-steward/tools.py)；[催办](../ops/escalate.py)。

对应 I06、D10。

### D. 时间窗检查存在，但 Bronze 复制没有经过它

实际链路是：

```text
ingest_table → sync.sync_table → Trino INSERT INTO Iceberg SELECT FROM 源 catalog
```

`connector.query()` 只在 `purpose='bulk'` 时检查 `_in_bulk_window()`。`sync_table()` 的元数据读取经过数据工具，但复制数据走自己的 Trino 路径，没有调用该窗口检查。

因此当前不能承诺“批准后自动排到晚上执行”。Connector 在窗口外的报错虽写“任务已排队”，该分支本身执行的是记录拒绝并抛异常，没有创建持久化排期任务。

应在实际复制执行入口接入约束，并让已批准、等待窗口、实际执行、失败/错过窗口分别可查询；补执行前通知与必要复查。保留现有 schema 漂移检查，不能为了定时执行而绕过它。

依据：[工具](../.hermes/plugins/data-steward/tools.py) `_ingest_table()` 第 157 行；[sync](../services/sync.py) `sync_table()` 第 284—335 行；[Connector](../services/connector.py) `_in_bulk_window()` 第 458 行、`query()` 第 471 行。

对应 I03、I04、I07。这是具体执行链未接通，不只是命名或架构偏好。

### E. 新 Bronze 不会自动形成蓝图的关联评估任务

当前接入更新同步状态，后置 hook 记录执行与资产来源。关联工具可以对指定资产提出候选、获取湖内技术证据、申请确认；但没有找到“新资产落地 → 幂等登记 Integration Assessment → 选择相关旧资产 → 执行或等待”的完整触发链。

`_silver_ready()` 负责在清洗轮开启后发现尚未清洗的 Bronze；它不能替代关联评估。新表可以评估为“不相关”并结束任务，不能把“工具能 propose_link”当成“每次新增资产都完成过评估”。

已有 overlap、孤儿值和 cardinality 线索可复用。当前孤儿统计基于去重后的值集合，且有采样上限，不能直接当成全量行级匹配率；历史 mapping 的有效日期、一对多异常及 Evidence 留痕仍需扩展；R16 不要求 Hermes 承担最终业务验收或异常清零。

依据：[sync](../services/sync.py) `sync_table()`；[门禁审计](../plugins/datasteward_gate/__init__.py) `_record_provenance()`；[恢复 monitor](../ops/resumable.py) `_silver_ready()`；[linkage](../services/linkage.py) `overlap()`、`candidates()`、`propose()`。

对应 I02、I03、I07。

### G. 每日预算和周报不能代替到线立即报告的 Cycle

当前预算检查按日累计 token/费用，配置为 0 时不启用，缓存 60 秒；读取失败时不阻断。超限后在工具门禁限制 L1 及以上动作。它不是独立 Cycle 的墙钟时间/token 双边界，也未自动切换到报告。

另有 `stage-report.py`：按 runs 终态或默认 15 天产生 Bronze 轮报告，`--send` 时先落 `ROUND_CLOSED`。但它没有登记在当前插件 `JOBS` 中；已有周报是每周一运行。不能把几个分别存在的机制相加，认定已完成“半天到点立即汇报”。

需补 Cycle 状态、边界触发、报告保留预算、停止后的入站记录、Sponsor 的下一轮范围/预算决定。现有用量记录、事实报告数据源与恢复 monitor 都应复用。

依据：[门禁](../plugins/datasteward_gate/__init__.py) `_budget_exceeded()` 与调用处；[stage-report](../ops/stage-report.py) `MAX_DAYS`、`round_state()`、`main()`；[cron](../.hermes/plugins/data-steward/cron.py) `JOBS`。

对应 I08、D01/D02/D06/D07/D14。

### H. 能联系谁、谁能回信、谁有权确认、谁可知道什么仍需分别实现

当前已经有 `register_contact` 和 `send_contact_email`，不能再说“没有指定收件人工具”。登记明确不授予角色或数据权限，发信检查已登记联系人及部分凭证外发模式。

Hermes 邮件入站另受 `EMAIL_ALLOWED_USERS` 等配置约束。因此也不能说“首次只有创建者能对话，介绍了谁就自动可以与谁双向对话”；是否只开放创建者取决于配置，登记联系人不会自动修改入站名单。

审批已有 role assignment 和按资产归属/域解析审批角色；但 callback 主要校验签名票据，未建立“当前在职状态 × 动作类型 × 资产范围 × 本次回复人”的完整复核。跨系统关联不能只因某个 steward 收到了签名链接，就认定他有权代表双方。

当前数据分类/Trino 权限也不能替代 Subject Visibility：表名、schema、质量摘要及多方邮件内容，需要按请求者和所有收件人的范围决定能否披露。联系人检查和凭证正则没有覆盖这一层。

依据：[联系人工具](../.hermes/plugins/data-steward/tools.py) 第 1296、1346 行；[门禁](../plugins/datasteward_gate/__init__.py) `resolve_approver_role()`；[callback](../services/approval_callback.py) 第 102—158 行；[Hermes adapter](../../hermes-agent/plugins/platforms/email/adapter.py) `EMAIL_ALLOWED_USERS`；[冲突升级行为 Case](../evals/behavior/cases/04-conflicting-stewards-escalation.json) 也将授权模型列为已知欠账。

对应 I01、I04、I06、I09、D22。R07/R08 已定可用小型受控目录、已确认上级/Admin、Sponsor/Boss 明确指定、合法转授权等独立可信来源；本人自述不能赋权。R14 进一步要求同一资产同一种 Authority Type 唯一当前 active approver，并按有效期换人；这些仍待映射代码，不必先接真实 OA。

## 六、建议实施顺序

1. **先统一职责与执行边界。** 按已定治理职责调整对外分析/Gold 边界；补 authority/visibility 独立可信来源及唯一当前审批人契约；修正实际复制路径的窗口准入及“已排队”状态承诺。
2. **在现有治理库上补项目、任务和问题关系。** 明确 Mission/Scope、完成条件、等待与恢复条件，再把邮件绑定和 Task Router 接入 Hermes 正式入口。
3. **接上独立 Cycle 与立即报告。** 复用用量、cron、报告事实源与门禁；明确阶段批准和周期续跑不是同一决定。
4. **完善资产工作链。** 新 Bronze 触发评估待办、湖内深度画像、规则后的必要样例复核、复杂 mapping、异常与证据沉淀；按 Done Criteria 验收可复用 Silver，再接任务优先级和多方静默合并。
5. **沿用现有 Eval 做行为验收。** 优先测同人多任务、混答、联系人资格、窗口外复制、到线报告、延迟回复与最新状态恢复；每项保留可达正对照和环境终态证据。

实施分工保持现有原则：模型负责相关性、语义、任务建议和摘要；确定性代码负责状态关联、有效性、事件幂等、权限、窗口、预算和审计。跨会话可靠性以最新 State/SQL 为依据，不能仅靠把聊天记得更长。
