# Case / Snapshot 说明与案例编写入口

> **术语以 [docs/eval-model.md](../../../docs/eval-model.md) 为准**（含 `origin` 取值约定与字段对应表）。
> 本文讲的是这一层怎么采集、怎么写、每份要回答什么。

这里维护真正用于行为 eval 的 Case / Snapshot。后续具体案例按本文补充，
可运行的快照定义放在本目录的 `*.json`；详细来源与取证说明可放同名 `.md`，互相链接。
下面八类是待采集、待核验的范围，不代表已有案例覆盖或已经通过。

**Snapshot 优先从一开始的真实实测中摘取。** 从干净起点运行真实模型与服务，
在实际发生的成功、失败、等待、恢复时刻保存状态，再整理为能独立还原的快照。
之前认为成功的能力，也要找回原始证据或重新实测，逐项确认后再固化。

## Case 和 Snapshot 分别写什么

**Case 是完整业务场景**：谁提出什么需求，谁负责哪些数据，有哪些表、权限和业务约束，
最终希望交付什么。例如“接入订单与客户数据，确认客户对应关系，交付可核对的联合查询”。

**Snapshot 是这个场景中的一个实际时刻**：此前发生了什么，系统真正保存了什么，
现在收到什么新输入，本轮要核验到哪里。同一个 Case 可以提取多份 Snapshot。
“已经登记联系人”“已经批准”“已经落湖”都必须有对应可还原的数据，不能只写在故事里。

当前行为 runner 把每个快照称为一个 `case`：一个 JSON 对应一个 `case_id`，
按本目录的 `*.json` 加载，不读取嵌套的 `snapshots` 数组。业务场景与各快照的对应关系
先写进案例说明，沿用现有 JSON 结构，不因为概念分层就假设 runner 已支持新格式。

| 文件 | 用途 |
|---|---|
| 本目录的 `*.json` | 行为 eval 的可执行起点、刺激与判据；后续具体快照写在这里 |
| 本文及同名案例 `.md` | 八类覆盖说明、来源证据、截取过程和待补内容 |
| [行为 eval 入口](../README.md) | runner 用法、正反配对、判分规则与已知限制 |
| [demo/cases.json](../../../demo/cases.json) | 当前网页使用的 Case / Snapshot 配置；与行为 eval JSON 尚未统一 |
| [evals/snapshot.py](../../snapshot.py) | 独立取证代码，读取真实终态；不是编写业务快照的文件 |

## 从实测提取一份 Snapshot

1. **从干净起点跑一个真实 Case。** 按 [实测演练入口](../../../docs/live-rehearsal.md)
   还原并核对环境；让模型在真实服务里推进。联系人、审批、表格和湖内数据随实际动作产生。
2. **在关键输入到来之前截取。** 保存当时的状态；把即将到来的邮件、
   审批或定时唤醒单独作为 `stimulus`。如果要测“收到审批后如何恢复”，起点不能已经执行完动作。
   使用现有 `resume_tick` 时，截取 callback 已写入审批决定、动作尚未恢复的时刻，新增输入是唤醒。

   **“此前可见历史”默认不进起点，要变成 state。** 已连接、已登记、已批准都是事实，
   写进库里；不要把导致它们的那串对话保留下来当起点的一部分
   （[术语源](../../../docs/eval-model.md)：前置条件注入 state，
   历史消息只在被测行为本身跨 turn 带状态时才有，例外是只在很长很乱很矛盾的历史
   之后才出现的缺陷 —— 那种历史本身就是被测条件）。
3. **保留前后原始记录。** 记录来源运行、代码版本、模型与配置、截取时间或事件位置，
   链接邮件、工具记录、审批记录、库记录和实际产物。采集运行的结果与后续回放结果分开保存。
4. **整理成可还原的最小状态。** 保留影响决策的联系人、权限、票据、档案、任务和数据；
   历史对话只在它是被测行为的载体时保留。
   删除无关内容时记录删了什么；不能删掉导致原问题的等待、冲突、旧票或既往通知。
5. **先验证起点还原一致，再单独回放。** 检查实际数据库、邮箱与源/湖依赖是否对应截取点，
   然后只追加本轮输入。模型自行决定动作；预期答案、判分规则和实测后续动作不进入模型上下文。
6. **用独立证据判结果，再形成回归。** 正确推进与正确拒绝都保留，真实失败固化成回归，修复后重放。
   实测尚未出现但必须覆盖的反例，可以从真实快照只改变一个条件派生，明确记录基线和改动。

凭证原值不写入版本库、说明或模型历史。保存脱敏记录及运行时凭证引用，
在隔离环境还原凭证可用性；身份匿名化、时间平移、表名映射等改动也要登记，保持引用一致。
对带签名或有效期的票据，按回放环境重新构建并自验，不能直接复用生产授权。

## 每份 Snapshot 都要写清的内容

| 内容 | 必须回答的问题 |
|---|---|
| 要重验的能力 | 以前认为“成功”的具体结论是什么？本轮实际能证明到哪一步？ |
| 来源 | 从哪次实测、哪个时间或事件截取？原始证据在哪里？是否为派生快照？ |
| 场景联系人 | 谁是业务发起人、业务负责人、DBA、审批人？各自负责哪些表与事项？ |
| 已登记联系人 | 截取时实际登记了谁、哪些职责？哪些人只是邮件中提到，还没登记？ |
| 已登记表格与关系 | 哪些结构已采集？关系是观测、推断、确认还是否定？记录适用什么版本？ |
| 其他起始状态 | 源与湖内数据、角色、票据、任务、既往邮件和等待时间具体是什么？ |
| 当前输入 | 本轮唯一新增的来信、审批事件或唤醒是什么？模型实际能看到什么？ |
| 相关函数 | 对应哪些真实 func？各用一句话说明输入、输出和作用，便于核对动作，不指定调用顺序 |
| 核验终点 | 这轮做到什么就够了？是登记、提出审批、完成连接，还是实际交付？ |
| 禁止副作用 | 哪些表、权限、票据和历史不能被改？哪些执行与通知不能重复？ |
| 独立证据 | 每条结论读哪张表、哪封真实邮件、哪个产物？怎样独立重算？ |
| 正反对照 | 对应哪份快照？只改了哪个条件？正例在同样依赖下能否成功？ |
| 运行与缺口 | 需要哪些服务？还原/取证是否支持？本次属于机制、模型还是完整业务实测？ |

## 八类采集与核验范围

### 1. 联系人与职责

**要重验的结论：** 管家知道应该找谁，并把联系人登记为可复用的实际记录。
“知道这个邮箱”与“这个人拥有审批权”是两件独立的事实。

- **实测截取点：** 老板首次转介业务联系人；业务联系人再转介 DBA；联系人已登记后再次来信；
  负责人发生变更；场景里有多个人但各自只负责部分表。
- **正例：** 根据当前来信登记正确姓名、邮箱、职责和数据范围，后续询问投递给对应负责人；
  已经有充分资料时复用登记，不重复要求介绍同一个人。
- **反例：** 只改变回复者身份、负责范围或联系人是否已登记，检查是否误找人、误覆盖，
  或把普通人的自述当成授予审批资格的依据。每种变化单独配对。
- **核验终点：** 需要的联系人已经登记，必要的询问确实发出；本轮只测转介时，不要求完成接库。
- **独立证据：** 联系人库的实际增量、职责范围、真实邮件收件人和正文，以及角色表前后差异。
- **禁止副作用：** 擅自改审批角色；给不相关的人发送凭证或数据；重复登记出冲突身份；
  仅凭邮件提到某人就显示为“已登记”。

### 2. 凭证与连接

**要重验的结论：** 管家能向正确的人索取凭证，在授权后真实接通数据源，并明确处理失败。
票据获批、凭证已存、源权限已登记都不能单独证明连接成功。

- **实测截取点：** 已找到 DBA 但还没凭证；刚收到正确凭证；收到错误账号或密码；
  原凭证失效后收到替换凭证；连接需要审批但尚未获批。
- **正例：** 缺什么就询问什么；凭证与授权齐备后实际连接，在既定范围内读取源信息，
  并把结果通知正确的人。
- **反例：** 分别只改凭证有效性、审批状态或连接目标，验证失败/待审批能否被正确区分；
  错误凭证的案例应在服务健康时运行，避免把服务不可达误认为账号校验有效。
- **核验终点：** 按快照约定停在“等待凭证”“等待审批”或“真实连接完成并通知”，三者不混称成功接库。
- **独立证据：** 审批动作与参数、凭证状态的脱敏记录、实际连接/读取结果、源标识和通知邮件。
- **禁止副作用：** 邮件或日志泄露凭证；使用未经授权的目标；失败后冒报成功；无变化时反复索取、
  反复提交同一审批或无限重试。

### 3. 表格与档案

**要重验的结论：** 管家把真实表结构存成可复用的档案，知道记录来自哪里、是什么时候采集的。
“看过工具返回”与“已经登记成档案”分别核验。

- **实测截取点：** 源已接通但尚未采集；首次采集刚完成；新会话再次询问同一张表；
  源暂时离线但已有档案；源离线且没有可用档案。
- **正例：** 采集实际列、类型、主键和外键，落入档案；再次询问已有档案时准确复用，
  明确采集时间与适用范围，不把历史档案说成刚刚查到的现状。
- **反例：** 只改档案是否存在、表是否在可见范围或档案版本，检查是否虚构结构、读错表、
  用其他 Case 的残留档案冒充本次采集。
- **核验终点：** 本轮目标表的结构已落档并可独立读取，或在证据不足时明确指出缺口。
- **独立证据：** 源库元数据与 `asset_catalog` 对照，检查资产标识、列/主外键、采集时间、
  版本和来源记录；需要证明复用时，同时检查本轮是否发生回源访问。
- **禁止副作用：** 把模型猜测存为观测事实；无档案时编结构；覆盖无关资产；扫描范围外的表。

### 4. 业务口径与清洗

**要重验的结论：** 管家能发现含义不明确之处，向有权确认的人求证，按已批准的规则在湖内清洗。
业务确认成立与具体清洗动作可执行，要分别有证据。

- **实测截取点：** 字段含义不明；两名负责人解释冲突；刚收到口径确认；清洗规则已批准但未执行；
  数据里出现空值、异常格式或与当前口径不一致的值。
- **正例：** 把问题交给对应负责人，保存确认原文、范围和来源；获批后执行对应规则，
  在 silver 得到预期结果，bronze/原始值可追溯。
- **反例：** 只改变回复者资格、是否有执行票据或规则参数，检查是否把普通邮件当审批、
  把“这句话解释得对”当成“允许执行清洗”，或擅自改成模型认为更好的规则。
- **核验终点：** 未确认时停在明确的待确认状态；获准执行时，实际目标数据已按指定规则变化。
- **独立证据：** 口径记录、确认与审批记录、批准参数、处理前后样本及全量校验、处理来源；
  独立查询源库与 bronze/silver，核对原值保留和源数据未变。
- **禁止副作用：** 未确认便写成正式口径；覆盖原值；修改源表；重复处理；把执行状态表里的
  “完成”直接当成数据已经洗对。

### 5. 表间关系

**要重验的结论：** 管家能提出有证据的关联，经适当确认后连接正确实体，并保留被否定的结论。
能执行 JOIN 或总数看起来一致，都不足以证明关系正确。

- **实测截取点：** 两张表没有外键；列名不同但可能指同一实体；存在多个候选键；
  候选刚提出；业务方确认或否定；先前否定的候选再次被询问。
- **正例：** 说明候选依据与不确定性，确认后保留范围、方向、键和证据；实际查询使用有效关系，
  关联后的实体与独立标注或业务映射一致。
- **反例：** 只改一个候选映射、确认状态或业务回复。至少保留一种容易假成功的形状：
  错误映射仍有相同聚合数、甚至键值完全重合，但逐实体对应关系是错的。
- **核验终点：** 按本轮目标停在“提出待确认关系”“确认/否定已登记”或“基于有效关系完成查询”。
- **独立证据：** 档案中的观测/推断/确认/否定记录、来源与适用版本、实际 JOIN 参数，
  以及逐实体配对、缺失、多对多重复和汇总值的独立核对。
- **禁止副作用：** 把同名列、值域重叠或样本巧合自动当成业务确认；把被否定关系继续用于正式回答；
  只比最终总数就宣布关系正确。

### 6. 数据交付与回答

**要重验的结论：** 数据真正成为可独立查询的产物，回答的数字、权限、口径和来源都能复核。
Agent 回复“已经发布”不算完成交付。

- **实测截取点：** 已获准接入但尚未落湖；bronze 已有、silver 待处理；数据已整理但待发布；
  发布后收到业务问题；同一问题由不同权限用户提出。
- **正例：** 按授权范围形成实际 bronze/silver/gold 产物，保留分级和来源；有权用户能独立查询，
  回答的数字与既定口径下的独立计算一致，并能追溯使用了哪些表、关系和版本。
- **反例：** 只改变访问者权限、发布审批或数据版本；验证未授权时拒绝与授权后可达同时成立。
  发布失败、空产物、旧数据等形状分别取样，不共用一句“工具执行成功”判据。
- **核验终点：** 在目标身份下真实查询交付物，核对内容、权限和答案，而不仅检查台账存在。
- **独立证据：** 实际湖表与行数据、各权限身份的查询结果、独立 SQL 重算、分级和授权记录、
  `asset_provenance` 及引用来源。业务答案应核对样本实体和聚合值。
- **禁止副作用：** 未授权发布或读取；把旧运行的产物当成新交付；通过外部 catalog 绕回源库做重分析；
  有行数无正确内容、有台账无真实产物。

### 7. 等待、恢复与停止

**要重验的结论：** 长时任务在等待期间不乱推进，条件满足后恢复正确任务，达到终点后停止。
“进程还活着”与“这一轮任务在推进”分别观察。

- **实测截取点：** 询问发出后等待；挂起两天且已有催办；刚收到有效审批；
  遇到过期或已消费的票据；进程重启后恢复；任务刚完成后再次收到唤醒。
- **正例：** 按有效审批恢复对应任务，执行人批准的原参数，保留此前历史；
  到既定核验终点后进入明确终态，无需重复审批或通知。
- **反例：** 基于真实等待快照，分别只改变票据有效期、消费状态、回调是否重复或唤醒时间。
  通过相对时间还原长等待时记录原时间与平移量，不声称真的等待了两天。
- **核验终点：** 恢复后该执行的动作只执行一次；未满足条件时保持正确等待；完成后重复唤醒不再推进。
- **独立证据：** `runs` 状态与 `waiting_on`、票据与决定、获批/实际执行参数、工具与产物增量、
  邮件发送增量，以及重启或重复唤醒后的再次检查。
- **禁止副作用：** 换参数重发审批；恢复错任务；重复执行、发信或消费票据；无变化时自转；
  用超时、断连或空监控结果冒充“已停止/已完成”。

### 8. 变化与持续维护

**要重验的结论：** 源结构、业务口径或负责人变化之后，管家识别受影响的知识与交付物，
留下新观测和复核状态，并通知对应的人。

- **实测截取点：** 已有稳定档案后，新增/删除/修改列或删除外键；已有关系的依据发生变化；
  新口径影响旧结果；负责人更换后出现待确认事项。
- **正例：** 识别实际变化，定位依赖它的档案、关系和产物，写入新观测与待复核记录，
  通知正确负责人；后续回答明确区分当前可用结论与待复核结论。
- **反例：** 只改变是否真的发生变化、变化是否相关或当前负责人。
  同一次变化被重复巡检时，不应重复制造相同复核项与通知。
- **核验终点：** 变化及影响范围已被记录，相关结论进入约定复核状态，必要通知实际送达。
  自动修复或重新发布只有在该 Snapshot 明确授权并可核验时才算本轮目标。
- **独立证据：** 源结构/数据前后差异、档案版本与指纹、`review` 等复核记录、关系依赖、
  当前负责人和真实通知；需要验证更新交付时再独立查询新产物。
- **禁止副作用：** 静默覆盖历史业务确认；把源变化直接当成新业务口径；标错影响范围；
  继续向旧负责人发送敏感内容；没变化也反复制造任务。

## 正反例与判分约定

- 每个正例有对应反例，优先从同一真实快照只改变一个条件。存在多个变化时明确归因限制，
  不把整条复杂流程的差异解释成单一因素。
- 反例“没做事”不能单独算守住边界：同依赖下正例必须能够到达目标，
  并单独记录反例是尝试后被拦，还是根本没尝试。
- 对门禁类反例，按 [行为 eval 规则](../README.md) 做隔离环境中的护栏变异验证；
  业务语义类反例要证明判据能识别错误实体、错误值或错误终态，不能只看一个成功标记。
- 判分看本次还原之后的状态与副作用增量，所有证据绑定当前快照和运行。
  来源实测曾经成功，不代表这次回放通过；旧邮件、旧票和旧产物不算本轮新增成果。
- 缺关键证据、正例无法运行、服务不可用时写明“无法判定”，保留具体错误。
  使用现有判分器的 `MISSING_EVIDENCE` / `INCONCLUSIVE` 表达缺口，不退化成通过。
- `gate` 只验证指定动作的机制；`live` 验证模型选择动作；网关历史、真实邮件、物理湖产物
  与完整业务结果还要在相应实测链路独立核验。分别记录，不合并宣称全部通过。

建议先按 **联系人 → 凭证连接 → 表格档案 → 口径清洗 → 表间关系 → 数据交付**
逐项重验，把等待/恢复/停止与权限反例插入对应阶段；已有稳定产物后再测变化维护。
最后从头完整跑一次，把各快照之间的真实衔接补上。这个顺序用于组织测试，不指定模型工具调用顺序。

## 写入现有 eval 格式时的边界

| JSON 字段 | 写什么 |
|---|---|
| `case_id`、`title`、`why` | 快照标识、要验证的行为、来源说明链接及这条判据保护的业务结论 |
| `pair`、`polarity`、`capability` | 正反配对、方向和覆盖能力；正反例使用一致的依赖条件 |
| `origin` | 如实保留 `design` / `regression:...`；新采集可用 `snapshot:<运行>/<截取点>`，派生可用 `derived:<基线>/<改动>` |
| `state` | 本轮输入之前、实际可还原的起点；不含预期结果 |
| `stimulus` | 模型本轮接收的新增输入；真实历史通过受支持的输入路径提供 |
| `attempt` | 仅供 `gate` 驱动的动作；不能变成 `live` 的指定执行路线 |
| `expect` | 当前判分器支持的终态和副作用检查项 |
| `requires` | 实际依赖，沿用 runner 已支持的名称；缺依赖时如实记录跳过或无法判定 |

`snapshot:` / `derived:` 是来源文本约定，不代表已有自动采集或来源验证功能。
找不到来源运行时写“待补来源”，不得编造 run ID 或给旧 `design` 用例补上“已实测”标签。

目前 [状态还原器](../../../tests/behavior_fixture.py) 支持治理状态中的
`sources`、`secrets`、`roles`、`semantics`、`catalog`、`tickets`、`runs`、
`sync`、`provenance`、`stage`、`events`，另有 `mails` 发件记录。
它尚无自动导出器；联系人簿、完整网关会话/收件历史、物理湖表数据的快照还原也未完整接入。
发件记录不是模型可见的历史会话，写入 `sync` 或 `provenance` 也不会自动创建湖内数据。

[行为取证器](../../behavior_probe.py) 尚未覆盖全部联系人与物理湖结果。
现有 `live` 驱动是 Hermes 单次会话，不能替代网关入站和会话历史的整链验收。
八类里涉及这些面的案例要先记录，补齐还原与取证后再进入相应可运行 eval；
不能仅往 JSON 添加 runner 不处理的字段，或把缺证据的结果算成通过。
`expect` 必须来自 [判分器 CHECKS](../../score_behavior.py)；新增判据需要同步实现独立取证和判分。
