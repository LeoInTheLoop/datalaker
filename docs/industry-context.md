# 行业经验与真实数据

readme 的设计是推演出来的，逻辑自洽但缺少外部锚定。
这份文档把每一条关键设计对应到**真实发生的事**和**可引用的数字**。

> **数字的可信度**：本文数据主要来自分析机构报告与从业者调查，不是受控实验。
> 不同来源对「失败」的定义不同（放弃 / 未上生产 / ROI 不达标），**不可直接相互比较，也不应求平均**。
> 它们的价值在于**方向一致**：多个独立来源指向同一结论。下文标注了每条的来源与局限。

---

## 1. 这是不是真问题

| 数据 | 来源 | 年份 |
|---|---|---|
| **60–85%** 大数据项目失败 | Gartner | 2015–2017 |
| **87%** 数据科学项目未能上生产 | VentureBeat | 2019 |
| **98.8%** Fortune 1000 在投资数据，但只有 **37.8%** 认为自己是数据驱动 | NewVantage Partners | 2020 |
| 到 2027 年 **80%** 的数据与分析治理项目将失败 | Gartner | 预测 |
| 数据质量差平均每年造成 **$12.9M** 损失 | Gartner | 2020 |

> 局限：Gartner 的比率是分析师估计，方法论未公开；VentureBeat 的样本是自报；
> NewVantage 只覆盖 Fortune 1000。**但四个独立来源方向一致。**

### 失败的原因是组织性的，不是技术性的

这是本项目最重要的外部支撑：

> **92% 的高管认为「文化」是成为数据驱动的主要障碍，而非技术。**
> —— NewVantage Partners，2022（连续五年得到同一结论）

学术侧的结论一致。Gahi（2026）在《What Went Wrong with Data Lakes? A 15-Year Reality Check
from the Field》中综合 64 份来源与近 500 条一线记录后写道：

> "The Data Lake sold a technical fix to problems that were mostly about people and process."
> （数据湖为一个主要关于人和流程的问题，卖了一个技术解法。）

**这正是 readme 第 1 节的论断**：需要的不是更强的数据系统，而是一个能替你去跟人确认的员工。

## 2. 时间都花在哪了

| 数据 | 来源 |
|---|---|
| 数据专业人员每周浪费约一半时间；**30%（约 14 小时/周）** 花在找不到、无法保护或准备数据上 | IDC, 2018 |
| **37%** 的「获得洞察」时间用于**搜索数据**，36% 用于准备数据 | IDC, 2018 |
| 数据团队平均 **30%** 时间用于搜索数据 | Atlan, 2023 |
| 数据工程师平均 **40%** 时间在评估或检查数据质量，约合**每周 2 天** | Monte Carlo, 2022 |

### 规模会放大这件事

Monte Carlo 2026 年调查给出了一个可直接用于容量估算的对照：

| 团队 | 平均表数量 |
|---|---|
| 花 **>50%** 时间处理数据质量 | **2,571 张表** |
| 花 **<50%** 时间处理数据质量 | **208 张表** |

> 这组数字支撑了 readme 10.7 的 WIP 限制与 10.3 的「候选集是 open 任务而非全部历史」：
> 一个真实环境的表数量在数百到数千量级，**逐表人工处理不可行，必须分组与限流**。

## 3. Data Swamp 的可测量定义

Gahi（2026）把「数据沼泽」从比喻变成了可诊断的状态。满足以下**三项或以上**即判定为 swamp：

| # | 指标 | 公式 | 阈值 |
|---|---|---|---|
| 1 | **Ownership Coverage Rate** | 有指定 steward 的数据集 / 总数据集 | **< 50%** 有风险 |
| 2 | Metadata Completeness Index | 已填必填字段 / 总必填字段 | < 40%（数据密集行业应取 < 30%） |
| 3 | **Dataset Dormancy Rate** | 过去 90 天零查询的数据集 / 总数据集 | **> 40%** 有风险 |
| 4 | Lineage Coverage Gap | 有血缘记录的关键管道 / 关键管道总数 | 监管类 < 100%、运营类 < 80% 有风险 |
| 5 | Duplication Ratio | schema 相似度 >90% 或内容哈希相同的重复对 / 总数据集 | > 20% 有风险 |
| 6 | Validation Coverage Rate | 有自动质量门禁的生产管道 / 生产管道总数 | < 100% 有风险 |

> 作者注明这些是**从实践中总结的启发式阈值，非经验验证的临界值**，
> 且强调「趋势比绝对值更有诊断力」——连续几个季度指标恶化，比某一次超标更能说明问题。

**直接可用于本项目**：

- 指标 1 和 3 正是 readme 11.2「源系统侧权限现状发现」的量化形式
  —— 「87 张表无人认领」「财务月度表 187 人可读但近 90 天仅 6 人访问」不是编的场景
- 指标 5、6 可直接作为 Remediation Ledger（第 7 节）的检测项
- 整组指标可以作为 Claw 的**首次体检报告**，比任何演示都更有说服力

## 4. 退化是有路径的，不是突然发生

Gahi 给出的五阶段模型（典型时间线，无干预时）：

| 阶段 | 时间 | 特征 |
|---|---|---|
| **1 快速摄入** | 0–6 月 | 强调 time-to-data，治理被推迟到「第二期」，用户热情高 |
| **2 治理推迟** | 6–18 月 | 元数据缺口出现但被当作临时问题；**ownership 未定义，人人以为别人负责** |
| **3 信任侵蚀** | 12–24 月 | 出现无人能答的问题；用户转向影子电子表格与私人导出 |
| **4 退回熟悉系统** | 18–36 月 | Excel 泛滥；lake 沦为只有专家能用的暂存区 |
| **5 归档状态** | 24 月+ | 持续存在但停止交付价值；删不掉（删除需要从未做出的治理决策） |

### 阶段 3 那三个「无人能答的问题」

原文列举的是：

> "Which customer table is authoritative?"（哪张客户表是权威的？）
> "Why do sales figures differ between reports?"（为什么销售数字在两份报告里不一样？）
> "What does this field actually mean?"（这个字段到底什么意思？）

**这三个问题的共同点：答案不在数据里，在人的脑子里。**
它们正是 Claw 设计中「必须停下来问人」的那一类判断（readme 5.2 停止点）。

## 5. Data Steward 的真实工作流

来源：Data Governance Field Library《The Data Steward Playbook》，以及行业角色调查。

### 时间投入

| 角色 | 每周投入 |
|---|---|
| Data Steward | **5–10 小时** |
| Data Owner | **2–3 小时** |

> 这个数字解释了为什么 readme 10.7 的 WIP 限制必须存在：
> Owner 每周只有 2–3 小时，一次给他 30 个待批事项，等于什么也批不了。

### 实际节奏

| 周期 | 内容 |
|---|---|
| **每日 15–30 分钟** | 跑关键质量检查。「The daily check is non-negotiable. 15 minutes every morning.」失败即刻按约定渠道通知 owner |
| **每周 1–2 小时** | 更广的检查、梳理累积问题、汇总成简报交给 owner |
| **事件触发** | 质量失败（按严重度分类、记录、再升级）；变更请求（评估影响）；消费者投诉（进 backlog，由 owner 定优先级） |

### 处理变更请求的标准动作

Playbook 的原话是：

> "Tell the owner what will break, what is safe, and what you would do if it were your call.
> Then they decide."
> （告诉 owner 什么会坏、什么是安全的、如果由你决定你会怎么做。然后让他们决定。）

**这与 readme 11.5 的「带着依据提案，而不是开放式提问」是同一件事**，
且与 6.1 的同步频率提案、11.5 的权限收敛提案用的是同一个模式。
不是我们发明的交互范式，是这个岗位本来就该这么干。

### 四个公认痛点

| 痛点 | 原文表述 | 对应设计 |
|---|---|---|
| **有责无权** | 要对不向你汇报的人执行标准，只能靠影响力 | 第 9 节把「批准」变成系统层面的硬门禁，而非人情 |
| **静默修复** | 未记录的修复造成知识流失，无法识别模式 | 第 7 节 Remediation Ledger 强制留痕 + 复发统计 |
| **升级过载** | 把每个问题都甩给 owner 而不附建议，会造成瓶颈 | 10.7 WIP 限制 + 提案式交互 |
| **关系破裂** | 期望不清晰时 steward–owner 关系迅速恶化 | 10.4 角色化 + 5.5 固定汇报节奏 |

### 工具现状

Playbook 描述的典型 steward 工作环境：

> 用电子表格管理元数据、用邮件跟踪质量问题、用 PowerPoint 记录血缘——然后不堪重负。

**这就是 Claw 要替代的东西。** 不是替代 Trino，是替代那个电子表格和那些邮件线程。

## 6. Schema 变更的真实破坏力

支撑 readme 6.1「schema 变更后继续同步需 L2 确认」的设计：

| 数据 | 说明 |
|---|---|
| Schema drift 占**静默**下游数据质量事故的 **40%+** | 「静默」是关键：不报错，结果照样错 |
| Schema drift 频率每上升 1 个百分点，生产事故增加 **27%** | 非线性放大 |
| 缺少自动契约测试的生产管道中，**60%+** 受 schema drift 影响 | |
| 数据损坏平均在触发变更后 **8–72 小时**才被发现 | 发现延迟就是污染扩散窗口 |

> 这解释了为什么 6.1 把「源系统加了字段」定为需要人确认的 L2 动作，
> 而不是让 Agent 自行决定要不要、以及它是什么意思。

## 7. Governance Debt：为什么拖延的代价是复利

Gahi 提出的核心解释机制，把技术债务的概念延伸到治理：

### 七种治理债务

| # | 类型 | 说明 |
|---|---|---|
| 1 | Metadata Debt | 关于数据含义、来源、归属的文档缺口 |
| 2 | Quality Debt | 摄入时未处理的质量问题 |
| 3 | Security Debt | 延迟实施的访问控制与审计能力 |
| 4 | Compliance Debt | 监管要求与实际做法的差距 |
| 5 | **Organizational Debt** | **缺失的 stewardship 职能、未定义的 ownership** |
| 6 | Operational Debt | 平台建成后运营纪律的缺失 |
| 7 | Engineering-Discipline Debt | 版本管理、CI/CD、测试的缺失 |

### 为什么是复利

论文列出四个复合机制，其中两个对本项目最相关：

- **知识退化**：解释和治理数据所需的制度性理解随人员流动而流失。
  「本可以用几个小时记录下来的东西，几年后需要数周的考古工作，如果还能找回的话。」
- **1-10-100 传播法则**：在**摄入时**发现问题的成本 : 在**管道中**发现 : 在**决策时**发现
  ≈ 每阶段放大一个数量级。

> **这是 readme 7.1「不修源头就是付永久利息」的理论依据。**
> 也解释了为什么 Remediation Ledger 的复发统计有价值——
> 它把「每阶段一个数量级」这件抽象的事，变成了「累计清洗 124 万行」这个具体数字。

## 8. 已有 lake 的公司为什么仍需要治理层

支撑 readme 第 18 节：

论文提出 **Governance Gravity（治理引力）** 概念——组织无法仅靠技术迁移逃离既有治理结构的拉力。
观察到的现象是：即使 lake 技术上完全可用，监管报告、财务对账、审计追踪仍然回流到数据仓库，
因为 lake 提供不了**语义一致性、审计轨迹和对账保证**。

其中一个复合案例：

> 某银行把风险报告迁到 data lake。数月后监管方要求历史交易对账，
> 而 lake 无法复现与审计报告相符的数字——各系统时间戳粒度不同、
> 货币换算发生在管道的不同环节、「交易日期」的定义在各源系统之间不一致。

**这三个不一致，没有一个是存储或计算能解决的**，全部需要找人确认口径。
这正是第 18.1 节的论点：平台解决存储和计算，不解决「这个字段到底什么意思、该问谁」。

## 10. 可以直接引用的三句话

面试或答辩时，这三句比任何架构图都有用：

1. > **"The Data Lake sold a technical fix to problems that were mostly about people and process."**
   > —— Gahi (2026)

2. > **92% 的高管说，成为数据驱动的主要障碍是文化，不是技术。**
   > —— NewVantage Partners，连续五年同一结论

3. > **Steward 的标准动作是：告诉 owner 什么会坏、什么是安全的、如果你来决定会怎么做——然后让他决定。**
   > —— The Data Steward Playbook

第三句是整个项目交互设计的原型。**我们没有发明新的工作方式，只是把它自动化了。**
