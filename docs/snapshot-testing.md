# Snapshot 测试契约

## 被测对象是整套 agent，不是那个模型

**被测的是 Hermes gateway ＋ data-steward 插件 ＋ Skills ＋ 门禁 ＋ Connector
＋ 治理库 ＋ 真实邮件链路这一整套**，不是「这个 LLM 聪不聪明」。
这一条决定了怎么读一次 FAIL。

一次 FAIL 落在哪一层**都是有效发现**，没有哪一层可以被判成「不算」：

| 失败长什么样 | 它是谁的缺陷 |
|---|---|
| Skill 没把「索取凭证必须要只读」写清楚 | 这套系统的 —— 不是「测的不是模型判断，所以不算」 |
| 门禁该拦没拦、拦错了对象 | 这套系统的 |
| 工具签名逼着模型二选一 | 这套系统的 |
| 模型读了全部材料还是判错 | 这套系统的 |

换模型只是其中一个变量，不是被测对象本身。所以两件事都不许做：**不能为了让某个
模型过而放宽判据**；也**不能因为「那是 prompt 的问题不是模型的问题」就不算缺陷** ——
prompt 和 Skill 就在被测范围里。

推论是 R8 那次的读法：模型登记了联系人、发了信，但没要求只读账号。这既不是
「模型不行」也不是「测偏了」，而是**这套系统在这个局面下交付不出合格结果**。
下一步该查的是 Skill 里那句话有没有写、写了模型有没有读到，两条都算修复路径。

## Snapshot Runner

### 界限

> **对声明支持的 Snapshot，完整恢复影响本轮行为的状态，让原系统正常继续，
> 并留下可独立判分的证据；无法恢复的依赖，在启动前明确拒绝。**

可以暂时只支持一部分场景。**不能把缺失状态当成空状态，继续出结果** ——
那样产出的不是"覆盖面小一点的结论"，是错的结论：起点不是声明的那个，
判分却照常给出 PASS/FAIL。所以能力边界要落在**启动前的拒绝**上，不是文档里的一句免责。

衡量 Runner 完整度的问题不是"能还原多少类状态"，而是这三条：

1. 声明支持的，恢复后**自验**与声明一致（引用关系连得通，不只是行数对）。
2. 声明不支持的，**启动前**报错退出，不清环境、不建 run、不投信。
3. 判分只用外部证据，且**起点基线与本轮增量分得开**。

### 五块的现状

| 组成 | 做什么 | 现在在哪 |
|---|---|---|
| **isolate run** | 隔离 PG / 湖 / 邮箱 / session，再把这一刻的前置事实写回库 | `clear_runtime()`、`clear_lake()`、`clear_governance()`、`restore_snapshot_state()` |
| **过程记录** | 每次真实模型输入（system / messages / tools）＋ 输入哈希 ＋ 脱敏；hook 记 request/response 事件 | `services/input_audit.py`、`services/snapshot_evidence.py`、`HERMES_DUMP_REQUESTS` |
| **max time** | 固定时间窗到点由外部停网关，写独立结束记录 | `DEMO_WINDOW_SECONDS`、`completion.json` |
| **max turn** | `pre_tool_call` 数这一轮动手几次，被 block 的也算，到线不放行 | `CLAW_MAX_TURN`、`CLAW_TURN_SCOPE` |
| **final state dump** | 一轮结束后把终态落成结构固定、可离线重判的归档 | **`TODO(R8)`：还没有** |

`restore_snapshot_state()` 当前只认 `source_connected` 与 `catalog_observed`。
**声明了别的一律在启动前拒绝**（`validate_snapshot()`，2026-09-15 补）：
未知字段、类型不对、未知子字段、`history` 非空、`resume_tick`、未知 `stimulus.kind`
都会抛 `SnapshotUnsupported`，且发生在 `RUNS.begin` 与 `clear_*` **之前** ——
清完再失败等于毁掉上一轮现场还什么都没测。拒绝理由通过 HTTP 400 原样返回页面：
`{"error": "state.contacts 还原器不支持；当前只支持：catalog_observed、source_connected"}`。
只有这一个异常类的消息可外传，其余异常仍只返回类型名，避免把上游错误串带出去。

### 第一阶段：治理状态恢复后的单次继续执行

还原、校验、停止、取证由确定性代码完成；下一步做什么仍交给正常 Hermes。

| 必须支持 | 第一阶段覆盖 |
|---|---|
| 联系人与角色 | 已登记、已换人；**联系信息与审批资格分别恢复** |
| 档案与口径 | 观测、推断、确认、否定，**及其依据** |
| 票据、决定、任务 | 等待、获批待恢复、过期、已消费、已完成 |
| 时间与既往动作 | 执行窗口、催办时间、已有通知及任务关联 |
| 起点自验 | 实际恢复结果与声明一致，引用关系能连通 |
| 终态证据 | 起点基线、终态、期间副作用、停止原因，可离线重判 |

**明确暂不支持**：完整历史会话、任意源环境、物理 lake 快照。
依赖这些的 Snapshot **必须拒绝启动**。

边界要说到这个精度：「已登记联系人后会不会重复登记」第一阶段就能测；
「长对话之后会不会忘掉联系人」不能据此宣称覆盖 —— 那要历史会话。

### 历史决定要能恢复，但分三段看

`decisions` 的约束是**运行中 Agent 不能写**，不是"还原器不能恢复"。
[`runs.resumable()`](../services/runs.py) 直接 `JOIN decisions ON d.approval_id = r.waiting_on`：
没有历史决定行，「callback 已写决定、cron 尚未恢复」这个起点**永远构造不出来**，
而那正是恢复类测例的主形状。

| 阶段 | 规则 |
|---|---|
| 恢复前 | 独立还原器恢复历史票据、决定及其关联，**记录来源** |
| 运行中 | 新决定仍只能由独立 callback 产生，Agent 权限不变 |
| 判分时 | 历史决定属于**基线**，不能算成本轮新完成的审批 |

现在 `restore_snapshot_state()` 里"只恢复已连接结果、不补造票据和决定"是**连接起点**
的正确做法（那个 case 本就不该伪造一次审批），**不是通则**，不要推广到所有 Snapshot。

### 三个容易混的"差不多"

- **`_WRITERS` 可以参考，不等于照搬就完成。**
  [`tests/behavior_fixture.py`](../tests/behavior_fixture.py) 那套词汇本身也**没有联系人恢复**；
  它的 `mails` 写的是发件记录文件，不是 Hermes 邮箱与会话。真链路这边还要处理
  任务与票据互相引用、时间有效期、动作指纹，以及 Postgres 的权限差异。
  两层能力倒挂成立，但"便宜层有这些字段"不等于真链路已有还原实现。
- **"真采集"不等于"恢复历史档案"。**
  `catalog.observe()` 重新观察**现在**的源库，能构造"刚刚建档"，
  构造不出"昨天的档案还是旧结构、今天源库已经变了"——后者必须同时保留旧档案与新源状态，
  而那正是闭环 B（巡检 / SchemaDrift）要测的局面。
- **新判据写 Python 不是问题。** 合理目标是：新案例**组合已有判据、只改数据**；
  新增一种判断能力时可以新增独立取证器与判分函数；Runner 不必理解"销售冠军""清洗发布"
  这些业务类型。真正的问题是业务判分耦合在 `services/demo_ui.py` 里，
  不必追求"任何新判据都零代码"。

### 优先级

1. ~~**未知字段、错误类型、不支持的依赖 —— 启动前报错。**~~
   **已完成**（2026-09-15）：`validate_snapshot()` 校验声明、`snapshot_mailbox()`
   校验依赖（例如凭证 Case 要 DSN），两道都在破坏性动作之前；
   `tests/test_snapshot_integrity.py` 钉住「拒绝时一个清空动作都没发生」。
2. **挑一个恢复闭环成套补齐**（还原 ＋ 自验 ＋ 取证）：
   「已获批待恢复 → 正常 cron 唤醒 → 原动作只执行一次」，同时做**过期票反例**。
3. **固定每轮证据格式与独立判分**，再谈重复运行与失败集合比较 ——
   单有 final dump 不足以证明重复试验的起点一致。
4. **按下一批验收补**历史会话、源环境变体、lake。
   **顺序取决于下一批要验收什么**：如果下一批是 Bronze / Silver 交付，
   lake 恢复就是前置依赖，不能固定排在最后。

## 模型实际得到什么

- 系统指示、工具定义、Skill：正常运行时原有内容。
  全新会话可能触发 Hermes 自带的首次使用介绍；它照常保留在实际输入记录里。
- `inbound_mail`：仅投递一封当前业务邮件，走 GreenMail SMTP → Hermes IMAP。
- `resume_tick`：不投递邮件，不编写提示；恢复已有任务状态后，等待正常 cron
  monitor 发现到期、审批完成等变化。当前内置三个 Case 都是邮件触发，不能把它们
  报成无人来信的主动通知实测。
- 前置业务事实进入数据库，供正常工具查询。当前支持连接状态、真实采集的表档案。
  尚未实现任意任务/session/memory 的完整恢复；有非空 `history` 的 Case 会拒绝启动，
  不把旧信重新投成新刺激。`resume_tick` 只适用于现有恢复器确实能恢复的状态。

`expected_outcome`、Case 说明、标题、终点、`tool_scope` 留在观察器。Agent 容器
不挂载 `demo/`、`tests/` 或观察器 `runs.json`。旧 `tool_scope` 与 `max_turn`
只保留作旧材料记录，不参与模型权限和停止判断。

测试专用设置仅为隔离数据库/邮箱/session、控制启动与固定停止时间、记录请求。
状态恢复完成前网关和 cron 不启动。所有 Case 共用 `DEMO_WINDOW_SECONDS`
（默认 900 秒，含模型健康检查和启动）；控制文件仅含随机 run id 与 deadline。
预期结果不影响是否继续执行；窗口中观察到好结果也不提前停或立即宣告通过。
当前 demo overlay 另有 `CLAW_MAX_TURN`（默认 40），它限制全局工具调用次数，
没有按 Case 挑选工具，也不读取 Case 文件。实际值与用量同时显示在页面；本次
实测保留该配置，未触及次数上限，实际由 300 秒窗口关闭。

**第二道停止是硬 turn**（`CLAW_MAX_TURN`，部署配置，默认 40）：`pre_tool_call`
数这一轮已经动手几次，**被 block 的调用也算**，到线后一律不放行并回一句
「这是外部设定的停止点，不是你做错了什么」。计数范围是这一轮的 run id
（`CLAW_TURN_SCOPE`，entrypoint 传，不经过控制包那条只许过 `run_id + deadline`
的边界）。上限**不来自 Snapshot 字段** —— 容器不挂载 `demo/`。
时间窗保证「不会一直跑」，硬 turn 保证「不会在窗口里把同一堵墙撞二十次」，
两道都要有：时间到了不代表它做过事，动作数够了也不代表时间到了。

## 邮件怎么触发

| 路径 | 触发 | 谁决定内容 |
|---|---|---|
| 当前业务来信 | Hermes IMAP 收到邮件 | 模型按正常上下文决定工具调用/回复 |
| 后台推进 | 正常 cron 发现到期任务、审批结果等状态变化 | 正常 monitor 与模型 |
| 审批通知 | 工具调用被正常审批门禁挂起 | 系统模板 |
| 连接结果通知 | Connector 真正完成连接验证 | 系统模板 |

系统模板发出的信不证明模型自主写了信。判断主动发信须核对模型请求中的工具
调用和真实收件箱记录，不能仅数邮件封数。

## 如何审计

页面「查看实际模型输入与运行配置」或 `GET /api/inputs` 返回当前轮证据：

- Hermes 原生 `HERMES_DUMP_REQUESTS` 保存的完整请求：system/messages/tools 等。
- 只读 API hook 记录请求 id、session、平台、模型、输入哈希及响应/错误事件。
- 原生请求文件归档到独立 `demo_input_audit` volume，网关重置不删除历史轮。
  凭证和审批链接脱敏；哈希来自 hook 接收到的原始内容，脱敏副本不能直接重算它。
- 外部停止写入独立 `completion.json`，包含停止原因、时间和进程退出码，
  网关或 Docker 重启后仍能确认这一轮如何结束。
- 记录缺失、尚有请求未结束、原生请求与 hook 数量不符、记录错误均为
  `inconclusive`；检测到测试指示泄漏直接失败。完整记录不是自动证明所有业务判断正确。

判分只用外部证据。关联确认必须匹配同一资产/关系和真实 `approve` 决定；拒绝票、
别的关系的票、单独候选、任意一封问候邮件不能让它通过。自由文本中的语义确认或
正确采用外键仍需人工/独立语义核验，缺证据保持未判定，不能为了全绿放宽条件。
联系人 Case 的邮件内容也须由独立审阅者核验，审阅结果绑定邮件内容哈希后记录在
观察器 `verification` 的 `mail_content_review` 项；它不进入 Agent 的状态或提示。

`tests/run_behavior_case.py --driver live` 仍是旧的 `hermes -z` 单次模型测试，
使用独立 SQLite/outbox，不覆盖真实 IMAP/cron/session 链。它与本页的
`hermes_gateway` Snapshot 证据分开记录，旧结果不自动升级为新测试的通过证据。

## 回归

`tests/test_snapshot_integrity.py` 修改隐藏答案/工具名单，验证输入和生产门禁不变；
`tests/test_demo_snapshot_terminal.py` 验证隐藏终点不影响到期任务的 monitor 输出。
另验证无额外历史刺激、日志脱敏、缺失证据、正常配置复用和错误判分反例。
这些是确定性检查；真实服务与模型的结果另记，不与单测混报。
