## 3. 关键决策与理由

### 决策 1：不自写 Agent loop —— 只写一个 Hermes plugin ⭐ 最重要

**发现**：Hermes Agent（`NousResearch/hermes-agent`）是 MIT 开源 Python 框架，不是托管服务。
它已经自带：

- `agent/conversation_loop.py` —— 完整 tool-calling loop
- **`pre_tool_call` directive hook** —— 可 `block` / `modify`，且超时 **fail closed**
- `tools/approval.py` —— 人工审批 gate（cli / gateway / smart 三种 surface）
- `plugins/platforms/email/adapter.py` —— Email 收发适配器
- `canonical_tool_args` / `ToolCallSignature` —— 动作指纹，可直接复用
- session 持久化、`budget_config`、`checkpoint_manager`、MCP 客户端

**影响**：readme 第 4 节原本计划「自写 loop 骨架 + 六个 hook」，现收缩为**写一个 plugin**。
省下的工作量应投入到数据侧（Connector Service、DQ、Policy Sync）。

**放弃的方案**：自建 loop。理由是会重复造轮子，且 Hermes 的 fail-closed 语义比自己写更可靠。

### 决策 2：异步挂起用 `block`，不用 `approve`

Hermes 的 `{"action":"approve"}` 走它自己的审批 gate，那是**同步**语义（等这次交互）。
我们要跨天挂起，因此改用：

```
无票据 → {"action":"block", "message":"[PENDING_APPROVAL] 已发邮件给 owner"}
      → run 自然结束（进程无需挂着）
      → 邮件回调写 decisions 表
      → 外部事件触发新 run → 重试 → 有票据 → 放行
```

**进程可以死，审批状态在库里。** 比进程内挂起更健壮。

### 决策 3：本机放弃 OpenMetadata，R1–R4 用轻量 `assets` 表

**实测**：开发机 8GB，Docker VM 仅 **3.828GiB**（且用户另有容器占用 2GB 限额）。

| 组 | 估算 | 可行性 |
|---|---|---|
| core（MinIO + Iceberg REST + Trino -Xmx1G） | ~2.6GB | ✅ 可行 |
| governance（OpenMetadata + ES + MySQL） | ~4.5GB | ❌ **超出上限** |

**应对**：R1–R4 本就不依赖 OpenMetadata（只有 R5 的 Policy Sync 需要它作为 tag 来源）。
改用一张轻量 `assets` 表承载 owner / tag / lineage，**保持接口一致**，
R5 时再决定上真实 OpenMetadata 还是换远程机器。

实测占用：MinIO 149.8MiB，Postgres 55.9MiB。

### 决策 4：审批改为两表模型（修正了 readme 原设计的漏洞）

原设计单表 `approvals` + `GRANT SELECT` 给 Agent。**但 Agent 必须能创建审批请求（INSERT）**，
同一张表上就无法阻止它写 `decision` 字段。

改为：

- `approvals` —— Agent 可 INSERT（发起请求）+ UPDATE `used_at`（消费票据）
- `decisions` —— Agent **只有 SELECT**，仅 callback 服务可 INSERT

有效票据 = 两表 join + 未消费 + 未过期。
「Agent 伪造批准」在**权限层面**不可能，不依赖代码正确性。readme 9.4 已同步更新。

## 3.5 R0 范围之外、本轮额外完成的（属于 R1 第 2–3 步）

按第 5 节「先做所有不依赖答案的事」的原则，R1 中不需要外部凭证的部分已提前完成：

### ✅ 审批存储迁至 Postgres 并验证真实列级权限（原欠账 #4）

`infra/init-steward.sql` 建库建角色，`tests/test_grants.sh` **12/12 通过**。
在真实 Postgres 上证明了 Agent 无法：伪造批准、改批准人、延长有效期、
改动作指纹、删除记录、修改决定；令牌重放被 `token_jti` 唯一约束拒绝。

**这一条 SQLite 证明不了** —— 它没有列级权限。

### ✅ 审批 callback 服务（独立进程）

`services/approval_callback.py`，stdlib `http.server`，无 Web 框架依赖。
`services/tokens.py` 用 HMAC-SHA256 自签令牌，不引入 JWT 库。

`tests/test_callback_e2e.py` **11/11 通过**，覆盖完整闭环：

```
Agent 尝试 L3 动作 → 被拦截并落库审批请求
  → 签发 approve / deny 两枚令牌
  → 改 URL 拿 deny 令牌去 approve  → 403（令牌意图绑定）
  → 篡改签名                        → 403
  → 正常点击批准                    → 200，决定落库
  → Agent 重试                      → 放行
  → Agent 再重试                    → 重新挂起（票据一次性）
  → 重放同一链接                    → 409
  → 另一动作点击拒绝                → 进 deny list
```

### 决策 5：SQLite 连接必须用完即关

端到端测试first次跑出 `database is locked`。根因不是并发本身，而是
callback 的 Handler 每个请求新建 `Store` 且从不关闭，连接泄漏持有写锁。

WAL + `busy_timeout` 是必要但不充分的；真正的修复是 `Store` 支持
`close()` / 上下文管理器，Handler 用 `with` 包住。
**生产迁 Postgres 后此问题消失**，但连接管理的习惯要保留。

## 7. 不要做的事

- ❌ **不要自写 Agent loop** —— Hermes 已有，且其 fail-closed 语义比自写可靠
- ❌ **不要用 `{"action":"approve"}` 实现跨天挂起** —— 那是同步语义，见决策 2
- ❌ **不要在本机尝试启动 OpenMetadata 全家桶** —— 实测内存不足，会拖垮机器
- ❌ **不要把审批 callback 和 Agent 放同一进程** —— 列级 GRANT 会形同虚设
- ❌ **不要拉 `latest` 镜像** —— 磁盘仅剩 29GB；本机已有 `postgres:15-alpine`、`minio/minio:RELEASE.2023-03-20`
- ❌ **不要信任 `_sql_guard` 当前的关键字判断** —— 它是占位实现，R3 换 AST 前不要当作安全边界
- ❌ **不要在 HTTP handler 里新建 Store 而不关闭** —— SQLite 会持写锁把 Agent 挡在门外（决策 5）
- ❌ **不要给测试脚本硬编码 `token_jti`** —— 唯一约束会让第二次运行失败
