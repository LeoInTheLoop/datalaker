## 3. 关键决策

### 决策 27：判分器必须体外，与铁律 2 同一条理由

审批 callback 与 Agent 同进程时列级 GRANT 形同虚设；
判分器与被测系统同进程时红线指标同样形同虚设。
`evals/` 只 import 标准库与 psycopg，`evals/test_isolation.py` 把这条断言成代码。
体内的 runner 故意放在 `tests/run_eval_case.py`，两边只走环境变量 + 文件。

### 决策 28：时间当数据处理，不当代码改

升级读的是 `now() - approvals.created_at`，回拨时间戳与真的等了那么久**完全等价**。
考虑过给被测代码注入可控时钟，放弃了：判断发生在 SQL 的 `now()` 里，
进程侧偏移量影响不到它，真做要把所有时间读取抽象一层——为测试改产品结构，方向反了。
副作用是好的：Agent 对 `approvals` 只有受限写权限，**只有 eval 侧动得了时钟**。

### 决策 29：任务活得比进程久，且彼此独立

`pipelines/ingest_table.py` 原来的注释写着「审批点击后由 scheduler 重新拉起」，
但 scheduler 只跑升级和周报，**这条链路在代码里不存在**。
补 `runs` 表后：状态落库、N 条并行、恢复顺序 = 人的响应顺序、一条崩了不牵连另一条、
每条单独调用从不合批。恢复放在 scheduler 而不是 callback：
点击的人只负责给出决定，任务何时被拉起由调度决定。

### 决策 30：清洗分三档，不是两档

按 readme 16.2 逐条对应：只有**去重**是 auto；enum/拼写/类型是 **propose**
（有具体变换但要人批准这条规则）；补空值/改数量级/改日期是 **ask**。
一开始把 propose 混进 auto，eval 当场抓到：`sellers.seller_city` 被自动归一，
而那列根本没人要求动；更糟的是 `lower()` 不折叠音标，
`São Paulo` 洗完仍是 `são paulo`——**规则没修好它声称要修的东西，却已经改了数据**。

### 决策 31：策略由 tag 生成，但先落文件不上 OPA

readme 画的是 OPA。R3 已落地 file-based access control，两者输入是同一份事实
（分类 + owner）。先把「事实 → 策略」做对，换 OPA 时改的是渲染函数不是数据来源。
上来就引入 OPA 会多一个必须一直活着的进程，换不来这一阶段需要的能力。
`TODO(R5)`：需要行级过滤时再换。

### 决策 32：不给护栏开豁免，改成参数化入口

内容型规则要看原始值，而 `query()` 会把无 LIMIT 语句夹到 1000 行、
显式大 LIMIT 又要审批。**没有加 `approved=True`**，而是新开
`connector.sample_rows()`：只收表名列名、自带独立上限、结果不进模型上下文。
与 R3 决策 22（元数据查询参数化）是同一条。

### 决策 33：ground truth 之外的修复不算修错

Olist 的 `sellers.seller_city` 真的有拼写漂移，Agent 修了它。
一开始按「没注入 = 修错」算，False Repair Rate 100%——
等于因为「发现了我们没埋的雷」而扣分。改成：分母只算落在注入范围内的修复，
范围外的另列一栏。

## 4. 踩过的坑

| 坑 | 教训 |
|---|---|
| `sync_state` 表**没有任何建表语句** | R3 手工在 Postgres 建的，SQLite 后端整条同步路径崩在「表不存在」。DDL 必须跟代码走 |
| `save_state` 只写了 Postgres 一路 | `get_state` 早就分了岔，写入侧没跟上。本地默认 SQLite，于是同步永远不通 |
| 确认信发失败**打崩 callback** | 异常冒到 handler 外，HTTPServer 直接断连，看着像服务挂了，实际只缺一个邮件依赖。通知失败必须被吃掉 |
| `NOTIFY_CHANNEL` 环境变量压不住 `.env` | `get()` 只读 `.env`，测试无法临时切通道。进程环境必须优先 |
| `list_tables` 不限 schema | eval 的脏 schema 污染源清单，同名表重复出现 |
| `n_live_tup` 重启后归零 | 而「行数估算」是铁律 3 的前提。改用 `pg_class.reltuples` 兜底，未知返回 -1 不是 0 |
| 无序 `LIMIT` 采样有系统性偏差 | 更新过的行在堆尾，采样窗口读前段。8% 的注入一个都采不到 |
| `TABLESAMPLE SYSTEM` 后再 `LIMIT` | 「随机选块 + 只读前段」，偏差原封不动回来 |
| `SYSTEM` 是整块取舍 | 注入行聚在少数几个尾块，没选中就整批全漏。十万行量级改用 `BERNOULLI` |
| `sample_values` 外层没写 LIMIT | 被护栏夹成 1000 行，内容型规则一直只看前一千行 |
| `_reason` 字段写进 `rules.json` | Trino 严格校验拒绝未知字段直接起不来（R3 同款）。理由落旁路 `.why.json` |
| psycopg 把 SQL 里的 `%` 当占位符 | `rolname NOT LIKE 'pg\_%'` 报错，改 `left(rolname,3)` |
| 编辑脚本切片为空 → `str.replace("")` | 每个字符间插一次，`data_tools.py` 涨到 18MB。按周期切回来恢复了，**改文件前必须验证切片非空** |
| 测试依赖共享库里的历史数据 | `审批偏好可统计` 与暂存表快照断言时红时绿。测试要自己准备数据（R3 同款教训又犯一次） |
| 异步发信后立刻断言 | `_notify_async` 在后台线程，直接读 `REC.sent` 是竞态 |

## 6.5 安全发现：网络内部可以匿名冒充任何身份

**问「Agent 是不是真跑在容器里」问出来的。** 答案是不是（`steward-agent`
容器的命令是 `sleep infinity`），而尝试把它塞进去时发现容器里没有 docker CLI，
于是给 `sync._trino` 加 HTTP 路径 —— 一加就撞上了这个：

```
http-server.authentication.allow-insecure-over-http=true
```

它让 8080 上的请求**完全绕过密码认证**。R3 的缓解是「不把 8080 映射到宿主机」，
但 compose 网络内部照样敞着。实测（从 scheduler 容器）：

```
匿名 + X-Trino-User: analyst  →  ['***']            遮蔽生效
匿名 + X-Trino-User: admin    →  ['13800001111']    ← 未遮蔽的真实手机号
匿名 + X-Trino-User: admin    →  SHOW TABLES FROM northwind.public 全列出
```

也就是说 **11.4 的列级遮蔽在网络内部形同虚设**：任何容器都能自称 admin。

修法与连带影响：

| | |
|---|---|
| 配置 | `allow-insecure-over-http=false`，8080 匿名从 200 变 403 |
| 宿主机 CLI | 原来连的就是免认证的 8080，必须改走 `https://localhost:8443` + 密码 |
| L0 冒烟 | 同上；注释里那句「容器内走 HTTP，免密码」正是洞的来源 |
| 新断言 | `⚠️ 网络内部也不能匿名冒充身份` —— 从容器里探，防它被改回去 |

**连带发现：探活与干活走两条路，迟早静默跳过。** 加认证之后，
`test_clean` 和 `run_all` 里那两条免密码的 `docker exec` 探活开始失败，
于是 19 条断言凭空消失而回归仍然全绿。两处都改成走 `sync._trino`。

## 6.6 LLM 在环：非确定性那半边的数字之前是假的

大 case 原本用一张时刻表模拟 10 个人（`responds_after_days`），
所有人都准时、都同意 —— **于是 16 条线里 15 条完成**，看着很好。
接上 `services/persona.py` 让模型扮演对方之后（`LLM_PERSONA=1`），
同一个 case 只完成 3～6 条。差的那十条不是 bug，是真实世界。

模型给出的摩擦，正好是设计里预设的那几种：

| 实际发生 | 对应设计 |
|---|---|
| 王姐反复回「这不是我管的表」（NOT_MY_SCOPE / DELEGATE） | 兜底路由把无前缀的表全推给她 —— 见下 |
| 王姐正文写了「同意」但**没点链接** | 10.5：门禁只认票据，那条线继续挂着继续升级 ✅ |
| 周经理连着五天「我下周转岗，你找新来的对接吧」 | DELEGATE 是中间态，需要有人去接 |
| 从不回信的吴总监 | 3/6/9 升级 → 第 12 天 ABANDONED ✅ |

### 由此修掉的：审批人解析改成三级

原来只有两级：表名前缀 → 兜底角色。northwind / olist 的表没有域前缀，
**全部落到同一个兜底人身上，而她正确地拒绝了**。兜底本身没错，
错在它是唯一的依据 —— 人一旦确认过归属，就不该再靠表名去猜。

```
① 记忆层记过归属  →  用它（人确认过的事实，最可信）
② 表名前缀能推断  →  用它（确定性信号，但只是约定）
③ 都不行          →  回退兜底（宁可发给上一级，也不要发丢）
```

`tests/test_ownership_routing.py` 13 条，含存储异常时必须回退而不是抛出
（门禁不能因为查不到归属就崩）。

### 判定语义也跟着改了

LLM 在环之后，两条断言原来的写法都不成立：

- **「没有线卡在 waiting」** —— 人不回信时线就该挂着。改成
  「等审批且**超过 3 天**的线必须都在升级链上」，并把 **WIP 排队**
  与**等审批**分开数：前者是队列，不是卡死。
- **「bronze 行数达到下限」** —— 对方大面积不配合时行数当然低。
  改成「凡是拿到批准的都真写进去了」（`bronze_tables == done`）。

两种模式各自 10 条判定全过。**确定性模式留着当回归**（要可重复），
LLM 模式手工跑（有随机性且烧 token）。

## 6.7 批量 eval：155 条注入，加权召回 85.8%

`evals/gen_cases.py` 按数据类型机械枚举产出用例（**不手写**：手写会下意识
只挑自己知道能检出的列，测出来的是「我出的题我会做」）。三个批量 case 实测：

| case | 有效注入 | Recall | Escalation | False Repair | 对照组 |
|---|---:|---:|---:|---:|---|
| olist_raw | 72 | **87.5%** | 100% | 0.0% | ✅ |
| northwind | 69 | **85.5%** | 98.6% | 0.0% | ✅ |
| acme | 14 | **78.6%** | 92.9% | N/A（0 次修复）| ✅ |
| **合计** | **155** | **85.8%** | — | — | 红线全绿 |

按缺陷类型（有效 Recall，分母已剔除「表没进 bronze」与「无规则」）：

```
high_null_rate    100%   unit_outlier      100%   type_mismatch     100%
pk_unique_full    100%   broken_foreign_key 100%
date_before_order  67%   enum_drift         64%   spelling_drift     61%
```

### 从 64.4% 到 85.8%：三处修的都不是「规则不够强」

首轮跑出来是 64.4%，逐一拆开之后发现**大部分不是漏检**：

| 问题 | 性质 | 修法 |
|---|---|---|
| 注入是空操作（值本来就是大写、整列本来就是 NULL） | **注入器不验证自己有没有生效** | 注入前后比列 checksum，没变就如实记成未注入，不计入分母 |
| `type_error` 注在文本列上 | **考题出错**：规则判据是「多数是数字、少数不是」，往人名列塞 `unknown` 数值占比接近 0，规则**正确地不报** | 生成器只往数值列注 |
| `enum_drift` 的 `max_distinct=50` | **规则里一个武断的上限**：大小写漂移跟基数无关，几千个城市名照样会有 | 拿掉上限，改按覆盖行数筛（`spelling_drift` 上的同款 500 早先已拿掉） |

还有一处在判分器：**修复也要按 (表, 列, 缺陷类型) 匹配**。
同一列叠了两条注入时，为 `spelling_drift` 做的清洗被算到同列 `broken_fk`
（`expect=ask`）头上，False Repair 一度报 9.1%。带上类型后是 0.0%。
**这和检出侧那次是同一个错**：只按 (表, 列) 匹配，数字会好看，但不真。

> 剩下的三类（拼写 61% / 枚举 64% / 日期 67%）才是真正的规则弱项，
> 且都集中在「同一列上的第二、三条注入」——与采样覆盖有关，留给下一轮。
