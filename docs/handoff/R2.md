## 2. 本轮的关键设计决策

### 决策 16：Harness 按四支柱重新组织（4.6）

Permission / Tool / Memory / 执行形态。一对比就发现优先级排错了：
**Permission 已做透，但 Tool 是空的、执行形态没实现**，而原计划 R2 先做 IMAP 收信。
没有工具 Agent 什么也做不了，因此入站交互后移到 R3。

### 决策 17：工具准入两层，主防线是「不注入」

原方案把 gate deny by default 当主手段，次优。

```
① 不注入 prompt（主）  Hermes 白名单 → 模型压根不知道有 terminal
② gate deny by default（兜底）→ 兜住幻觉工具名与配置遗漏
```

**理由是成本**：137 个内置工具定义每次请求白烧 1.4–2.7 万 token。
且工具在 prompt 里模型就会尝试，被拦后还会换说法再试。

第二层仍必要：白名单是配置会漏，gate 是代码路径上的强制。

### 决策 18：执行形态是三层，分界是「控制流谁决定」

不是「要不要模型」的二分：

| 层 | 有 LLM | 控制流 |
|---|---|---|
| 纯函数 | ❌ | 代码 |
| **Pipeline** | ✅ | **代码**（步骤写死） |
| **Agent loop** | ✅ | **模型** |

清洗 Pipeline 内部也调模型（判断异常类型那步），但不会自己决定
「要不要顺便看看另一张表」。**Pipeline 挂在总 Agent 下面。**

收益：Pipeline 的 LLM 调用次数可预估、可做 golden test、失败能定位到步骤。
Agent loop 不可预估——这正是 5.6 预算兜底存在的理由。

### 决策 19：Pipeline 用 LangGraph，但边界必须划清

| 归 LangGraph | 归本项目 harness |
|---|---|
| Pipeline 内部步骤流转 | **跨天的人工审批挂起** |
| 单次执行的中断恢复 | **审批状态的权威来源** |
| | 工具准入与门禁 |

**不使用 LangGraph 的 `interrupt`**：它为「同一 run 内暂停等输入」设计，
我们的挂起是跨天、跨进程、带签名令牌的。正确做法是
gate 返回 PENDING 后 **Pipeline 正常结束**，点击后由 scheduler 重新拉起。

约束：**只用 `langgraph` 的图与 checkpoint，不装 `langchain` 主包**——
它的 Agent/Chain/Memory 抽象与已有 harness 重复。

### 决策 20：记忆收窄为两类具体的

- **资产关联**：表间关系、常一起查询、血缘
- **审批偏好**：谁批得快、谁要更多依据、谁总拒某类、什么时段回复率高

后者让交互从「一个模板发所有人」变成「按人调整」，
**数据全部来自已有 approvals/decisions/events，只需统计不需新采集**。

语义检索价值较低，推到 R4。

### 决策 21：text2sql 都不放，拆成参数化工具

skill / workflow / graph **都是编排，不是安全边界**。
边界只有工具签名、gate 和 Connector。

参数化的第二个好处：审批邮件里一眼可读——
`ingest_table(FIN.monthly)` 比一段 SQL 清楚得多，
而审批人每周只有 2–3 小时，**读不懂就只能盲批**。

## 3. 踩过的坑

| 坑 | 教训 |
|---|---|
| WIP 按解析后的真人计数，永远匹配不上 | `approvals.approver` 存的是**角色**（10.4）。且换人时在办事项不该被清零 |
| 新方法只加在 SQLite `Store`，`PgStore` 没有 | 容器跑 Postgres 直接 `AttributeError`。**双端实现必须同步补** |
| Postgres 返回 `Decimal`，除以 float 报错 | 跨方言时注意类型 |
| 周报绕过 Store 直接写 SQLite 语法 | 方言差异必须封装在 Store 内（`completed_since` / `ledger_summary`） |
| 升级一次只升一级 | 停机数天后重启不该一小时升一级慢慢追，要**一次升到位** |
| `${VAR:?}` 在未激活 profile 里照样求值 | compose 解析整个文件，必需变量会阻塞其他 profile |
