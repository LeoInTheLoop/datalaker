**阶段目标**：从「有治理约束、能接入和处理数据的 Agent」，走到
「持续理解企业数据、维护这份理解、并发现跨表价值的数据管家」。

## 1. 这一阶段在补什么

R5 结束时能做的事：接入源、落 bronze、按人定的口径洗成 silver、
全程有审批和血缘。**这些都是「做一次」的能力。**

缺的是「持续」那一半：

```
做一次          持续
接进来      →   知道它后来变了没有
问到口径    →   知道这条口径什么时候不再成立
能 JOIN     →   知道这两张表为什么能连、连接后的结论何时失效
```

用一句话概括缺口：**工具能搬表、能执行 JOIN，但没有维护
「这些表为什么能连、该怎么连、连接后的结论什么时候不再可信」。**

## 2. 现状核实（开工前逐条验过，不是推测）

| 论断 | 核实结果 | 证据 |
|---|---|---|
| 联系人有存储、无工具 | ✅ 属实 | `role_assignment` 表齐全；`assign_role()` 的**非测试调用点 0 个**（只在 `test_ownership_routing` / `run_scenario_live` / `run_case_full` / `test_r2_harness`）。演练里「负责人换了」是脚本替 Agent 做的 |
| 改审批权被禁 | ✅ | `modify_role_assignment` = `(Level.L4, None)` |
| metadata 仍回源库 | ✅ | `describe_asset` → `connector.describe_table` → `_meta_exec`；`data_tools.get_table_metadata` 同路 |
| 口径只存当前值 | ✅ | `asset_semantics` 有 `UNIQUE(asset, key)`，`remember()` 是 UPSERT |
| `remember()` 不更新 `source_item` | ✅ **是个 bug** | 两个后端的 `DO UPDATE SET` 都只更新 value/confirmed_by/confirmed_at → **新口径配旧出处** |
| 指纹只含列名+类型 | ✅ | `sync._schema_hash` = `[[name, type]]`；主外键、可空性、默认值全不覆盖 |
| 没有元数据巡检 | ✅ | cron 只有 `claw-resume` / `claw-escalate` / `claw-weekly-report` |
| `memory.py` 没接进主链路 | ✅ | 非测试调用点只有 `data_tools.py:365` 一处 |

**两处要修正外部评审的说法**：

1. **「缺少完整的修订历史」——已经有了一半。** R5 加的 `asset_provenance`
   台账在 `semantics_defined` 事件的 `detail` 里存了当次的 value 和
   confirmed_by。所以口径的**变更历史是有的**，只是分散：当前值在
   `asset_semantics`、变更史在台账。真正缺的是推断状态、失效条件、适用版本。

2. **推断与确认不是「完全没区分」，是「区分得太弱」。**
   `memory.infer_asset_links()` 把外键推断写进 `asset_semantics`，
   靠 `confirmed_by="system:fk_inference"` 这个**字符串前缀**跟人工确认区分。
   而 `UNIQUE(asset, key)` 意味着人一确认就把推断**覆盖掉** ——
   之后再也看不出「系统曾经推断过什么、人为什么改了它」。

## 3. 三条闭环

每条都给**可验收的判据**。没有判据的目标会变成「感觉做完了」。

### 闭环 A：认知可复用

> **验收**：`reset_live.py` 之后起一个全新会话，**不访问源库**，
> 它能准确说出某张表的结构、负责人、口径，并且**区分哪些是推断、哪些是人确认的**。

现在做不到：`describe_asset` 每次回源库；推断与确认混在一张表里。

**要建的：`asset_catalog`（独立治理库里，与口径/审批/台账并列）**

按三类内容**分列存**，因为它们的写入权限和失效规则不一样：

| 类别 | 内容 | 谁能写 | 失效条件 |
|---|---|---|---|
| 观测事实 | 列名、类型、主外键、可空性、采样统计 | **只有 Connector**，模型不能改成另一份「事实」 | 源库 schema 指纹变了 |
| 模型推断 | 「两套系统的客户编号可能指同一实体」 | 模型可新增、修订，**必须带依据和待验证状态** | 依据的事实变了 / 被人否定 |
| 人工确认 | 客户对应关系、收入口径、退款归属 | 经审批写入，记确认人、证据、适用版本 | 人改口径 / 适用版本过期 |

**关键设计点**（这几条是踩过的坑换来的）：

- **推断不覆盖事实，确认不覆盖推断。** 三类各自成行，不共用
  `UNIQUE(asset,key)`。人确认之后，原来的推断仍然查得到 ——
  「系统曾经猜错过什么」是下次少犯错的依据。
- **每条带 `status`**（observed / inferred / confirmed / refuted）
  和 `evidence`（依据什么）。`trace_asset` 输出时必须**标出来**，
  不能把推断说得像事实 —— R5 实测过一次「查不到它就会猜」，
  猜出来的答案（postgres 超级用户）比不答更糟。
- **顺手修 `remember()` 的 `source_item`**：UPSERT 时一起更新，
  否则新口径配旧出处。

**改动面**：`approvals.py` 加表 + 两个后端方法 · `init-steward.sql` 同步 ·
`describe_asset` 改成先读档案（带「取自 X 时刻的快照」）· `trace_asset` 标类别 ·
`connector` 采集后写观测事实。

---

### 闭环 B：认知会更新

> **验收**：在源库上改一个字段（加列 / 改类型 / 删外键），
> **巡检能发现**，指出哪些旧结论因此失效，并生成复核任务给对应负责人。

现在做不到，而且有一条**认知上的纠正必须写在这里**：

> **读取自己的旧认知可以减少访问源库；但发现源库变化，
> 必须有新的外部观测。**

档案只能省掉重复访问，**不能替代观测**。以为存了档案就「知道」源库变了，
是这条闭环最容易犯的错。

**现在为什么发现不了**：

- `sync_table` 里比指纹，但**不触发同步就不会走到那条路径**
- 指纹只含列名+类型 —— 主外键、可空性、默认值变了都发现不了
- `check_freshness` 只看「距上次同步多久」，**不代表检查过源库变没变**
- 没有任何一个 cron 作业在做元数据巡检

**要做的：一条巡检链**

```
定期轻量采集（只读 metadata，不读数据）
  → 与档案里的观测事实比较
  → 变了：标记受影响的推断与口径为「待复核」
  → 生成复核任务，发给该资产的负责人
  → 人确认后更新档案，并把受影响的 silver 标记为需重洗
```

**关键设计点**：

- **走 monitor 作业**，与 `claw-resume` 同款：便宜脚本先跑、
  按字节哈希输出、没变就不点模型。巡检本身不该烧 token。
- **指纹要扩**：列名、类型、可空性、主键、外键。现在只有前两项。
- **口径改了要建待办。** 现在 `define_semantics` 只在返回值里提醒
  「旧数据要重洗」，没有任何机制保证那件事会发生 ——
  提醒一句话和建一条待办，差别就是「会不会被忘掉」。
- **巡检发现的是「事实变了」，不是「该怎么办」。** 后者要问人。

---

### 闭环 C：关联产生价值

> **验收**：挑两套**没有显式外键**的系统（如 `acme.crm_customer` 与
> `olist_raw.customers`），完成实体对应确认，回答一个**单表答不了**的问题，
> 并核验答案。

这是最终目的，也是最难的一条。前两条是它的前提。

**现在有什么**：`describe_asset` 能给外键推断出的 join 路径，
`sql_query(plane=lake)` 能执行 JOIN。**都只覆盖「源库自己声明了外键」的情况。**

**跨系统没有外键。** 这时候「能不能连」是业务判断：
两个 `customer_id` 是不是同一个人，只有业务知道。

**要做的**：

1. **候选发现**（模型推断）：列名相似、值域重叠、基数匹配 ——
   产出**候选**，落进档案的 inferred 层，**带证据**（重叠率、样本）
2. **人确认**（L2）：把候选连同证据发给负责人，批了才成为 confirmed 映射
3. **用映射回答问题**：JOIN 走 lake，结论要记**依赖了哪些数据版本**
4. **核验答案**：抽样对照、或用另一条路径交叉验证 ——
   **答案对不对，不能只看 SQL 跑通了**
5. **被否定的假设也要留**（refuted + 原因）：避免下次再猜同一个错

**关键设计点**：

- 候选发现**只在 lake 侧做**（铁律 3：源系统禁关系展开）
- 「结论依赖哪些数据版本」要记 —— 否则源变了之后，
  旧结论仍然被当成有效的，那是最贵的一类错

## 4. 顺序与理由

**A → B → C，不要并行。**

- **A 是另外两条的前提**：没有档案就无从比较变化（B），
  也无处记录「为什么能连、依据是什么」（C）。
- **B 依赖 A 的基线**：拿什么跟「现在的源库」比？比的就是 A 存下来的观测事实。
- **C 依赖 A 的三层结构**：候选是 inferred、确认是 confirmed、
  否定是 refuted —— 没有那三层，C 的产出没地方放。

A 的验收最干脆（新会话不碰源库也能说清楚），适合先做。

## 5. 不要做的事

- **不要把三类内容混进 `asset_semantics`。** 它现在就是混的
  （`system:fk_inference` 前缀），而 `UNIQUE(asset,key)` 让确认覆盖推断 ——
  这正是要改掉的东西，不要在上面继续加字段。
- **不要用「档案有了」代替「观测过了」。** 见闭环 B 那句纠正。
- **不要让模型改观测事实。** 它可以推断、可以提议，但「源库里到底有什么」
  只能由 Connector 采集写入。模型能改事实的那一刻，这套档案就不可信了。
- **不要在源库上做候选发现。** 值域重叠、基数统计都是重扫描，铁律 3。
- **不要把 `trace_asset` 的输出写成「事实」的口吻。** 推断就标推断。
  R5 实测过一次它把猜的答案说得斩钉截铁（postgres 超级用户），
  那种错比「无档」危险得多。

## 6. 顺带欠的账（不属于三条闭环，但会挡路）

1. **指纹规则变更 = 存量在途审批全废。** 改 `IDENTITY_KEYS` 或
   `action_hash` 之后，旧票据的哈希是用旧规则算的，新代码查不到 ——
   表现是「人批过了但恢复时又发一份新审批」。开发期靠手动重算，
   **生产需要一次迁移**。做闭环 A 时如果动到指纹，必须先还这笔。

2. **枚举口径靠正则从自然语言里抠。** `test_silver_usable` 用
   `\b[A-Z][A-Z_]{2,}\b` 从「统一成全大写，枚举只允许 PAID / PENDING /
   UNPAID / VOID」里抠出枚举 —— 换个写法（小写枚举、中文值）就抠不出来，
   而那时这条断言会**静默跳过**而不是报错。闭环 A 建档案时，
   `define_semantics` 应该有结构化的 `allowed_values` 字段，
   而不是让机器去解析自然语言。

3. **「谁有权批准」这一层不存在 —— 现在「有权」等于「收到了信」。**
   （2026-09-06 核实，用户点名的欠账，**明确放到后面做**）

   现在的链路是：`resolve_approver_role` 三级解析出角色（人确认过的归属 →
   表名前缀推断 → 兜底粗粒度）→ `resolve_role()` 换成人 → 发信 →
   令牌的 `who` 字段签的就是那个人 → callback 校验**签名、意图、一次性**，
   然后落库。

   **中间没有任何一层在问「这个人有权批这件事吗」**：
   `decide()` 只校验连接是不是只读、decision 取值合不合法；
   `grep can_approve|authorized|has_authority` 在门禁与 callback 里**一处都没有**。

   所以角色解析一旦兜错（比如域推断不出、回退到上一级），
   那个人收到信、点了链接，审批就**照样生效** —— 系统没有任何机制
   分辨「他是对的人」和「信恰好发给了他」。

   **为什么现在还跑得下去**（别把这些当成授权校验）：
   - 双重确认：确认信只发到 approver 的**注册邮箱**，转发链接给别人点不了
   - 令牌一次性 + 72h 过期 + jti 唯一约束防重放
   - 审计轨完整：`decisions` 里记的是令牌里的 `who`

   这三条挡住的是**冒用**，挡不住**授权本身错了**。

   **做的时候怎么拆**（外部评审的分法，我认同）：
   - **登记类**（姓名、联系方式、负责的业务范围）：Agent 可自主登记，
     保留来源 —— 这部分归闭环 A 的档案，`confirmed` 层
   - **审批权本身**（谁能批 L3、谁是这个资产的 owner）：
     Agent **只能提议**，由已有权的人确认，再经**独立入口**生效。
     `modify_role_assignment` 现在是 L4（永不自动），那个定位是对的，
     不要为了方便把它降级 —— 它是铁律 2 在角色维度上的对应物。

   **先决条件**：得先有「谁能批什么」的模型（角色 × 动作级别 × 资产范围），
   而那张表现在不存在。`role_assignment` 只回答「这个角色现在是谁」，
   不回答「这个角色能批什么」。

## 8. 闭环 A 完工记录

**验收判据（§3 A 原文）**：新会话不访问源库，能准确说出某张表的结构、
负责人、口径，并区分哪些是推断、哪些是人确认的。

**怎么验的**：`tests/test_catalog.py`，50 条断言。关键一条不是「数一数
访问了几次源库」，而是**把 `connector._meta_exec` 换成直接抛异常** ——
源库访问不了还能答得出来，才叫真的不依赖它。两个后端各跑一遍：

| 环境 | 结果 |
|---|---|
| SQLite（`/tmp/dl_catalog_test.db`，docker core 起着） | 50 passed, 0 failed |
| Postgres（`steward` 库，`agent_role` 账号） | 50 passed, 0 failed |
| 全量回归 `tests/run_all.sh`（HERMES + core + mail） | ✅ 全部通过，跳过 2 项：Phoenix 未启动、gold 为空 |

### 建了什么

**`asset_catalog`**（`approvals.py` DDL + `init-steward.sql`，parity 测过）。
三类内容按 `status` 分行存，append-only，取代关系记在 `superseded_by`：

| status | 谁写 | 入口 |
|---|---|---|
| observed | 只有 Connector | `catalog.record_observed()` / `record_foreign_keys()` |
| inferred | 推断（模型、外键规则） | `catalog.record_inference()`，**evidence 必填** |
| confirmed | 人确认 | `catalog.confirm()` |
| refuted | 被否定的假设 | `catalog.refute()`，**留着不删** |

取代规则在 `_SUPERSEDES`：observed 只取代 observed —— 源库多一列不代表
人定的口径失效，那是两码事，失效判断留给闭环 B 显式做。

**观测层的边界在哪**：不在数据库权限（采集与 Agent 共用一个账号，拦不住），
在**工具签名** —— 没有任何工具接受 `status` 参数，也没有任何工具调
`record_observed` / `catalog_put`。这条有静态断言守着，下一个人加进去就红。

### 改了什么

| 位置 | 改动 |
|---|---|
| `services/catalog.py`（新） | 档案的读写与呈现；`observe()` 是唯一碰源库的函数 |
| `services/connector.py` | `describe_table` / `list_foreign_keys` **采集即建档**；落档失败吞掉，不影响查询 |
| `describe_asset` | 先读档案、读不到才回源；输出报快照时刻；加 `refresh` 参数；每条标［观测］／［推断］／［已确认］ |
| `trace_asset` | 口径按状态分标；新增结构档案与「推断／否定」两段 |
| `services/memory.py` | 外键推断改落 inferred 层；`related()` 先读档案、回退存量 `asset_semantics` |
| `define_semantics` | 新增结构化 `allowed_values`（§6.2 那笔账） |
| `test_silver_usable` | 优先读结构化枚举；抠不出来的**如实报条数**，不再静默跳过 |

### 顺手修的三个 bug（都不在原计划里）

1. **`remember()` 新口径配旧出处**（§2 点过名）：两个后端的 `DO UPDATE`
   都不更新 `source_item`，追溯时指向一份根本没提过这条口径的审批。已修。
2. **PG 后端的 `remember()` 根本跑不通**：`asset_semantics.confirmed_at` 是
   `DOUBLE PRECISION NOT NULL` 且无默认值，而 INSERT 压根没给它、UPDATE 又
   往里塞 timestamptz 的 `now()` —— 新行必然 NOT NULL 违例。**也就是说
   Postgres 上的口径沉淀一直是坏的**，演练跑在 SQLite 上所以没暴露。
3. **PG 上 `trace_asset` 全瘫**：它用 `hasattr(st.db, "execute")` 判后端，
   而 psycopg3 的 Connection **也有** `.execute` —— 于是 Postgres 走进
   SQLite 那条路，`?` 占位符抛错，被外层吞成一句「读不到治理库」。
   改成按后端类名分派（`catalog._semantics_rows`）。

> 三条里有两条是「只在 Postgres 上坏」。演练和大部分测试跑 SQLite，
> **两个后端的差异不会自己冒出来** —— 加了新方法就该两边各跑一遍。

### 留下的账

- **`sync._schema_hash` 没动**，仍然只覆盖列名 + 类型。档案里的观测事实
  已经是五项全的（列、类型、可空性、主键、外键），闭环 B 的比较基线用它，
  不必改 `_schema_hash`；真要改，先还 §6.1 那笔存量票据迁移。
- **`asset_semantics` 仍是口径的当前值存储**，门禁（`resolve_approver_role`）
  和清洗都读它，没动。档案只负责把「谁定的」翻译成推断／确认。
  两处存储并存是有意的，不是没改完 —— 但**闭环 B 要碰失效标记时得决定
  住在哪一边**，别两边各标一次。
- **PG 侧 `asset_catalog` 的写权限没细分**：`agent_role` 能写全部四层。
  边界靠工具签名，DDL 里留了 `TODO(R6)`。采集若拆独立账号，改成列级 GRANT。
- **验收侧的枚举正则还没删。** 写入侧已经不用提取了 ——
  `define_semantics` 的 `allowed_values` 由模型定口径时直接给出。
  但 `test_silver_usable` 里那条 `\b[A-Z][A-Z_]{2,}\b` 还留着兜存量口径。
  **判分器不引 LLM**（判据变成运行时生成的，同一份数据不同天可能不同结论，
  而失败也分不清是数据错还是抽取错 —— 与「判分器不许 import 被测代码」
  同一条原则），所以删它的正确做法是**一次性回填**：用模型把存量
  `normalize_rule` 补上 `allowed_values`，然后删掉兜底分支。
  存量只有个位数，值得做。在那之前抠不出来的会报条数，不再静默跳过。
- **存量 PG 治理库里还有 12 行 `key='links'` 的旧推断**（写在
  `asset_semantics` 里，`system:fk_inference`）。新代码不再往那写，
  `related()` 会回退读到它们。不清理 —— 那正是「存量库升级不该丢东西」
  这条路径的活样本。
