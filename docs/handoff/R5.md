## 1. 这个项目在做什么（不读历史也能懂的版本）

**数字员工形态的数据管家。** 它不是 ETL 工具，也不是 BI：它是一个会发邮件问人、
会等人回复、会被审批挡住的 Agent，在自己的 lakehouse 里整理出一份可信数据，
顺带把「谁能看哪些列」也理清楚。

三件事定义了它，缺一件这个项目就没有卖点：

1. **限制不靠模型自觉。** 所有约束（工具分级、审批票据、动作指纹、SQL 护栏、
   预算、WIP）都实现在 Hermes 的 `pre_tool_call` 钩子里。不写进 system prompt。
   ——因为限制一旦依赖模型听话，就永远证明不了「Agent 绕不过」。
2. **Agent 写不了「决定」。** 审批 callback 是独立进程 + 独立数据库账号，
   `decisions` 表对 Agent 只有 `SELECT`。同进程的话列级 GRANT 形同虚设。
3. **它会等人，而且等很久。** 一条线可能是：发现表 → 找 Owner → 发邮件 →
   等 8 小时 → 回复 → 请求审批 → 等 1 天 → 恢复 → 落 bronze。
   同时并行十几条，各自挂在不同的人身上。所以状态必须在库里，不能只活在进程里。

### 数据怎么流

```
源系统（只读、禁 join、限流）
   └─ ingest_table (L3，要 Owner 批) ─► iceberg.bronze   原样落地
        └─ apply_cleaning_rule (L2，要 Steward 批) ─► iceberg.silver  原值留 <列>_raw
             └─ publish_gold (L3) ─► iceberg.gold   对外；没分类不发布、_raw 不出去
                  └─ grant_read (L3) ─► rules.json   谁能进来；看到什么由分类决定
```

### 人怎么参与

```
门禁拦下 ─► 发审批邮件（两枚一次性签名链接）─► 人点链接
    │                                              │
    │                                    独立进程写 decisions
    │                                              │
    └─ 记「这条线在等谁」进 runs 表 ◄──────────────┘
                │
        cron monitor 发现有决定了 ─► 唤醒 Agent 再调一次工具
```

**正文里写「我同意」不算数**，必须点链接 —— 防的是转发链接被误点，
以及「邮件正文可以伪造」这件事本身。

## 2. 程序形态（重排之后）

设计文档在 [docs/restructure.md](../restructure.md)。四层，由内向外：

| 层 | 是什么 | 在哪 |
|---|---|---|
| **lakehouse** | Trino + Iceberg + MinIO。**Claw 挂掉它仍是完整数据产品** | `infra/`（compose `core` 组）|

| **Hermes + claw 插件** | **主程序，就是 Claw 本体**。工具 / 门禁 / cron / 系统提示都挂在它上面 | `.hermes/plugins/claw/` |
| **监控层** | 起停 Hermes、卡预算。**还没做**（M6） | `ops/claw-status.py` 只有只读面板 |

### claw 插件挂了什么

| 挂载点 | 干什么 | 能否否决 |
|---|---|---|
| `pre_tool_call` | 门禁：分级、票据、指纹、deny list、SQL 准入、预算、WIP、参数级禁令 | ✅ **唯一能否决的** |
| `post_tool_call` | event log + **收尾这条线** | ❌ 观察者 |
| `pre_approval_request` | 发审批邮件 | ❌ 观察者（Hermes 文档明说它不能否决）|

13 个工具全部注册在 Hermes 里，每个都在 `plugins/datasteward_gate/policy.py`
显式声明级别。**未声明 = L4 拒绝**，不是「问一下人」。

### M5 为什么先动记账

驱动反转（脚本从**扮演 Agent** 改成**扮演人**）真正挡路的不是脚本，是这个：

```
旧： 脚本 → runs.RUNNERS["ingest_table"] → Pipeline → gate（PENDING）
                    └── 回来之后由它调 runs.suspend / runs.finish
                        ↑ 这个包装就是脚本伸出去的胳膊

新： Hermes → tool_call("ingest_table") → gate（PENDING，工具 handler 根本没跑）
                                              └── 没有任何人记这条线
```

所以先把记账挪到门禁一侧（`_track_suspend` / `_track_close`），挂在已有的
`_notify_async` 旁边：一个告诉人，一个告诉登记表。**两个都是观察者，
不改变放行与否** —— 铁律 1 禁的是把「限制」散出去，不是禁止记录发生了什么。

### M5 第二步：线的身份是动作指纹，不是会话

第一步落地后立刻暴露下一块石头：**恢复发生在新会话里。** cron 唤醒的
agent run 有新的 task_id，而线是旧会话的 id 记的 —— 恢复成功后
`_track_close(task_id)` 找不到原线，它永远挂在 waiting_human，
monitor 每分钟为它白白唤醒一次模型。

这与 M2 那次「审批绑了会话」是**同一个错的另一半**：票据已经改成只绑
动作指纹，登记表还绑着会话。修法同一条原则（`_find_by_fingerprint`）：

- **收尾**：task_id 对不上时按 `(kind, action_hash(params))` 再找一次，
  找到就收那条（deny → abandoned 同理）
- **挂起**：新会话撞上同一动作时复用老线（含被 WIP 挡回的），不开第二条；
  指纹不同仍然各自一条线

`tests/test_gate.py` 第 23 组 4 条断言盯这个。

### `ensure_jobs`：名字相同不代表定义相同

`claw-resume` 从 no_agent 脚本改成过 monitor 作业，而 `ensure_jobs` 按名字
判重 —— 老作业会一直跑一个已删掉的脚本，失败只记在 Hermes 侧日志里。
（test-home 的 `cron/jobs.json` 里就躺着一条这样的老定义，是活证据。）
现在存量作业与定义表**逐字段比对**（script / monitor_script / no_agent /
prompt / schedule），对不上就 `update_job` 按表修正，并在注册输出里喊出来。
`.hermes/home/scripts/claw_resume.py` 已删（无引用）。

## 4. 关键决策

- **`grant_read(principal="claw")` 按 L4 拒绝，且不发审批。**
  工具名不足以描述一个动作：同一个 `grant_read`，开给真人是正常业务，
  开给自己就是提权。只按工具名分级的话，L4 那组 `grant_self` 有一个换名字的绕过口。
  实现成 `policy.py` 里的 `ARG_DENY` 表（**加禁令 = 加一行**）。
  不发审批是因为——自我提权不是「问一下人就行」的事，问了反而给了一次被误批的机会。

- **`publish_gold` 的两条前置：没分类不发布、`_raw` 不出去。**
  没有分类就推不出遮蔽规则，analyst 读到的是明文；`<列>_raw` 是清洗前的原值，
  跟着发布等于清洗白做。这两条是**操作本身的正确性前提**，不是门禁 ——
  别把两层混起来。

- **发件永远留在我们这边，收件并进 M5。**
  铁律 2 要求 callback 是独立进程，它身上没有 Hermes，回执只能自己发；
  第二份删不掉的前提下，把门禁那侧改走 Hermes 的 adapter 只会从「一份」
  变成「两份不一样的」。收件的差距是真的（IMAP / 附件 / 验真），
  但 M5 本来就要把入站落到它的 adapter 上。

- **`tracing.py` 不与 Hermes 的 observability 合并。**
  它只支持 Langfuse，而且没有 `WAITING_FOR_HUMAN` 这种跨进程、跨天的 span 概念。

- **恢复用 `monitor_script` 而不是每分钟点模型。**
  恢复必须让 Agent 自己再调一次工具（这才叫驱动反转），所以要点模型；
  但一分钟一次显然不行。Hermes 的 `monitor_script` 每 tick 先跑一个便宜脚本、
  按字节哈希输出，**没变就整个跳过 agent 运行**。于是实际成本是一次 SQL 查询。

- **搬 cron 会丢掉一条性质，这是自觉的取舍。**
  `ops/scheduler.py` 原注释写着「独立于 Agent 运行：Agent 挂了催办也不能停」。
  搬进 Hermes 之后不成立。换来的是作业锁、claim fence、按 `next_run` 恢复、
  失败投递、输出留存 —— 那 89 行全都没有。丢掉的由 **M6** 补回来。

## 5. 踩过的坑 —— 全是同一个形状

**闸门读的量根本没人写，或者闸门挂在网络后面。失败方式都是安静的。**
这个项目已经在这个形状上摔过十二次，新加的断言专门盯这一类。

| # | 现象 | 真相 |
|---|---|---|
| 1 | `publish_gold` 的 `_raw` 检查「通过」 | 它挂在 Trino 查询后面，Trino 一挂根本走不到 —— 测试看到「调用失败了」照样算过。纯参数判断提到连库之前 |
| 2 | 预算兜底从来没触发过 | `usage_ledger` 里只有 `persona.py`（扮演人的模型）的花销，Claw 自己一分钱没记，读到的永远是 0 |
| 3 | `record_usage` 在本地永远静默失效 | 它自己连 DSN，没有 DSN 就 `return` |
| 4 | Postgres 起不来但没人发现 | `init-steward.sql` 少建五张表，`GRANT ON asset_semantics` 指向不存在的表，`psql -f` 断在那里 |
| 5 | 「网络内部匿名探测」整条静默 SKIP | 它走 `docker exec datalaker-scheduler-1`，而 M4 之后那个容器默认不再守护。**而且它本来就是假绿**：只判「异常 = 被挡住」，那么「容器压根连不到 trino」也算通过 |
| 6 | `ops/resumable.py` 作为 monitor 每分钟报一次错 | 全新库里 `runs` 表还没建，`resumable()` 是只读打开的不建表。monitor 崩掉每分钟就是一次错误 tick |
| 7 | 白名单可以被打穿 | `sender_allowed` 只比对 `From:`，而 `From:` 是发件人自己写的。把 From 填成王姐的地址就能进来 —— 她有权回答口径、转介角色 |
| 8 | 拔盘时 5.5 组会红 2 条而不是跳过 | `test_hermes_tool_loop` 的「真写 bronze」「lake 全量检查」挂在 `sync._trino`（无 TRINO_URL 时回落 `docker exec`）后面，组里却没有 lake 探活 —— docker-free 门槛永远达不到全绿。用假 docker（CLI exit 1、服务照跑）参考跑抓出来的。修法与 9.5 同款：**探活走干活同一条路**，连不上就 SKIP 那两条 |
| 9 | `ensure_jobs` 按表修正了存量作业，但外面什么都看不见 | 「喊出来」只喊给了 stdout，而 Hermes 在插件注册阶段把 **stdout 和 stderr 都吞掉**（oneshot 实测，两条流里都搜不到）。修正真的发生了，外面看着一切正常 —— 同一个形状的第九次。修法：`_announce()` 再写一行事件日志，断言查那份留得下来的 |
| 10 | `approvals` 两边表都在、名字也对，但 **PG 侧少 6 列** | `kind` / `options` / `question` / `evidence` / `abandoned_at` / `escalation_level` 只加进了 SQLite。后果不是「少个字段」：`ask()` 的 INSERT 直接崩，**Postgres 后端上提问、升级、放弃三条路全断**。parity 测试只比表集合，比不出列 —— 第 4 坑的列级版。修法：补列 + 把 parity 升到列级 + 列级 GRANT 也要盖住代码真会写的列 |
| 11 | 把 callback 起在别的端口，链接却永远指向 8787 | `notify.approval_links` 只读 `.env`，不读进程环境变量。而 8787 上正跑着 docker 里的另一个 callback（不同的库、不同的签名密钥），于是「令牌无效」或干脆连接被掐 —— 看着像门禁坏了，其实是信发错了地方。同一文件里 `NOTIFY_CHANNEL` 早就写了「进程环境变量优先于 .env」，只修了那一处 |
| 12 | 点了链接、决定落库了，回执线程却每次都崩 | `_receipt` 借调用方的 store，而调用方是 `with open_store(...)` —— with 一退出连接就关了。报「SQLite objects created in a thread can only be used in that same thread」，连「回执失败」这条事件都写不进去。`_notify_async` 早就写过「后台线程必须建自己的连接」，同样只修了那一处 |
| 13 | 第一个源接进来之后，再没有第二个源进得来 | **接入死锁**：`connect_source` 自己被 `_source_not_granted` 挡住 —— 「把源加进清单」的动作被「这个源还没在清单里」拒了。清单为空时未启用，所以第一个源侥幸通过，之后全死。表现是发现覆盖率永远停在 0.33，看着像 Agent 不够勤快。修法：加入白名单的动作豁免于白名单（仍然是 L3，要人批）|
| 14 | 门禁挡住了、账也记了，**信没发出去** | `_notify_async` 是 daemon 线程，`hermes -z` 这种一次性进程退出时直接被杀。长驻进程里永远看不出来。实测大 case 时前 6 封发出去了、后面全丢，那些线永远等一个不会来的决定。修法：`atexit` 里 join，总时长有上限 |
| 15 | 「明明批过了，还是说没注册」 | `register_source` 只写进程内存的 dict，而 Hermes 每次会话是新进程。凭证必须落库（`source_secrets`，Agent 无权读）|
| 16 | 同一张表被记成两条线，WIP 被自己撑爆 | 驱动脚本用 `source_id`、门禁用工具实参 `source`，**动作指纹因此对不上**，`_find_by_fingerprint` 认不出是同一件事。18 条排队、一条都批不下来。这个坑一直存在，只是修掉「同会话多动作被合并」之后才第一次暴露出来 —— 两个 bug 互相盖住了对方 |
| 17 | 换了模型之后，恢复作业彻底不动 | Hermes 对**没 pin 模型**的 cron 作业有花费保护：全局模型一换就 `[drift_skip:silent]` 跳过，而且「告警只发一次，之后一直跳过」。日志里只有一行 ERROR，再也没有第二行 —— 看起来像 monitor 坏了。修法：`ensure_jobs` 创建时 pin 到当前配置，并把 model 纳入 drift 比对（script → skills → model，这是第三次） |
| 18 | 一次没推成的唤醒，把「有活要干」的信号永久消费掉 | Hermes 的 monitor **在跑 agent 之前**就存新哈希（它自己的注释写着理由：失败的运行不该反复告警）。对告警是对的，对我们不对 —— 那条线之后永远 `unchanged`。修法不是去掉抑制（那就每分钟点一次模型），而是让输出**按格子慢变**：同格内不变，跨格变一次，失败的线自己重试。格子大小可调（调试按分钟，生产按小时） |
| 19 | 人批过的那次白批了：恢复时又发一份新审批 | 恢复发生在新会话，模型只知道「推进 acme 这条线」，不会把当初那句 `description` 一字不差再写一遍，`dsn` 更不该再念一遍。指纹对不上原票据 → 新审批 + 新线。**踩了两次**：先是 dsn，修完又栽在 description 上。修法：`IDENTITY_KEYS` 表声明哪些字段定义动作身份，不声明就是全字段（最严）。列身份字段而不是列要剔除的 —— 前者漏一个只是多发审批（吵但安全），后者漏一个是两个动作共用一张票（安全缺口） |
| 20 | 换个模型就一个工具都不调 | `tool_turns=0`，只回一句「我来处理」。裸调用时它会调 —— 差别是网关里工具走**延迟下发**，藏在 `tool_search` 后面，弱模型不会主动去搜。**省 token 省掉了整个能力**。修法：`tools.tool_search.enabled: off`（白名单已把工具集砍到几千 token，塞得进） |
| 21 | config 里 enable 了 memory，模型一调就被自己的门禁拒 | **打开了却不声明 = 打开了个寂寞。** `enabled_toolsets` 里的 Hermes 自带工具（memory / todo / clarify）没在 `policy.py` 里声明，撞「未声明 = L4 拒绝」，而那条拒绝消息还在教模型「请在 policy.py 中显式声明」—— 它当然做不到。`tests/test_toolset_whitelist.py` 现在拿 config 与 POLICY 对一遍 |
| 22 | 队列满了之后，**已经批准的动作也推不动** | WIP 检查排在票据检查**之前**。待办堆到上限时恢复也被拒，而堆着的那些待办**正是这些线自己** —— 死锁。实测：6 张票已批准未用，全被「steward 当前已有 3 件待办」挡在门外。修法：先查票，有票就跳过 WIP（WIP 限制的是「新请求会不会淹没人」，已批的不产生新打扰）|
| 23 | 恢复时又发一份新审批（第三次栽在这上面）| 前两次是 dsn、description。这次是**默认值**：`define_semantics` 的 `key` 可选带默认，模型第二轮没给，指纹算的是原始参数（看不到默认值），于是「给了 semantics」和「没给」成了两个动作。修法：`key` 改必填。**带默认值的身份字段是个陷阱** |
| 24 | monitor 只给了身份的一半，模型每次自己编另一半 | `IDENTITY_KEYS` 认 (asset, key)，而 `resumable.py` 的输出里只有 asset。模型每次编一个 key → 每次都是新动作 → 新审批 → 把队列占满 → 那条线永远推不动。修法：monitor 按 `IDENTITY_KEYS` 给全身份字段（凭证仍然不给）|
| 25 | 口径「记住了」，知识库里一条都没有 | `define_semantics` 又是个**只有 policy 声明、没有实现**的空工具（`sql_query`/`connect_source`/`describe_asset` 之后的第四个）。模型找不到它就**拿别的凑合** —— 把业务口径记进了 Hermes 自己的 `memory`，看着像记住了，而清洗、发布、判分读的都是 `asset_semantics`，那里是空的。换个会话换台机器全丢 |
| 26 | 洗完了,但一条规则都没生效 | 模型把规则名抄成人类可读的 `status / enum_drift`,实际标识符是 `enum_drift__status`。返回话术是「未执行(没批准这条规则)」—— 和真的没批准长得一模一样,而后果是**洗了等于没洗、看着还成功**。修法:给了规则却一条都没匹配上时明确报错并列出可用规则名 |
| 27 | 人定了「全大写」,数据被洗成小写 | `enum_drift` 的注释从 R2 起就写着「标准形取哪个**要人定**」,而实现一直写死 `lower()`。口径确实沉淀在 `asset_semantics` 里,**只是没有人去读** —— 「闸门读的量没人写」的镜像:量写了,闸门不读。修法:`clean.normalized_case()` 去查人定的口径;**看不懂就返回 None 不洗**,不许猜一个默认值 |
| 28 | 三条参数完全不同的线,被合并成一条 | 收窄身份字段之后,**参数里一个身份字段都没有**时 `clean` 退化成空字典,于是「同一个工具的任何调用」都算同一个动作。这就是注释里警告的「变松」真的发生了。修法:一个身份字段都没给到时退回全字段(最严) |
| 29 | 演练的审批信发到了真实 Gmail 地址 | 通道配置**只读 `.env`,不读进程环境变量** —— 同一个坑踩了四处:`NOTIFY_CHANNEL`(早修过)、`APPROVAL_BASE_URL`、`SMTP_*`、收件人 `MAIL_*`。想把信发到本地模拟邮箱就只能改仓库里那份给生产用的配置,漏改一处信就真发出去了。修法:统一走 `notify.cfg()`(环境变量优先);明文 SMTP **只允许打 127.0.0.1/localhost/greenmail**;说了要打本地就绝不走 Gmail API |
| 30 | 阶段提案发给了字面量 "sponsor" | 收件人解析拿不到角色对应的人时，**把角色名当邮箱用了**。信躺在一个叫 `sponsor` 的收件箱里，谁也看不到 —— 提案发出去了、没人收到，日志一切正常。`_notify_async` 早就按 `MAIL_<ROLE>` 兜底了，这里漏了同一步 |
| 31 | 身份字段名写错，恢复永远对不上 | 给 `ingest_export` 声明身份时想当然写了 `("source","table")`，而它的参数其实叫 `saas_source`；`publish_gold` 更是压根没有 source/table（它认 `silver_table`）。**这种错看起来完全正常**：声明有了、测试也过，只有真跑一次带附件的接入才暴露。修法：断言身份字段必须是工具 schema 里真有的参数名 |
| 32 | 同一张表被重复接入，人白点链接、源库白扫全表 | 模型每收到一封信就重新规划一遍。清单里标「已接入」不够 —— 它不一定去看清单。修法:`ingest_table` 在**动手之前**查 `sync_state`,刚接过就直接说「X 分钟前刚接过，没有重接；要刷新用 full_refresh」|

第 7 条的修法照 Hermes 的规则来（它在自己的 adapter 里引了 GHSA-rxqh-5572-8m77）：
只认收件服务器 prepend 的**第一条** `Authentication-Results`，
DMARC pass / SPF pass 域对齐 / DKIM `header.d` 对齐 三选一，没有这个头就不通过。
顺带修掉 `fetch_unread` 把重复头折叠成最后一个 —— 恰好是攻击者塞进来的那条。

#### ① 恢复整链：链子接起来了

零件此前各测各的（`resumable.py` 单测、`ensure_jobs` 在假 cron 面上测、
跨会话指纹在门禁单测里测），**整条链一次都没接起来过** —— 而这个项目
摔过的六次全是「零件全绿、链子断掉」。现在接起来了，主语是 Hermes：

```
会话 A：调 ingest_table（L3）→ 门禁挂起、runs 记线
tick  ：没人批 → monitor 输出没变 → **桩收到 0 个请求**（一分钟一次的成本是一次 SQL）
批准  ：独立连接写 decisions（铁律 2）
tick  ：输出变了 → 唤醒 → Agent 自己再调一次工具 → 票据消费 → bronze 真写 5 行
收尾  ：新会话 task_id 对不上 → 按动作指纹收掉**旧会话**那条线 → 重新静默
```

跑法：`hermes cron run claw-resume`（同步执行、走 monitor 门；`cron tick`
只跑到点的作业，测试里触发不了）。壳脚本必须是 `HERMES_HOME/scripts/` 下的
**真文件** —— Hermes `resolve()` 后再校验，软链被穿透后拒掉。

**顺带修掉一个静默**：`ensure_jobs` 修正存量作业时的「按表修正」print，
在 Hermes 的插件注册阶段 **stdout 和 stderr 都被吞掉**（oneshot 实测，
两条流里都搜不到）。改成 `_announce()`：print 照旧，再写一行事件日志
（`events.run_id='cron'`），那份是留得下来的。断言查的是事件日志。

#### ④ 周报改成提案 —— 已落地，三层别混

`claw-weekly-report` 从 `no_agent` 脚本改成**带 skill 的 agent 作业**。
「不点模型」在这里不是优点：周报写给人看、要给建议和理由。一周一次，
成本可忽略。真该 `no_agent` 的是催办（升级阶梯是确定性判断）。

```
skill   claw-stage-proposal   写成什么样、必须调哪个工具  —— 引导，可以不听
工具    propose_stage_decision 把小结变成三选一的提问（L1）—— 只发问，不改东西
门禁    _silver_round_closed   没人拍 start_silver 就不许洗 —— 强制，绕不过
```

几个当时想清楚了的点：

- **脚本从「作业本体」降级成「数据源」。** `ops/weekly-report.py` 一行没改：
  agent 模式下它的 stdout 会以 `## Script Output` 注入 prompt。四段数字仍由
  它查库算 —— 那是事实，不该让模型编。提示词里明写「不要重算」。
- **工具是 L1，不是 L2。** 与 `propose_cleaning` 同构：提案本身不改任何东西。
  设成 L2 的话，「发问」这件事自己也要先被批一次，套娃。
- **三个选项只在 `policy.py` 定义一处**，工具建提案、令牌校验点击、门禁判轮
  开没开都读它。抄成三份必然漂移，而漂移的表现是「人点了链接但决定落不进去」。
- **`decisions.chosen` 这一列 R2 就建好了，从来没人往里写。** 于是「人选了哪个」
  只活在邮件正文里，判分读不到。补上了写侧（callback 新增 `/choose` 路由，
  三选一各签一枚一次性令牌），而不是在判分那边猜。
- **skill 走 user 消息注入，不撞「限制不许写进提示词」那条断言**（那条只扫
  `role == "system"`）。但 skill 里照样不写限制 —— 写了也证明不了绕不过。
- **skill 名字出现在 prompt 里 ≠ 加载成功**：加载失败时 Hermes 塞的
  「not found and skipped」notice 里同样点了名字。断言要认内容
  （`follow its instructions` 在、`not found and skipped` 不在）。
  第一次跑就是这么发现 `external_dirs` 没配进 test-home 的。

`tests/test_weekly_proposal.py` 23 条把三层串起来跑真的 cron，验收是**库里那一行**。

#### ⑤ 停止信号 + 阶段报告 —— 已落地

`ops/stage-report.py`：全部线到终态 **或** 天数上限，二者先到为准。
到了就出阶段报告、落 `ROUND_CLOSED` 事件，门禁的 `_quiet_period` 读那条事件
——终态之后 L2 以上的动作一律拒（L0/L1 照放，否则连下一份提案都发不出去，
死锁）。**先落状态再发信**：发信失败时轮已经关了，比「发了报告还在到处
发起新动作」安全；而且判分要求报告不早于锚点。

#### ⑥ 源必须从邮件里来 —— 已落地，这是本阶段最本质的一次修正

**在此之前 `reveal_grant()` 直接往 `source_grants` 写一行。那是演的** ——
真实环境里没有任何人能凭空开权限。人给源只有两种形态：邮件正文里写
`host:port/db` + 账号密码，或者发个配置文件。

现在的链路：

```
人的信里带连接串 → Agent 调 connect_source(source_id, dsn)（L3）
  → 门禁挂起 → sponsor 点链接批
  → register_source 拿那次批准当依据（没有批准就没有数据源）
  → 凭证进 source_secrets（**Agent 读不到那张表**）
  → source_grants 由这次注册写 → 之后才碰得到这个源
```

关键点：

- **`CLAW_NO_BOOTSTRAP_SOURCES=1` 必须在 eval 里开。** `connector._BOOTSTRAP`
  预置了 5 个源的 DSN，只要它非空，Agent 不注册也连得上 —— 整条
  「源是人给的」就还是口号，trap 与发现覆盖率两维全是假的
- **`source_secrets` 是新表，PG 侧故意不给 `agent_role` SELECT。**
  「Agent 不持有 DSN」从文件开头那句架构注释变成了列级机制
- **驱动器一行权限表都不写**（`test_case_v2.py` 有断言钉住）
- 云上的 IAM role / IRSA 形态没做 —— 现在支持的是最常见的那条（邮件给明文）

#### ⑦ 连表 —— 已落地

**源系统禁 join，lake 里随便 join**（铁律 3）。准入规则 R2 就写全了
（`connector.review_sql`：lake 走 trino 方言、只准查 `iceberg.*`、JOIN 不算
风险项；source 则 JOIN 先问人）。**缺的一直是工具本身**：`sql_query` 在
`policy.py` 里声明了 L1，却从来没有 schema 也没有 handler ——
于是 Agent 根本没有办法连表。与 `connect_source` 之前一样是个空声明。

补了两个：

- **`sql_query`（L1）**：plane=lake 走 `sync._trino`，plane=source 走
  `connector.query`。handler 里**一行准入判断都没有** —— 门禁放行时会把
  重写过的 SQL（补了 LIMIT 等）合并回参数，两处各判一遍必然漂移
- **`describe_asset`（L0）**：列、类型、主键、**外键指向**、以及可用的
  join 路径。关系是源库自己声明的（`pg_constraint`），比猜表名准。
  join 路径**只给两边都已落进 lake 的**，且写成 `iceberg.bronze."源__表"`
  的形式 —— 在源库上提示「你可以这样 join」等于鼓励它去踩铁律 3 那条线

`tests/test_join.py` 17 条：源库 JOIN 被拦（注释分隔也拦得住，看 AST 不看
字面）、lake JOIN 直接放行且**真查出数据**、跨 catalog 被拒、未限定表被拒、
外键与 join 路径正确、对端没接进来的关系不出现在路径里。

#### ⑧ 入站接进会话 —— 已落地，走 Hermes 自己的链接层

5.2 组测的是 adapter 单体，证明「收得到、验得出真伪」，但**没有人把信
喂给 Agent**。现在 `hermes gateway run` 真起起来，整条链跑通：

```
mailsim 发信 → GreenMail → 网关轮询 → 验真 → 会话 → 模型 → 工具 → 回信
```

## 10. 不要做的事

- **不要把限制写进 system prompt。** 那一段只放「什么时候该停下来问人」的**引导**，
  模型可以不听而门禁照样拦得住。有一条断言专门检查提示词里没有「你不可以」。
- **不要在工具 handler 里判审批。** 被拦时 handler 根本不跑；写了就是把限制
  散进业务代码。有断言在 grep `find_valid` / `is_denied`。
- **不要 fork Hermes。** 允许改，但尽量不改 —— 这个 checkout 最后要变成产品本体。
- **不要写一个没跑过的断言数。**
- **不要把「异常 = 被挡住」当成安全断言。** 先证明连得上，再证明进不去。
- **Docker 连不上时不要发散排查。** 默认原因就是外置盘掉线：确认盘 → 重启 Docker →
  还不行就问人。`builder prune` / legacy builder 在只读文件系统上全部无效。
