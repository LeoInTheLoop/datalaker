# Data Steward Claw

一个持续负责企业数据的数据管家：发现散落的数据，找人确认含义与权限，
将数据整理到可独立使用的 lakehouse，并维护负责人、口径、关联和来源记录。

**目标是让原本孤立的数据产生可核验的联合信息。** 例如订单表只能看销售额；
连接成本、退款和回款记录，并确认客户对应关系及计算口径后，才能回答
“哪些客户销售额高，但利润低、回款慢”。Agent 负责推进这项工作，关键业务决定由人确认。

开发规范统一见 [CLAUDE.md](CLAUDE.md)。下面区分产品目标与当前代码，
不以机制测试通过代表生产可交付。

## 工作闭环

1. **发现与登记**：读取获准访问的数据源，记录结构、负责人和来源。
2. **理解与确认**：提出字段含义、跨表关系和质量问题，向相关人员求证。
3. **整理与关联**：获批后接入数据，按确认口径清洗、建立关联，保留原值和依据。
4. **交付与使用**：发布有权限控制的数据及定义，让下游直接查询并复核答案。
5. **持续维护**：复查源变化、知识有效性和未解决事项，更新档案与受影响的数据。

最终交付包括可查询的数据、已确认口径、负责人和权限关系、来源与处理记录。
Agent 停止运行时，已有交付物仍应可用；新同步、催办和自动维护会随对应进程停止。

## 基于 Hermes 扩展数据治理能力

**本项目的数据治理扩展名为 `data-steward`，使用 Hermes 原有 agent loop，
给它注册数据治理工具，在工具调用前后接入
审批、权限校验和状态记录，并使用 Hermes 自己的 cron 推进长时任务。**
模型思考、选择工具、读取结果并继续执行的循环仍由 Hermes 负责，没有另建一套 agent loop。

| Hermes 的机制 | 本项目接入的能力 |
|---|---|
| 工具注册与分发 | 接库、查结构、清洗、发布、记录口径等工具，调用 `services/` 中的业务代码 |
| `pre_tool_call` hook | 执行前检查策略、审批票据、参数、预算和 WIP 等条件 |
| `post_tool_call` hook | 记录执行结果、更新任务状态与资产来历 |
| `post_llm_call` hook | 记录模型用量 |
| cron | 检查可恢复任务、催办、生成阶段提案；有状态变化时才唤醒模型恢复任务 |
| 提示词与 Skill | 提供数据管家的工作说明和提案写法，执行约束由代码落实 |

`data-steward` 从 `.hermes/plugins/data-steward/` 注册，插件与工具集使用同名标识。
“插件”指 Hermes 加载这些代码的方式，
不是另一个运行框架。具体逻辑分布在该目录、`plugins/datasteward_gate/` 和 `services/`；
目录分开不代表进程分开。邮件入站使用 Hermes 适配器，通知发送仍有本项目自己的路径。

开发时优先使用 Hermes 扩展接口。接口无法满足必要的执行、状态或上下文需求时，
允许对本体做最小修改，并记录原因、兼容影响和验证结果；当前使用扩展接入。

独立于 Hermes 运行的部分：

- **审批 callback**：使用独立进程和数据库账号接收签名审批、写入决定，Agent 无权自行写入。
- **数据平台与治理数据库**：保存 lake 数据、口径、角色、审批和任务记录，可独立查询。
- **体外监控（待补）**：负责 Hermes 故障后拉起及进程级限额；目前已有只读状态面板。

审批与执行的主要路径：

```text
Hermes agent loop 选择工具
  → pre_tool_call 校验
      → 放行：执行工具 → post_tool_call 记账 → 结果返回 Hermes agent loop
      → 待审批：持久化任务并通知人
          → 独立 callback 写决定
          → Hermes cron 的 monitor 检测到变化
          → 唤醒 Hermes agent loop，重新调用工具并再次校验
```

允许的动作与审批角色由策略表决定。SQL 执行还有 Connector / lake 入口校验和数据库权限。
在 Trino 中引用外部 catalog 仍可能访问源系统；重分析使用已复制到 Iceberg 的数据。

## 要长期维护的知识

领域知识保存在治理库中，按资产、人员和业务问题查询。Hermes 的通用 memory
可保留沟通偏好，但不能成为口径、权限或资产来源的唯一存储。

| 知识 | 例子 | 更新方式（目标） |
|---|---|---|
| 观测事实 | 列、类型、主外键、数据画像、采集时间 | 由采集模块写入并保留版本 |
| 待验证推断 | CRM 客户与订单客户的对应关系 | 模型可提出与修订，注明依据和状态 |
| 已确认定义 | 收入口径、空值含义、实体映射 | 经有权人员确认，保留证据和适用范围 |
| 组织关系 | 谁负责资产、谁可确认哪类事项 | 联系信息可维护，审批资格变更单独授权 |
| 工作经验 | 被否定的关联、质量问题、有效修复规则 | 保留适用条件、结果和失效原因 |
| 可复用答案 | 业务问题、核验过的 SQL、依赖资产版本 | 依赖变化时标记待复核 |

日常查询优先读档案，同时返回观测时间和有效状态。**旧档案是比较基线，不能证明源库没有变化。**
发现变化仍需定期轻量读取元数据、数据检查或外部事件；随后标记受影响的知识并生成复核任务。
新知识当场落库，定期任务负责复查、失效处理和冲突整理。

这套完整的认知维护机制是目标。观测、推断、确认、否定四类已按状态分行存进
`asset_catalog`（推断不覆盖事实，确认不覆盖推断，被否定的假设留痕），
读档默认不回源并报出快照时刻；失效判定与定期复查尚未建立，见下表。

## 如何判断有价值

对同一组业务问题，在同一数据快照、访问范围和核验标准下比较三种条件：

| 条件 | 衡量的增量 |
|---|---|
| 单表 | 原来能正确回答哪些问题 |
| 多表直接关联，保留原始口径 | 数据连接本身增加了什么信息，也引入了哪些错误 |
| 治理后关联，实体与口径已确认 | 数据管家的治理增加了多少可靠答案 |

先做两个真实的跨表问题，分别记录：新增正确答案数 / 总问题数、关联与计算正确性、
经业务核验的新增发现，以及结论能否追溯到记录和口径。避免用信息条数代替有效发现。
这是一组待建设的价值评估，不能用已有 DQ 召回率代替。

安全与运行可靠性单独设门槛：有无越权动作、源库负载是否满足约定、恢复是否重复执行、
任务结束是否停止。机制测试、脚本安排工具的演练、模型自主选工具的实测分别报告。
百分比带分母，重复实验带次数；没有测量就标明未测。

已有 [DQ 汇总](evals/report/aggregate.md) 记录注入集检出 133/155，属于该批历史数据上的规则表现。
当前 v2 阶段报告判分存在收件人兜底过宽的问题，源快照变化的二值结果也不能直接称为越权写入率。
源系统有正常业务写入时，还需独立证据区分变更来源。

## 下一步的三个完成点

1. ~~**认知可复用**~~：已完成（2026-09-06）。采集即建档；`describe_asset` 默认读档案、
   报快照时刻，源库断开仍能给出结构、负责人和口径，并标出观测／推断／已确认。
   验收记录见 [R6 §8](docs/handoff/R6.md)。
2. **认知会更新**：测试环境改变结构或关系后，巡检发现差异，标记旧结论并生成复核任务。
   **档案是比较基线，不能替代观测** —— 发现变化仍需新的轻量采集。
3. **关联有价值**：两套无显式外键的系统，经实体与口径确认后，正确回答单表无法回答的问题。

联系人与知识接口是前两项的支撑；维护审批边界、补齐判分和运行监控需与相应链路一起验收。

## 范围与阅读入口

当前主线是结构化数据及文件接入、批量整理、业务口径和权限治理。
源系统只观测和建议，源侧修复由其负责人完成。SaaS 数据优先走导出接入，
权限元数据走受控只读接口；具体厂商适配不视为通用接入已完成。

企业已有 lake 时，目标是治理既有资产并补齐外部数据，不要求另建一套。
多引擎适配需另验；实时流式接入、媒体治理、下游 RAG 和 ontology 暂不进入当前完成标准。
OpenMetadata 目前不是运行前提，历史选型仅作背景参考。
